    持续集成测验¶

    测验说明

    本测验用于检验持续集成/持续部署知识的掌握程度。共 15 道选择题，覆盖 CI/CD 概念、Jenkins Pipeline、GitHub Actions、Docker 应用和质量门禁。

    📙 中级难度 ⏱ 约 20 分钟 📝 15 道选择题

    第 1 题：CI/CD 基本概念¶

    持续集成（CI）的核心实践是什么？

    • A. 每月合并一次代码
    • B. 开发人员频繁地将代码集成到共享分支，每次集成自动触发构建和测试
    • C. 只在发布前进行一次集成测试
    • D. 将所有代码放在一个文件中
    查看答案

    答案：B 持续集成（Continuous Integration）强调开发人员至少每天一次将代码集成到主干分支，每次集成自动触发编译、单元测试和接口测试，尽早发现和修复集成问题，避免"集成地狱"。

    第 2 题：CI 与 CD 的区别¶

    以下关于 CI 和 CD 的描述，哪个是正确的？

    • A. CI 是持续集成，CD 只指持续部署（Continuous Deployment）
    • B. CI 是持续集成，CD 可以指持续交付（Continuous Delivery）或持续部署（Continuous Deployment）
    • C. CI 和 CD 是完全相同的概念
    • D. CI 指代码审查，CD 指代码部署
    查看答案

    答案：B CI（Continuous Integration）是持续集成。CD 有两种含义：持续交付（Continuous Delivery）确保代码随时可发布，但需要人工审批后部署；持续部署（Continuous Deployment）则完全自动化，代码通过测试后自动部署到生产环境。

    第 3 题：Jenkins Pipeline 基础¶

    在 Jenkins 声明式 Pipeline 中，以下哪个关键字用于定义流水线的各个阶段？

    • A. steps
    • B. stage
    • C. node
    • D. job
    查看答案

    答案：B Jenkins 声明式 Pipeline 使用 pipeline → stages → stage 结构。stage 定义流水线的各个阶段（如 Build、Test、Deploy），steps 定义阶段内的具体操作，node 是脚本式 Pipeline 中的概念。

    第 4 题：Jenkinsfile 语法¶

    以下 Jenkinsfile 语法中，哪个是正确的声明式 Pipeline 结构？

    • A. pipeline { stages { stage('Build') { steps { echo 'Building' } } } }
    • B. job { steps { echo 'Building' } }
    • C. build { task('Build') { run { echo 'Building' } } }
    • D. workflow { phase('Build') { action { echo 'Building' } } }
    查看答案

    答案：A Jenkins 声明式 Pipeline 必须以 pipeline 块开始，包含 stages 块，每个阶段用 stage 定义，具体操作放在 steps 块中。这是 Jenkins Pipeline 的标准语法结构。

    第 5 题：Jenkins 触发机制¶

    以下哪种方式可以自动触发 Jenkins Pipeline 执行？

    • A. 只能手动点击"Build Now"
    • B. 配置 Webhook，当代码推送到 Git 仓库时自动触发
    • C. 每天定时手动执行
    • D. 需要重启 Jenkins 服务才能执行
    查看答案

    答案：B Jenkins 支持多种自动触发方式：①Git Webhook（代码推送触发）②定时构建（类似 cron 表达式 H/5 * * * *）③轮询 SCM（定时检查代码变更）④其他 Pipeline 触发。Webhook 是最常用的方式，实现真正的持续集成。

    第 6 题：GitHub Actions 基础¶

    在 GitHub Actions 中，一个 Workflow 文件应该放在哪个目录下？

    • A. .github/workflows/
    • B. .ci/pipelines/
    • C. jenkins/
    • D. actions/config/
    查看答案

    答案：A GitHub Actions 的 Workflow 文件必须放在仓库的 .github/workflows/ 目录下，使用 YAML 格式编写。文件名任意（如 ci.yml），通过 on 字段定义触发条件。

    第 7 题：GitHub Actions 触发事件¶

    在 GitHub Actions 中，以下哪个 on 配置可以在代码推送到 main 分支时触发 Workflow？

    • A. on: click
    • B. on: push: branches: [main]
    • C. on: schedule
    • D. on: manual
    查看答案

    答案：B GitHub Actions 使用 on 字段定义触发事件。on: push: branches: [main] 表示当代码推送到 main 分支时触发。还可以使用 on: pull_request、on: schedule（定时）、on: workflow_dispatch（手动）等。

    第 8 题：GitHub Actions Job 与 Step¶

    在 GitHub Actions 中，以下关于 Job 和 Step 的描述，哪个是正确的？

    • A. 一个 Step 包含多个 Job
    • B. 一个 Job 包含多个 Step，不同 Job 默认并行执行
    • C. Job 和 Step 是相同的概念
    • D. Step 必须使用 Docker 容器
    查看答案

    答案：B GitHub Actions 的结构是 Workflow → Job → Step。一个 Workflow 包含一个或多个 Job，每个 Job 运行在独立的 Runner 上。不同 Job 默认并行执行（可用 needs 设置依赖），同一个 Job 内的 Step 按顺序串行执行。

    第 9 题：Docker 在 CI 中的作用¶

    在 CI/CD 中使用 Docker 的主要优势是什么？

    • A. 只是为了减少代码量
    • B. 保证构建和测试环境的一致性，实现"一次构建，到处运行"
    • C. Docker 会自动编写测试用例
    • D. Docker 可以替代所有 CI/CD 工具
    查看答案

    答案：B Docker 容器化将应用及其依赖打包在一起，解决了"在我机器上能跑"的环境问题。在 CI/CD 中，可以使用 Docker 镜像作为构建环境，保证开发、测试和生产环境完全一致，也便于快速创建和销毁测试环境。

    第 10 题：Dockerfile 在 CI 中的应用¶

    以下 Dockerfile 指令中，哪个用于指定基础镜像？

    • A. RUN
    • B. COPY
    • C. FROM
    • D. CMD
    查看答案

    答案：C FROM 指令指定构建镜像的基础镜像，是 Dockerfile 的第一条指令（ARG 除外）。RUN 执行命令，COPY 复制文件，CMD 指定容器启动时的默认命令。

    第 11 题：构建流水线设计¶

    一个标准的 CI/CD 流水线通常包含以下哪些阶段？

    • A. 只有代码编写
    • B. 构建（Build）→ 单元测试 → 集成测试 → 部署（Deploy）
    • C. 只有部署
    • D. 编写文档 → 代码审查 → 发布
    查看答案

    答案：B 标准的 CI/CD 流水线通常包括：代码提交 → 构建（编译/打包）→ 单元测试 → 集成/接口测试 → 代码质量检查 → 部署到测试环境 → 验收测试 → 部署到生产环境。每个阶段都可能设置质量门禁。

    第 12 题：构建制品管理¶

    在 CI/CD 流程中，构建制品（Artifacts）应该存储在哪里？

    • A. 开发人员的本地电脑
    • B. 制品仓库（如 Nexus、Harbor）进行统一管理
    • C. Git 代码仓库中
    • D. 随意放在临时目录
    查看答案

    答案：B 构建制品（如 JAR 包、Docker 镜像）应存储在专用的制品仓库中（如 Nexus、JFrog Artifactory、Harbor）。这样可以版本化管理、控制访问权限、避免 Git 仓库臃肿，并且方便在不同环境间传递和部署。

    第 13 题：质量门禁¶

    质量门禁（Quality Gate）在 CI/CD 中的作用是什么？

    • A. 限制开发人员的代码提交频率
    • B. 在流水线的某个阶段设置通过条件，不满足则阻止流程继续
    • C. 只用于检查代码格式
    • D. 限制 CI/CD 工具的使用次数
    查看答案

    答案：B 质量门禁是在 CI/CD 流水线中设置的检查点，定义了代码必须满足的条件（如测试覆盖率 ≥ 80%、无严重 Bug、代码扫描通过等）。不满足条件时流水线会失败，阻止问题代码进入下一阶段，确保软件质量。

    第 14 题：代码质量扫描¶

    在 CI/CD 流水线中集成代码质量扫描工具，以下哪个是常用的代码质量平台？

    • A. SonarQube
    • B. Photoshop
    • C. Microsoft Word
    • D. Chrome 浏览器
    查看答案

    答案：A SonarQube 是最流行的代码质量和安全扫描平台，支持 30+ 种编程语言，可以检测代码异味、Bug、安全漏洞和测试覆盖率。通常集成在 CI 流水线中作为质量门禁的一部分。

    第 15 题：Jenkins Pipeline 并行执行¶

    在 Jenkins 声明式 Pipeline 中，如何实现多个阶段并行执行？

    • A. 在 stage 内部使用 parallel 块
    • B. 创建多个 Jenkinsfile
    • C. 在 post 块中配置
    • D. 使用 input 关键字
    查看答案

    答案：A Jenkins 声明式 Pipeline 支持在 stage 内部使用 parallel 块并行执行多个分支。例如可以同时在不同浏览器上运行 UI 测试，或同时执行单元测试和接口测试，提高流水线执行效率。
