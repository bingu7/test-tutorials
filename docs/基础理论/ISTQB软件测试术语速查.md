## 新手导读

很多新人会“会做但说不清”。例如把冒烟测试、回归测试、系统测试混在一起，把严重程度和优先级混在一起。术语速查的目标不是背定义，而是让你在沟通时减少误解。

建议学习方式：

1. 先看中文解释，理解工作场景。
2. 再记英文术语，方便读官方文档和面试表达。
3. 最后看“常见误区”，避免说错。

## 一、测试基础概念

| 中文 | 英文 | 通俗解释 | 工作场景 |
|------|------|----------|----------|
| 软件测试 | Software Testing | 通过评估和验证降低软件质量风险 | 执行用例、评审需求、分析缺陷 |
| 缺陷 | Defect / Bug | 实际结果和期望结果不一致 | 登录失败、金额错误、越权访问 |
| 错误 | Error | 人在理解、设计或编码时犯的错 | 需求理解错、代码写错 |
| 失效 | Failure | 软件运行时表现出来的问题 | 页面报 500、按钮无响应 |
| 质量 | Quality | 产品满足需求和用户期望的程度 | 功能、性能、安全、易用性 |
| 风险 | Risk | 可能发生的问题及其影响 | 支付错误、数据泄露、库存超卖 |

常见误区：

- 缺陷不是只来自代码，也可能来自需求、设计、配置、数据和环境。
- 测试不能证明软件没有缺陷，只能降低未知风险。
- 没有发现 Bug 不等于质量好，可能是测试不充分。

## 二、测试级别

| 中文 | 英文 | 关注对象 | 常见负责人 |
|------|------|----------|------------|
| 单元测试 | Unit Testing | 函数、方法、类 | 开发 |
| 集成测试 | Integration Testing | 模块之间的数据交互 | 开发 + 测试 |
| 系统测试 | System Testing | 完整系统 | 测试 |
| 验收测试 | Acceptance Testing | 是否满足业务验收标准 | 产品、用户、测试 |

例子：

```text
优惠金额计算函数是否正确 -> 单元测试
订单服务调用库存服务是否正确 -> 集成测试
用户从下单到支付是否正确 -> 系统测试
业务方确认活动规则是否满足上线要求 -> 验收测试
```

常见误区：

- 接口测试不等于集成测试，但接口测试经常承担集成验证的工作。
- 验收测试不只是点页面，也要确认业务目标是否达成。

## 三、测试类型

| 中文 | 英文 | 目的 |
|------|------|------|
| 功能测试 | Functional Testing | 验证功能是否符合需求 |
| 非功能测试 | Non-functional Testing | 验证性能、安全、兼容、易用等质量属性 |
| 回归测试 | Regression Testing | 验证修改没有破坏已有功能 |
| 冒烟测试 | Smoke Testing | 快速确认核心流程是否可测 |
| 探索式测试 | Exploratory Testing | 边学习、边设计、边执行测试 |
| 兼容性测试 | Compatibility Testing | 验证不同系统、浏览器、设备表现 |
| 性能测试 | Performance Testing | 验证响应时间、吞吐量、稳定性 |
| 安全测试 | Security Testing | 验证认证、授权、输入校验、数据保护 |
| 可用性测试 | Usability Testing | 验证用户是否容易理解和使用 |

对比：

| 类型 | 什么时候做 | 结果怎么判断 |
|------|------------|--------------|
| 冒烟测试 | 新版本刚部署后 | 主流程是否可继续测试 |
| 回归测试 | 修复缺陷或改动功能后 | 老功能是否被影响 |
| 探索式测试 | 需求复杂或风险高时 | 是否发现脚本用例没覆盖的问题 |

## 四、测试设计技术

| 中文 | 英文 | 适合场景 |
|------|------|----------|
| 等价类划分 | Equivalence Partitioning | 输入范围可分为有效和无效集合 |
| 边界值分析 | Boundary Value Analysis | 数值、长度、时间边界 |
| 判定表 | Decision Table Testing | 多条件组合影响结果 |
| 状态迁移测试 | State Transition Testing | 订单、流程、审批、支付状态 |
| 场景测试 | Scenario Testing | 用户完整业务流程 |
| 错误推测 | Error Guessing | 根据经验补充易错点 |

例子：

```text
手机号必须 11 位：
等价类：空、10 位、11 位、12 位、包含字母
边界值：10 位、11 位、12 位

订单状态：
待支付 -> 已支付
待支付 -> 已取消
已支付 -> 退款中
已取消 -> 不允许支付
```

常见误区：

- 等价类和边界值不是只用于输入框，也适用于接口参数、文件大小、并发数、时间范围。
- 场景法不能替代异常测试，只覆盖主流程是不够的。

## 五、测试工作产品

| 中文 | 英文 | 用途 |
|------|------|------|
| 测试计划 | Test Plan | 明确范围、资源、排期、风险、准入准出 |
| 测试策略 | Test Strategy | 明确整体测试方法和测试类型组合 |
| 测试用例 | Test Case | 描述可执行的步骤和期望结果 |
| 测试数据 | Test Data | 支撑测试执行的数据 |
| 缺陷报告 | Defect Report | 记录问题、证据、影响和期望 |
| 测试报告 | Test Report | 汇总执行结果、缺陷、风险和上线建议 |

一条清晰链路：

```text
需求 -> 测试计划 -> 测试用例 -> 测试执行 -> 缺陷报告 -> 回归验证 -> 测试报告
```

## 六、缺陷管理术语

| 中文 | 英文 | 说明 |
|------|------|------|
| 严重程度 | Severity | 缺陷对系统或用户的影响程度 |
| 优先级 | Priority | 缺陷应该多快被修复 |
| 阻塞 | Blocker | 导致测试无法继续或核心流程不可用 |
| 复现步骤 | Steps to Reproduce | 让别人能重现问题的操作过程 |
| 实际结果 | Actual Result | 系统现在发生了什么 |
| 期望结果 | Expected Result | 系统应该发生什么 |
| 回归验证 | Retest / Regression Verification | 修复后验证问题是否解决 |

严重程度和优先级区别：

| 场景 | 严重程度 | 优先级 |
|------|----------|--------|
| 支付金额错误 | 高 | 高 |
| Logo 显示错位 | 低 | 可能低 |
| 活动页文案错别字，明天上线 | 低 | 可能高 |
| 后台低频统计报表字段错误 | 中 | 可能低 |

## 七、测试管理术语

| 中文 | 英文 | 说明 |
|------|------|------|
| 准入标准 | Entry Criteria | 什么条件满足后可以开始测试 |
| 准出标准 | Exit Criteria | 什么条件满足后可以结束测试 |
| 测试覆盖率 | Test Coverage | 测试覆盖需求、代码、接口或风险的程度 |
| 测试估算 | Test Estimation | 评估测试工作量和时间 |
| 测试监控 | Test Monitoring | 跟踪测试进度、缺陷、风险 |
| 测试控制 | Test Control | 根据监控结果调整计划和优先级 |
| 风险测试 | Risk-based Testing | 按风险大小分配测试资源 |

准入标准示例：

- 需求评审完成。
- 测试环境可访问。
- 开发自测通过。
- 冒烟用例通过。
- 测试数据准备完成。

准出标准示例：

- P0/P1 用例全部通过。
- P0/P1 缺陷全部关闭。
- 核心接口和主流程回归通过。
- 遗留风险已评估并被产品或项目负责人接受。

## 八、敏捷与 DevOps 术语

| 中文 | 英文 | 说明 |
|------|------|------|
| 用户故事 | User Story | 从用户角度描述需求 |
| 验收标准 | Acceptance Criteria | 判断故事是否完成的标准 |
| 持续集成 | Continuous Integration | 代码频繁合入并自动构建测试 |
| 持续交付 | Continuous Delivery | 代码始终处于可发布状态 |
| 持续部署 | Continuous Deployment | 通过流水线自动发布到生产 |
| 测试左移 | Shift Left Testing | 更早参与需求和设计评审 |
| 测试右移 | Shift Right Testing | 关注上线后的监控和反馈 |
| 质量门禁 | Quality Gate | 不满足质量条件时阻止合并或发布 |

例子：

```text
测试左移：需求评审时发现“优惠券叠加规则”没写清楚。
测试右移：上线后观察错误日志、接口成功率、支付回调延迟。
质量门禁：P0 冒烟测试失败时不允许发布。
```

## 九、自动化测试术语

| 中文 | 英文 | 说明 |
|------|------|------|
| 测试脚本 | Test Script | 自动化执行的代码 |
| 测试套件 | Test Suite | 一组相关测试用例 |
| 测试夹具 | Fixture | 用例执行前后的准备和清理 |
| 数据驱动 | Data-driven Testing | 同一逻辑使用多组数据执行 |
| 关键字驱动 | Keyword-driven Testing | 用关键字描述测试操作 |
| 页面对象模型 | Page Object Model | 把页面元素和操作封装成对象 |
| 易碎测试 | Flaky Test | 结果不稳定、时好时坏的测试 |
| 测试报告 | Test Report | 展示执行结果、失败原因和附件 |

常见误区：

- 自动化不是把所有手工用例都转成脚本。
- 自动化不能无人维护。
- UI 自动化越多，维护成本通常越高。
- 稳定的接口自动化通常比大量 UI 自动化更适合回归。

## 十、接口测试术语

| 中文 | 英文 | 说明 |
|------|------|------|
| API | Application Programming Interface | 系统之间交互的接口 |
| 请求方法 | HTTP Method | GET、POST、PUT、PATCH、DELETE 等 |
| 请求头 | Header | 鉴权、内容类型、客户端信息等 |
| 请求体 | Body | POST/PUT/PATCH 常见参数位置 |
| 状态码 | Status Code | HTTP 层处理结果 |
| 业务码 | Business Code | 系统自定义业务结果 |
| 鉴权 | Authentication | 证明“你是谁” |
| 授权 | Authorization | 判断“你能做什么” |
| 幂等 | Idempotency | 同一请求多次执行结果一致或可控 |
| 契约测试 | Contract Testing | 验证服务之间接口约定是否兼容 |

容易混淆：

```text
认证 Authentication：验证身份，例如登录。
授权 Authorization：验证权限，例如是否能查看别人的订单。
```

## 十一、面试表达模板

当面试官问“你怎么理解软件测试”时，可以这样回答：

```text
软件测试不是简单找 Bug，而是通过需求分析、测试设计、测试执行、缺陷跟踪和风险评估，帮助团队判断产品是否满足需求、是否具备上线条件。

从测试级别看，有单元测试、集成测试、系统测试和验收测试；从测试类型看，有功能、接口、性能、安全、兼容、回归等。实际项目中我会根据业务风险和测试成本安排优先级，例如订单、支付、权限这类高风险模块会优先覆盖。
```

当面试官问“严重程度和优先级区别”时，可以这样回答：

```text
严重程度表示缺陷影响有多大，优先级表示应该多快修。比如支付金额错误严重程度和优先级都高；页面文案错别字严重程度低，但如果当天要上线，优先级也可能高。
```

## 动手任务：给一份术语混乱的缺陷报告做「术语纠偏」，并判定测试级别与类型

> 这是本教程的收尾练习。请**独立完成**，不要先看参考答案。目标不是"把词换成英文"，而是**让每个结论都能对一个 ISTQB 标准定义负责**。

### 任务背景

你新接手一个测试项目，翻看前任留下的缺陷报告与测试记录，发现术语使用很随意：
"验证"和"确认"混着写，"错误/缺陷/失效"当成同义词，严重程度和优先级直接合成了一个"重要程度"字段，
测试记录里还把"回归测试"和"系统测试"当成了同一个维度的概念。
你要做的是：**逐条纠正**，给出标准术语，并说明为什么原写法会误导后续的缺陷评估与测试归因。

### 任务数据

**数据一：一份待纠偏的缺陷报告（`BUG-2026-0317`）**

```text
标题：【严重】下单金额算错，验证不通过
优先级：严重程度高 → 重要程度：高

描述：
1. 我验证了一下，这个功能确实坏了，说明开发没做确认，需求确认没做好。
2. 用了优惠券之后金额不对，这是程序员写代码时犯的一个错误（error），
   也是系统的失效（failure），我提交的这条失效（failure）请尽快修复。
3. 顺便提一下，页面有几个错别字，重要程度也是高，跟前一条一起修吧。
4. 接口返回 500 时前端白屏，这属于单元级别的功能测试没覆盖到的问题。

复现步骤：
1. 用户账户有满 200 减 20 的券
2. 下单金额 199.00，仍可用券，最终金额 179.00（期望 199.00）
```

**数据二：一张测试记录表（术语混用）**

| 编号 | 记录原文 | 说明 |
|------|----------|------|
| A1 | 对登录模块的函数 `hashPassword()` 单独跑了一遍，属于系统测试 |  |
| A2 | 把用户服务、订单服务、支付服务部署起来联调，属于单元测试 |  |
| A3 | 在接近生产的环境按需求文档全流程跑一遍，属于验收测试 |  |
| A4 | 由业务方在真实业务场景下确认是否满足使用需要，属于功能测试 |  |
| A5 | 检查页面 1 秒内首屏渲染完成，属于功能测试 |  |
| A6 | 不看代码，只按需求写用例覆盖等价类与边界值，属于白盒测试 |  |
| A7 | 依据个人经验与上次相似模块的缺陷集中区域设计用例，属于基于经验的技术 |  |
| A8 | 修改后重跑原有用例，确认没有引入新的失效，属于确认测试（validation） |  |

**ISTQB 标准定义（判定依据，请对照使用）：**

| 术语 | 标准定义要点 |
|------|--------------|
| error（错误） | 人的行为产生了不正确的结果（mistake），是缺陷的**起因** |
| defect（缺陷 / bug / fault） | 工作产品中的不完善之处，是失效的**原因** |
| failure（失效） | 组件或系统在运行中**未能执行其必需功能**，是缺陷被触发后的**表现** |
| verification（验证） | 确认是否**正确构建**了产品（对照设计/规格，"我们是否把产品做对了"） |
| validation（确认） | 确认是否**构建了正确的产品**（对照用户需要，"我们是否做了用户要的产品"） |
| severity（严重程度） | 缺陷对系统/业务**影响的程度**，由缺陷本身决定 |
| priority（优先级） | 修复的**紧急程度/先后顺序**，由业务与进度决定 |
| 测试级别 | 单元测试 / 集成测试 / 系统测试 / 验收测试（按**被测对象与阶段**划分） |
| 测试类型 | 功能测试 / 非功能测试 / 白盒测试 / 黑盒测试 / 基于经验的测试（按**测试目的与手段**划分） |

### 任务要求

请依次完成：

1. **纠偏缺陷报告**：逐条指出数据一中术语误用的位置，写出正确术语，并说明"用错会导致什么后果"。至少覆盖：验证/确认、错误/缺陷/失效、严重程度/优先级三组。
2. **重写一条规范缺陷报告**：把 `BUG-2026-0317` 改写成术语准确、严重程度与优先级**分开填写**的版本，并为优先级给出业务理由。
3. **判定测试级别与类型**：逐条判定数据二 A1–A8 分别属于哪个测试级别 / 哪种测试类型，写出判定依据；原文错误的要给出正确说法。
4. **写一份术语对照速查表（可复用产出）**：4 列（易混术语对 / 常见错误用法 / 标准定义 / 一句话判别法），至少覆盖 5 组易混术语。

### 提交物

| 产出 | 要求 |
|------|------|
| 纠偏清单 | 逐条列出原写法、正确术语、误用后果，≥ 6 条 |
| 重写后的缺陷报告 | 含独立的 severity 与 priority 字段及各自的判定理由 |
| A1–A8 判定表 | 3 列（编号 / 正确的级别或类型 / 判定依据），8 行齐全 |
| 术语对照速查表 | ≥ 5 组易混术语，每组给出可操作的判别法 |

### 完成标准

- [ ] 能准确复述 error → defect → failure 的因果链：错误（人的行为）导致缺陷（工作产品不完善），缺陷被触发时表现为失效
- [ ] 能区分 verification（验证＝是否正确构建）与 validation（确认＝是否构建正确的产品），不看中文译名也能判断
- [ ] 能独立判定 severity 与 priority：严重程度由影响决定、优先级由业务与进度决定，二者可任意组合（高严重低优先级、低严重高优先级都合法）
- [ ] 能分清"测试级别"与"测试类型"是两个**不同维度**：同一批用例可以同时属于某个级别与某种类型
- [ ] 每条纠正都能引用 ISTQB 标准定义，而不是凭语感

    **第 1 题：逐条纠偏（依据 ISTQB Glossary + CTFL v4.0）**

    | # | 原写法 | 问题 | 正确表述 | 用错的后果 |
    |---|--------|------|----------|------------|
    | 1 | "我验证了一下，这个功能确实坏了" | 把"验证"当成"随便试一下"，且"坏了"不是标准术语 | 这是**执行测试并观察到 failure（失效）**；随后定位到代码中的 **defect（缺陷）** | 混淆 verification 与"跑一遍"，会让测试报告说不清到底做了哪种活动 |
    | 2 | "验证…没做确认" | verification 与 validation 概念颠倒混用 | **verification（验证）**＝对照规格确认产品被**正确构建**；**validation（确认）**＝确认构建了**正确的产品**（满足用户需要） | 需求是否正确的讨论会被错记成"验证问题"，归因错人 |
    | 3 | "需求确认没做好" | 把需求评审问题与 validation 混同 | 需求本身有误属于**需求评审/验证**要发现的问题（缺陷存在于需求工作产品中） | 把需求缺陷算到测试头上，流程改进方向就错了 |
    | 4 | "程序员写代码时犯的一个错误（error）" | 这一步用 error 是对的：**人的行为失误** | **error（错误）**：人产生不正确结果的行为 | 若把 error 直接写成"缺陷已上线"，会越过因果链 |
    | 5 | "也是系统的失效（failure）" | 把"提交缺陷"叫成 failure | 他提交的是 **defect（缺陷）记录**；**failure（失效）**是系统运行时未能执行必需功能**这一现象** | 缺陷跟踪系统的字段语义被污染，统计指标（缺陷密度 vs 失效率）全部失真 |
    | 6 | "我提交的这条失效（failure）请尽快修复" | 修复的对象永远是 defect，不是 failure | 修复的是 **defect（缺陷）**；failure 是它的外在表现，本身不可"修" | 沟通返工：开发按"现象"打补丁而不根因修复 |
    | 7 | "重要程度：高"（把两个字段合并） | severity 与 priority 被合并成一个字段 | **severity（严重程度）**与 **priority（优先级）**必须**分开**：金额算错 severity 高；是否紧急修由业务进度决定 priority | 合并后无法区分"影响大但可延后"与"影响小但必须马上修" |
    | 8 | "页面有几个错别字，重要程度也是高" | 错别字 severity 低，却被直接赋了高值 | 错别字 severity 应为**低**；若当天要上线才可能 priority 为**高**——这是"低严重程度 + 高优先级"的典型组合 | 严重程度口径被业务进度污染，历史数据不可比 |
    | 9 | "这属于单元级别的功能测试没覆盖到" | 把**测试级别**与**测试类型**混成一个概念；且接口 500 白屏不是单元测试的职责 | 接口返回 500 导致前端白屏，应为**系统测试**（或集成测试）层面的**功能测试**未覆盖；单元测试的范围是单个单元（如函数/类） | 归因错层，测试策略被错误调整（去补单元测试而不是补接口异常场景） |

    因果链一句话：**error（人的错误行为）→ 产生 defect（工作产品中的缺陷）→ 在特定条件下触发 failure（运行中的失效）**。三者是**因 → 果 → 表现**，不是同义词。

    **第 3 题：测试级别 / 类型判定（A1–A8）**

    | 编号 | 原文 | 判定 | 依据与纠正 |
    |------|------|------|------------|
    | A1 | 单独跑 `hashPassword()`，说"属于系统测试" | 正确是**单元测试**（级别）；测试类型为**白盒测试** | 被测对象是单个函数/单元 → 单元测试级别。"系统测试"错：系统测试的对象是完整系统。 |
    | A2 | 多服务联调，说"属于单元测试" | 正确是**集成测试**（级别） | 被测对象是多个组件/服务之间的接口与交互 → 集成测试。"单元测试"错：单元测试不做跨服务协作。 |
    | A3 | 接近生产环境按需求文档全流程跑，说"属于验收测试" | **系统测试**（级别）；通常为**黑盒功能测试**（类型） | 在接近生产的环境对**完整系统**按需求做端到端测试，是系统测试。验收测试是**由客户/用户主导**、以确认是否满足业务需要为目的的级别，把测试团队的端到端回归叫验收测试会混淆责任主体。 |
    | A4 | 业务方在真实业务场景确认是否满足使用需要 | **验收测试**（级别），具体为**用户验收测试（UAT）**；从类型看是**功能测试** | 判定关键：由业务方/用户主导、目的是确认是否满足业务需要 → **validation（确认）**性质的验收测试。原文写"功能测试"只答了类型维度，漏答了级别维度。 |
    | A5 | 检查 1 秒内首屏渲染完成 | **非功能测试**（类型），具体为**性能效率测试** | 测的是"多快"，属于非功能需求（性能效率）→ 非功能测试。原文"功能测试"错：功能测试关注"做什么"，非功能测试关注"做得怎么样"。 |
    | A6 | 不看代码，按需求设计等价类与边界值，说"属于白盒测试" | 类型是**黑盒测试**；设计技术属于**黑盒测试设计技术**（等价类划分、边界值分析） | 等价类划分与边界值分析都是**基于规格、不依赖内部结构**的技术 → 黑盒。"白盒测试"错：白盒需要了解代码内部结构（语句/分支/路径覆盖）。 |
    | A7 | 依据个人经验与缺陷集中区域设计用例 | 类型是**基于经验的测试**（如错误猜测、探索式测试） | ISTQB 中"基于经验的测试"是与黑盒/白盒并列的测试类型分类，依据测试人员的经验、知识与直觉。 |
    | A8 | 修改后重跑原用例，说"属于确认测试（validation）" | 这是**回归测试**（测试类型/目的维度），**不是** validation | 回归测试的目的是确认修改**没有对未变更部分造成不利影响**。而 **validation（确认）** 是"确认构建了正确的产品"，与"改完重跑"是两件事——这里正是中文译名坑：`validation` 常被译作"确认"，但与"回归确认"完全不同。 |

    关键提醒：**测试级别（单元/集成/系统/验收）与测试类型（功能/非功能/白盒/黑盒/基于经验）是两个正交维度。** 例如 A3 可以同时描述为"系统测试级别下的黑盒功能测试"。

    **第 4 题：术语对照速查表**

    | 易混术语对 | 常见错误用法 | 标准定义 | 一句话判别法 |
    |------------|--------------|----------|--------------|
    | verification（验证） vs validation（确认） | 两者都译作"验证/确认"混着写 | verification＝对照规格确认**正确构建**了产品；validation＝确认构建了**正确的产品** | 问"跟谁比"：跟**规格**比 → 验证；跟**用户需要**比 → 确认 |
    | error（错误） vs defect（缺陷） vs failure（失效） | 三者都写成"bug/问题" | error＝人的失误行为；defect＝工作产品中的不完善；failure＝运行时未能执行必需功能 | 问"在哪一步"：**人**出错 → error；**产品里**存在 → defect；**运行时**暴露 → failure |
    | severity（严重程度） vs priority（优先级） | 合并成一个"重要程度/等级" | severity＝影响程度，由缺陷本身决定；priority＝修复紧急度，由业务与进度决定 | 问"谁说了算"：技术影响说了算 → severity；业务节奏说了算 → priority |
    | 测试级别 vs 测试类型 | 把"单元/集成/系统/验收"与"功能/非功能"当同级选项二选一 | 级别按**被测对象与阶段**划分；类型按**目的与手段**划分，两者正交 | 问"测什么对象/到哪个阶段" → 级别；问"用什么手段/达到什么目的" → 类型 |
    | 回归测试 vs 确认测试 / validation | 把"改完重跑"叫确认测试 | 回归测试＝确认修改未对未变更部分造成不利影响；validation＝确认构建了正确的产品 | 问"因为什么而跑"：**因为改了东西** → 回归；**因为要确认满足用户需要** → validation |
    | 黑盒 vs 白盒 | 用等价类/边界值却报成白盒 | 黑盒＝不依据内部结构，基于规格；白盒＝基于代码内部结构 | 问"看不看代码"：不看 → 黑盒；看 → 白盒 |
