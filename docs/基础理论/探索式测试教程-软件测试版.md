# 探索式测试教程（软件测试人员专用）

!!! abstract “教程简介”
    探索式测试不是”随便点点”，而是在有限时间内围绕一个明确目标，边学习、边设计、边执行、边记录风险。它特别适合新功能、需求不清晰、业务复杂和高风险模块。

## 新手导读

很多新手以为测试只有两种：照测试用例执行，或者写自动化脚本。实际项目里，还有一类非常重要的能力：当需求不完整、场景很多、时间有限时，测试人员要主动探索风险。

第一遍先记住：

```text
脚本化测试：按提前写好的步骤执行。
探索式测试：带着目标去探索，过程中不断产生新测试点。
```

探索式测试不是替代测试用例，而是补充测试用例。它能帮助你发现“用例里没写到，但用户真的会遇到”的问题。

---

## 一、什么是探索式测试

探索式测试强调同时进行四件事：

| 动作 | 说明 |
|------|------|
| 学习 | 快速理解功能、业务规则和系统行为 |
| 设计 | 根据观察实时产生新的测试思路 |
| 执行 | 马上操作系统验证想法 |
| 记录 | 记录缺陷、疑问、风险和后续用例 |

例子：

```text
测试购物车时，你发现商品价格会随促销活动变化。
于是你临时补测：
- 加购前后价格变化
- 勾选和取消勾选后总价变化
- 优惠券叠加后总价变化
- 多端同时修改数量后总价变化
```

这些场景可能不在原始测试用例里，但非常有价值。

---

## 二、探索式测试适合什么场景

| 场景 | 为什么适合 |
|------|------------|
| 新功能第一次提测 | 需求和实现都还不稳定，需要快速摸清行为 |
| 需求描述不完整 | 需要通过系统行为反推规则并提出问题 |
| 业务规则复杂 | 组合场景多，固定用例容易漏 |
| 高风险模块 | 支付、订单、权限、上传、优惠等容易出严重问题 |
| UI 交互复杂 | 用户操作路径多，需要观察体验问题 |
| 上线前补充测试 | 在固定用例之外寻找遗漏风险 |

不适合只靠探索式测试的场景：

- 稳定回归测试。
- 明确的合规检查。
- 必须重复执行的核心流程。
- 需要自动化长期监控的接口。

这类场景更适合测试用例和自动化。

## 三、探索式测试和脚本化测试的区别

| 对比点 | 脚本化测试 | 探索式测试 |
|--------|------------|------------|
| 测试目标 | 验证已知场景 | 发现未知风险 |
| 执行方式 | 按步骤执行 | 根据观察实时调整 |
| 适合阶段 | 回归、验收、稳定功能 | 新功能、复杂功能、高风险功能 |
| 产出 | 用例执行结果、缺陷 | 缺陷、风险、疑问、新用例 |
| 优势 | 可重复、可度量 | 灵活、发现能力强 |
| 风险 | 容易机械执行 | 容易变成随便点，需要目标和记录 |

成熟团队通常两者结合：

```text
脚本化测试保证已知风险不复发。
探索式测试发现新的风险和遗漏场景。
```

## 四、Charter：探索式测试任务卡

探索式测试最好不要空着脑袋开始。先写一个 Charter，也就是探索任务卡。

模板：

```text
探索目标：
测试范围：
关注风险：
测试数据：
时间盒：
记录方式：
结束标准：
```

示例：购物车金额探索

```text
探索目标：发现购物车金额计算和库存联动风险。
测试范围：加购、改数量、勾选、优惠券、删除、结算前金额。
关注风险：金额错误、库存超卖、优惠叠加错误、多端数据不同步。
测试数据：正常商品、库存为 1 商品、促销商品、可用优惠券。
时间盒：60 分钟。
记录方式：记录操作路径、异常现象、截图、接口响应。
结束标准：完成 5 类金额变化场景，输出缺陷或风险清单。
```

Charter 的作用是让探索式测试保持方向，不变成“随手点”。

## 五、Session-Based Testing：基于会话的探索

Session-Based Testing 是一种更可管理的探索式测试方式。每次探索都有固定时间盒和记录。

### 5.1 Session 基本结构

| 项目 | 示例 |
|------|------|
| 时长 | 45 到 90 分钟 |
| 主题 | 登录安全、订单状态、文件上传 |
| 负责人 | 测试人员 A |
| 产出 | 缺陷、疑问、风险、新增用例 |
| 复盘 | 哪些有效，哪些需要继续测 |

### 5.2 Session 记录模板

```text
Session 主题：
时间：
测试人员：
测试环境：

探索目标：
实际覆盖：
发现缺陷：
发现疑问：
发现风险：
新增测试点：
需要跟进：
```

### 5.3 执行节奏

```text
5 分钟：确认目标和数据
30-60 分钟：集中探索
10 分钟：整理记录
10 分钟：复盘和补充用例
```

不要一边聊天一边探索。探索式测试需要注意力，最好一次只围绕一个主题。

## 六、探索式测试常用启发法

启发法不是固定答案，而是帮助你快速想测试点。

### 6.1 CRUD 启发

适合后台管理、数据维护功能。

| 操作 | 测试问题 |
|------|----------|
| Create | 能否新增，必填字段如何校验 |
| Read | 能否查看，是否越权看到别人的数据 |
| Update | 能否修改，状态变化是否受限制 |
| Delete | 能否删除，删除后关联数据如何处理 |

### 6.2 数据启发

| 数据类型 | 测试问题 |
|----------|----------|
| 空值 | 空字符串、空数组、null |
| 边界 | 最小值、最大值、刚好等于限制 |
| 特殊字符 | 空格、中文、符号、换行、Emoji |
| 重复数据 | 重复提交、重复名称、重复订单 |
| 大数据 | 长文本、大文件、大列表 |

### 6.3 状态启发

适合订单、审批、支付、任务流。

```text
待支付 -> 已支付
待支付 -> 已取消
已支付 -> 退款中
已取消 -> 不允许支付
退款中 -> 已退款
```

测试问题：

- 状态能否非法跳转。
- 重复操作是否幂等。
- 页面状态和数据库状态是否一致。
- 异常中断后状态是否可恢复。

### 6.4 权限启发

| 维度 | 测试问题 |
|------|----------|
| 未登录 | 是否能访问页面或接口 |
| 普通用户 | 是否只能操作自己的数据 |
| 角色差异 | 不同角色按钮和接口权限是否一致 |
| 直接请求接口 | 前端隐藏按钮后接口是否仍能调用 |
| token 替换 | 用户 A token 是否能访问用户 B 数据 |

### 6.5 时间启发

适合验证码、优惠券、订单超时、会员有效期。

- 刚开始。
- 即将过期。
- 已过期。
- 跨天。
- 跨月。
- 时区差异。
- 系统时间被调整。

## 七、探索式测试记录怎么写

探索式测试最怕“测过但没证据”。记录要简洁但可追踪。

### 7.1 缺陷记录

```text
标题：库存为 1 的商品可提交 2 件订单
路径：商品详情 -> 加购物车 -> 修改数量 -> 提交订单
测试数据：商品 ID 10001，库存 1
实际结果：订单创建成功，库存变为 -1
期望结果：提示库存不足，不创建订单
证据：截图、接口响应、库存 SQL
风险：可能导致超卖
```

### 7.2 疑问记录

```text
问题：购物车价格应该按加入时价格，还是实时价格？
现象：加入购物车后，后台修改商品价格，购物车总价随之变化。
影响：会影响用户支付金额和投诉风险。
需要确认：产品确认价格规则。
```

### 7.3 新增用例记录

```text
新增用例：商品加入购物车后价格变化
前置条件：商品已加入购物车
步骤：后台修改商品价格，用户刷新购物车
预期：按产品确认规则展示价格，并给出明确提示
```

## 八、实战案例：登录功能探索

### Charter

```text
探索目标：发现登录功能在安全、会话和异常输入上的风险。
范围：手机号密码登录、失败次数、锁定、退出登录、token。
时间盒：45 分钟。
测试数据：正常账号、禁用账号、未注册手机号。
```

### 探索路径

1. 正常账号登录成功。
2. 密码错误 1 次、4 次、5 次。
3. 锁定后输入正确密码。
4. 未注册手机号登录。
5. 禁用账号登录。
6. 登录后复制 token，请求用户信息接口。
7. 退出登录后继续使用旧 token。
8. 修改 token 后请求接口。

### 可能发现的问题

| 问题 | 风险 |
|------|------|
| 输错 5 次未锁定 | 暴力破解风险 |
| 账号不存在提示过于明确 | 枚举账号风险 |
| 退出登录后旧 token 仍可用 | 会话失效风险 |
| token 过期后接口返回用户数据 | 鉴权漏洞 |

## 九、实战案例：文件上传探索

### Charter

```text
探索目标：发现头像上传的类型、大小、权限和安全风险。
范围：JPG、PNG、超大文件、非法类型、后缀伪装、未登录上传。
时间盒：60 分钟。
```

### 探索路径

1. 上传正常 JPG 和 PNG。
2. 上传 0 KB 文件。
3. 上传刚好 5 MB 文件。
4. 上传超过 5 MB 文件。
5. 上传中文文件名。
6. 上传超长文件名。
7. 将脚本文件改名为 `.jpg` 上传。
8. 未登录直接调用上传接口。
9. 用户 A 尝试替换用户 B 头像。

### 重点观察

- 前端限制是否能被接口绕过。
- 后端是否校验真实文件类型。
- 上传失败是否泄露服务器路径。
- 文件 URL 是否可被猜测。
- 旧头像是否被清理或保留。

## 十、探索式测试输出物

一次合格的探索式测试至少应该输出：

| 输出物 | 内容 |
|--------|------|
| Session 记录 | 测试目标、范围、时间、覆盖情况 |
| 缺陷清单 | 可复现的问题和证据 |
| 疑问清单 | 需要产品或开发确认的问题 |
| 风险清单 | 可能影响上线的问题 |
| 新增用例 | 从探索中沉淀出的回归用例 |

示例总结：

```text
本次围绕购物车金额进行了 60 分钟探索，覆盖加购、改数量、勾选、优惠券和结算前金额。发现 1 个缺陷：库存为 1 时可提交 2 件订单；发现 2 个需求疑问：价格是否按实时价、优惠券是否可与满减叠加。建议修复库存问题后，将价格变化和优惠叠加补充为回归用例。
```

---

## 十一、新手常见错误

| 错误 | 问题 | 改法 |
|------|------|------|
| 随便点页面 | 没有目标，难以复盘 | 先写 Charter |
| 只记录 Bug | 漏掉需求疑问和风险 | 同时记录缺陷、疑问、风险 |
| 不保留证据 | 开发难以复现 | 截图、接口、日志、SQL 都保留 |
| 测太大范围 | 时间被摊薄 | 每个 Session 只聚焦一个主题 |
| 不沉淀用例 | 下次还会漏 | 把有效探索点转成回归用例 |

## 十二、练习任务

请选择一个功能完成 45 分钟探索：

```text
登录
购物车
下单支付
权限控制
文件上传
```

要求输出：

1. 一张 Charter。
2. 至少 10 条探索路径。
3. 至少 2 个疑问或风险。
4. 至少 1 个缺陷示例。
5. 至少 3 条新增回归用例。

完成标准：

- 不是随便点，而是围绕明确目标探索。
- 记录中能看出测试数据和操作路径。
- 每个风险都能说明影响。
- 有价值的探索点被沉淀成后续用例。

探索式测试的价值在于训练测试人员的判断力。工具能帮你执行，但发现未知风险，仍然需要人的观察、怀疑和推理。

## 动手任务：为「优惠券中心 v2.3」写一份可评审的 Charter + Session 记录

> 这是本教程的收尾练习。请**独立完成**，不要先看参考答案。目标不是"点出一个 Bug"，
> 而是**用一份能被他人复现、复核、复用的探索记录，证明你的探索是有目标的**——
> 这是区分"探索式测试"和"随便点点"的唯一标准。

### 任务背景

你是「云书商城」的测试工程师。优惠券中心 v2.3 下周上线，本次新增了
**"叠加用券"** 和 **"券后价展示"** 两个改动。产品只给了一句话需求，开发明天提测，
留给你的探索时间只有 **45 分钟**。团队现有 12 条回归用例（见下方"任务数据"），
用例集是上一个版本的，本次**没有更新**。你需要用一次时间盒内探索，回答一个问题：
**这 12 条用例漏掉了哪些风险？**

### 任务数据

**第一部分：需求原文（产品邮件，未澄清）**

```text
优惠券中心 v2.3 上线说明

1. 支持多张券叠加使用，让用户更省钱。
2. 商品详情页和购物车展示"券后价"。
3. 以上功能本周五提测，下周三上线。
```

**第二部分：现有回归用例集（v2.2 遗留，未更新）**

| 编号 | 用例标题 | 前置条件 | 步骤 | 预期 |
|------|----------|----------|------|------|
| TC-01 | 满 100 减 10 券正常使用 | 购物车 120 元 | 选择券→提交订单 | 订单金额 110 元 |
| TC-02 | 未满门槛不可用券 | 购物车 80 元 | 查看券列表 | 满减券置灰 |
| TC-03 | 券过期后不可用 | 券已过期 1 天 | 选择券 | 提示"券已过期" |
| TC-04 | 单张券可用后取消订单 | — | 用券→取消订单 | 券退回账户 |
| TC-05 | 无券用户正常结算 | 无可用券 | 提交订单 | 原价下单成功 |
| TC-06 | 券列表按到期时间排序 | 3 张券 | 查看列表 | 最先过期排最前 |
| TC-07 | 券详情页展示门槛说明 | — | 点开券详情 | 展示"满100可用" |
| TC-08 | 同一张券不可重复使用 | — | 连续下两单用同一张券 | 第二单不可选该券 |
| TC-09 | 券与积分不可同时使用 | — | 两者都勾选 | 提示互斥 |
| TC-10 | 券后价在商品详情页展示 | 详情页 200 元 | 查看价格区 | 展示"券后 190" |
| TC-11 | 券后价在购物车展示 | 购物车 200 元 | 查看合计 | 展示"券后 190" |
| TC-12 | 券金额不参与运费计算 | 运费 10 元 | 用券结算 | 运费按原价算 |

**第三部分：可用测试数据（沙箱环境，可反复重置）**

```text
券 A：满 100 减 10，全场通用，有效期 7 天        （普通满减券）
券 B：满 100 减 15，全场通用，有效期 7 天        （满减券，与 A 同门槛）
券 C：8 折券，最高抵扣 30 元，限"图书"品类，5 天后到期
券 D：已过期券（昨天到期，页面仍可见）
券 E：满 200 减 50，仅"数码"品类，仅限 App 端
券 F：无门槛 5 元券
券 G：门槛刚好 100 元（订单正好 100 元时判断边界）
商品 P1：图书《测试之美》99.00 元，库存 3
商品 P2：图书《敏捷实践》120.00 元，库存 1
商品 P3：数码耳机 299.00 元，库存 10，仅 App 端可见
账号 U1：新用户，已领 A/B/C/F/G
账号 U2：老用户，已领 A/D/E，且 historically 已用过一次 A
账号 U3：同一账号在网页端与 App 端同时登录（并发场景）
```

### 任务要求

请依次完成：

1. **写一张 Charter**（不超过 10 行）。必须包含：探索目标、测试范围、关注风险、
   测试数据、时间盒（写死 45 分钟）、记录方式、结束标准。目标要写成
   **"发现哪一类风险"**，不能写成"测一下优惠券"。

2. **设计并执行 12 条探索路径**，覆盖上方至少 4 种启发法（CRUD / 数据 / 状态 /
   权限 / 时间，见本教程第六章）。每条路径必须写出：**操作路径 → 预期 → 实际 →
   判定（符合 / 存疑 / 缺陷）**。路径不能用 TC-01 到 TC-12 的原文照抄。

3. **做一次盲区对照**：逐条判断 TC-01 到 TC-12 分别"已覆盖 / 部分覆盖 / 未覆盖"
   你要探索的风险点，并用一张表列出**至少 6 个用例集盲区**，每个盲区要指明
   它对应哪种启发法。

4. **填写 Session 记录**（用本教程第五章 5.2 的模板），并输出三张清单：
   - 缺陷清单：至少 3 条，每条含标题、路径、测试数据、实际结果、期望结果、影响。
   - 疑问清单：至少 4 条，每条必须指名 **要向谁确认**（PO / 开发 / 运维）。
   - 风险清单：至少 3 条，每条给出 **影响面 + 建议动作**。

5. **把探索结果沉淀成 3 条可复用回归用例**，格式必须能被直接录入用例库
   （前置条件 / 步骤 / 预期，含具体数据）。

6. **给出一句结论**（60 字以内）：这份用例集能不能支撑本次上线？若不能，缺什么？

### 完成标准

- [ ] Charter 的目标写成"发现 X 类风险"而非功能名，且 7 个要素一个不缺。
- [ ] 12 条探索路径中，至少 4 种启发法在"判定"列里能看出痕迹（例如数据启发
      提到"门槛刚好等于 100"、时间启发提到"5 天后到期、跨天"）。
- [ ] 盲区对照表里，每条盲区都能指向一条具体数据（如券 B 与券 A 同门槛叠加）。
      **写不出具体数据的盲区不算盲区，只是猜测。**
- [ ] 缺陷清单里每条都有"实际结果"和"期望结果"两句，且期望结果能追溯到需求或
      常识契约；只有"感觉不对"的条目一律不算。
- [ ] 疑问清单每条都写了确认对象，没有一条是"自己再研究研究"。
- [ ] 每条新增回归用例都能被**另一个人**照着独立执行一遍。
- [ ] 结论明确回答了"能不能上线"，且与前面的缺陷/风险清单不矛盾。
- [ ] Session 记录的总时长与 Charter 的时间盒一致（45 分钟），且写出了
      实际覆盖 vs 计划覆盖的差距。

??? tip "参考答案与思路（先自己做完再看）"

    **第 1 题：Charter 应该长什么样**

    合格示例（对照它的每一处"可评判"设计）：

    ```text
    探索目标：发现"多券叠加"与"券后价展示"在金额计算、品类/端限制、
              并发与状态回退上的风险。
    测试范围：券的选择与互斥、叠加顺序、券后价展示位置、下单/取消/超时回退、跨端并发。
    关注风险：金额算错（多扣/少扣）、不可用券被绕过、券后价与实际支付不一致、
              券重复使用或丢失、品类与端限制被前端绕过。
    测试数据：券 A~G、商品 P1~P3、账号 U1~U3（含同一账号双端在线）。
    时间盒：45 分钟（5 分钟准备 / 30 分钟探索 / 10 分钟整理）。
    记录方式：操作路径 + 截图 + 下单接口响应 + 券状态与订单金额的库表记录。
    结束标准：完成 4 类启发法覆盖，输出缺陷/疑问/风险清单各 ≥3/4/3 条。
    ```

    为什么这算合格：目标是"发现风险"不是"测功能"；范围里出现了"回退""并发"
    这类最容易漏的维度；结束标准是**可计数的**，事后能判定有没有达成。
    **反面例子**：「探索目标：测试优惠券功能。」——无法判定完成与否，等于没写。

    **第 2 题：12 条探索路径的骨干（按启发法分组）**

    不必逐字一致，但**这四类每类都要有**：

    | 启发法 | 探索路径示例 | 想抓的风险 |
    |--------|--------------|-----------|
    | 数据 | 订单金额**恰好 100 元**时用券 A / 用券 G | 门槛判断是 `>` 还是 `>=` |
    | 数据 | 券 C（8 折，最高减 30）作用在 P2（120 元）与 P3（299 元） | 封顶规则是否生效（24 vs 30） |
    | 状态 | 用券下单 → 支付超时关单 → 券是否原样退回且未过期判定正确 | 券丢失或提前作废 |
    | 状态 | 用券下单 → 取消 → 再次下单用同一张券（TC-08 的**反向**） | 券能否被重复消费 |
    | 权限/端 | 网页端直接构造请求使用券 E（仅 App 端券） | 端限制只在 UI 做，接口可绕过 |
    | 权限/品类 | 购物车混合"图书 + 数码"时使用券 C（限图书） | 品类限制按整单还是按行判断 |
    | 并发 | U3 在网页端与 App 端同时用券 A 下单 | 券被同时消费两次（超发） |
    | 时间 | 在券有效期的**最后一分钟**下单，支付在过期后完成 | 以哪个时间点判定券有效性 |
    | 时间 | 券 C 在 5 天后到期，跨天/跨时区展示与判定是否一致 | 展示与校验用了不同时区 |
    | CRUD | 券 A 与券 B **同门槛**同时勾选，观察叠加顺序与总减免 | 叠加规则未定义（需求只说"可以叠加"） |
    | 数据/精度 | 券 C 打 8 折在 99.00 元上 | 除法后的分位舍入（79.20 是否正确） |
    | 组合 | 券 A + 券 C + 积分同时勾选（TC-09 只测了券与积分互斥） | 三者的新互斥规则未定义 |

    关键点：**TC-09 只覆盖了"券 vs 积分"，没有覆盖"券 A vs 券 B vs 券 C"的
    券间互斥**——这正是 v2.3 新功能带来的新组合。

    **第 3 题：用例集盲区至少应写出这几条**

    1. **多券叠加规则完全没测**（TC-01~TC-12 只有单券）。对应启发法：CRUD / 数据。
       依据：需求第 1 条新增了叠加，用例集停留在 v2.2。
    2. **叠加顺序与计算优先级未定义**：先满减再打折还是先打折再满减，
       结果不同（120 元：先减 10 再 8 折 = 88；先 8 折再减 10 = 86）。
    3. **品类限制的作用粒度未测**（券 C 限图书，混合购物车怎么算）。
    4. **端限制（券 E 仅 App）只是 UI 限制，没有接口层验证**。
    5. **券后价的一致性问题**：TC-10/TC-11 只验证"显示了 190"，
       没验证**券后价与实际支付金额一致**，也没验证失效券/不可用券时券后价如何展示。
    6. **并发/多端场景为零**：U3 双端同时用券，券超发是支付类功能的典型事故。
    7. **券的生命周期边界**：过期瞬间、退款回退、关单回退的券状态，
       TC-03 只测了"已过期不能用"，没测"快过期/刚过期/回退后"。
    8. **金额精度与封顶**：TC-01 用整数 100→110，掩盖了折扣的分位舍入与最高抵扣。

    判分要点：**每条盲区都必须能落到一条具体数据上**。写"边界值考虑不足"不得分。

    **第 4 题：三张清单的写法要点**

    缺陷示例（照这个颗粒度写）：

    ```text
    标题：券 A 与券 B 同门槛叠加时，系统只取减免金额较小的一张
    路径：购物车 P1+P2（219 元）→ 同时勾选券 A(减10) 与券 B(减15) → 提交订单
    测试数据：账号 U1，券 A、券 B，订单金额 219 元
    实际结果：订单金额 204 元（仅减免 15），券 A 未被使用也未给出提示
    期望结果：按 PO 确认的叠加规则计算；若不允许并存，应在前端明确互斥提示
    证据：下单接口响应 order_amount=20400；券 A 状态仍为"未使用"
    影响：用户看到"可以叠加"却拿不到优惠，客诉 + 资损争议
    ```

    疑问清单必须指名对象（这是本题最容易失分的地方）：

    ```text
    问题：券 A 与券 B 同为"满 100 减"，是否允许叠加？叠加顺序如何？
    现象：同时勾选时只生效了减免金额较小的一张，且无任何提示。
    影响：直接决定金额计算逻辑和用例预期，是本次最高优先级疑问。
    需要确认：PO 张 XX（需求第 1 条未定义叠加规则）。
    ```

    风险清单要点是"影响面 + 建议动作"，不要只写"有风险"：

    ```text
    风险：多张券并发消费导致券超发（U3 双端同时用券 A）。
    影响面：资损，且属于支付类问题，上线后难以追回。
    建议动作：上线前必须补服务端幂等 + 券状态乐观锁校验；
              未修复则本次"叠加用券"不建议上线。
    ```

    **第 5 题：新增回归用例示例**

    ```text
    用例：券后价必须与实际支付金额一致
    前置条件：账号 U1，商品 P2（120 元），券 C（8 折，最高减 30）
    步骤：
      1. 商品详情页记录展示的券后价
      2. 加入购物车，记录购物车合计的券后价
      3. 提交订单，记录接口返回的 order_amount
    预期：三处金额完全相同，且等于 96.00 元（120 × 0.8，未触发 30 元封顶）
    ```

    **第 6 题：结论示例**

    > 现有 12 条用例只覆盖单券场景，**不能支撑叠加功能上线**。
    > 叠加规则、并发超发、品类/端限制三道防线均无覆盖，需先澄清规则并补测。

    注意结论必须与前三张清单自洽：如果你只找到 3 个低级 UI 问题，却说"可以上线"，
    要解释为什么那些问题不阻塞——这本身就是判断力的体现。
