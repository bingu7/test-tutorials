# 敏捷测试教程（软件测试人员专用）

!!! abstract "教程简介"
    本教程面向软件测试工程师，讲解敏捷开发模式下测试人员的工作方式、协作流程和实践方法。

## 新手导读

敏捷测试重点不是背 Scrum 名词，而是理解测试人员如何在快节奏迭代中提前参与需求、持续反馈风险。

第一遍建议抓住这些问题：

1. 什么是迭代、用户故事、验收标准。
2. 测试人员什么时候介入需求评审。
3. 如何把验收标准转成测试点。
4. 为什么敏捷团队需要持续测试和自动化回归。

学完后，你应该能看懂一个用户故事，并写出对应的验收测试点。

## 一、敏捷基础

### 1.1 敏捷是什么

敏捷是一种 **迭代式、增量式** 的软件开发方法，核心理念：

- **个体与互动** 高于流程与工具
- **可工作的软件** 高于详尽的文档
- **客户协作** 高于合同谈判
- **响应变化** 高于遵循计划

### 1.2 敏捷 vs 瀑布

| 维度 | 瀑布 | 敏捷 |
|------|------|------|
| 周期 | 长（数月） | 短（1-4 周迭代） |
| 需求 | 前期固定 | 每个迭代可调整 |
| 测试阶段 | 编码后才开始 | 全程参与 |
| 反馈 | 上线后才得到 | 每个迭代末评审 |
| 风险 | 后期暴露 | 持续暴露 |
| 文档 | 重文档 | 够用即可 |

### 1.3 敏捷宣言十二原则（节选）

- 尽早持续交付可工作的软件
- 欢迎需求变更
- 业务人员与开发人员每天协作
- 面对面沟通最有效
- 可工作的软件是进度的首要度量
- 保持可持续的开发节奏
- 技术卓越与良好设计

## 二、Scrum 框架

Scrum 是最流行的敏捷框架。

### 2.1 核心角色

| 角色 | 职责 |
|------|------|
| **Product Owner（PO）** | 管理需求优先级，代表业务方 |
| **Scrum Master（SM）** | 保障流程执行，移除障碍 |
| **开发团队** | 开发 + 测试 + 设计（跨职能自组织） |

### 2.2 Scrum 事件

| 事件 | 频率 | 时长 | 目的 |
|------|------|------|------|
| **Sprint** | 持续 | 1-4 周 | 一个迭代周期 |
| **Sprint Planning** | 每个 Sprint 开始 | 最多 8 小时（1 月 Sprint），按比例缩放 | 确定本迭代做什么 |
| **Daily Standup** | 每天 | 15 分钟 | 同步进展、暴露问题 |
| **Sprint Review** | 每个 Sprint 结束 | 1-2 小时 | 展示成果、收集反馈 |
| **Sprint Retrospective** | 每个 Sprint 结束 | 1 小时 | 回顾改进 |

### 2.3 核心工件

| 工件 | 说明 |
|------|------|
| **Product Backlog** | 所有需求的优先级列表（PO 维护） |
| **Sprint Backlog** | 本迭代要完成的需求 |
| **Increment** | 本迭代交付的可工作软件 |

### 2.4 Sprint 流程

```
Sprint Planning → 每日开发 → Sprint Review → Retrospective
    ↓                  ↓              ↓              ↓
 确定范围           Daily Standup   展示成果       回顾改进
 拆分任务           编码+测试       收集反馈       优化流程
```

## 三、测试人员在敏捷中的角色

### 3.1 角色转变

| 传统测试 | 敏捷测试 |
|---------|---------|
| 独立测试团队 | 嵌入开发团队 |
| 需求文档驱动 | 用户故事驱动 |
| 编码后才测试 | 全程参与 |
| 手工执行为主 | 自动化为主 |
| 质量守门员 | 质量教练 |
| 发现缺陷 | 预防缺陷 |

### 3.2 测试人员的职责

**Sprint Planning 阶段：**

- 参与需求评审
- 拆分测试任务
- 评估测试工作量
- 识别风险点

**开发阶段：**

- 编写自动化测试用例
- 与开发并行测试
- 探索性测试
- 接口测试先于 UI 测试

**Sprint Review 阶段：**

- 展示测试结果
- 反馈质量问题
- 参与验收

**Retrospective 阶段：**

- 回顾测试过程
- 提出改进建议

### 3.3 测试左移与右移

```
左移（Shift Left）：尽早介入
需求 → 设计 → 编码 → 测试 → 发布
 ↑ 测试从这里开始参与

右移（Shift Right）：上线后持续关注
发布 → 生产监控 → 用户反馈 → 持续改进
                            ↑ 测试也参与
```

**左移实践：**

- 参加需求评审，提前发现歧义
- 提前写测试用例，帮助开发理解预期
- 接口测试在 UI 开发前完成

**右移实践：**

- 监控线上错误日志
- 分析用户反馈
- 参与生产环境验证

## 四、用户故事与验收标准

### 4.1 什么是用户故事

用户故事是需求的最小单元，格式：

```
作为 <角色>
我想要 <功能>
以便 <价值>

示例：
作为 注册用户
我想要 通过手机号登录
以便 不用记密码
```

### 4.2 验收标准（Acceptance Criteria）

每个用户故事必须有验收标准，定义"完成"的条件。

**格式示例：**

```
用户故事：作为用户，我想要重置密码，以便找回账号

验收标准：
1. 输入注册邮箱，系统发送重置链接
2. 链接 24 小时内有效
3. 点击链接后可设置新密码
4. 新密码需满足：8-20 位，含大小写和数字
5. 密码重置后，旧密码立即失效
6. 重置成功后跳转到登录页，提示"密码已重置"
```

### 4.3 Given-When-Then 格式

验收标准也可用 BDD 风格：

```
Given 用户已注册且邮箱为 test@example.com
When 用户点击"忘记密码"并输入邮箱
Then 系统发送重置链接到该邮箱
And 链接在 24 小时内有效
```

### 4.4 测试人员参与用户故事

**Sprint Planning 时：**

- 检查验收标准是否完整
- 补充异常场景
- 评估可测试性
- 拆分测试任务

**示例任务拆分：**

```
用户故事：登录功能
├── 测试任务 1：编写接口自动化用例（2h）
├── 测试任务 2：编写 UI 自动化用例（1h）
├── 测试任务 3：探索性测试异常场景（1h）
└── 测试任务 4：跨浏览器验证（0.5h）
```

## 五、敏捷测试策略

### 5.1 测试金字塔（敏捷版）

```
        ╱╲
       ╱UI ╲          少量（5%）
      ╱──────╲        端到端验证
     ╱  接口   ╲      中量（20-25%）
    ╱──────────╲      业务逻辑验证
   ╱   单元测试  ╲    大量（70%+）
  ╱──────────────╲    快速反馈
```

**敏捷强调：** 自动化测试占比高，手工测试聚焦探索性测试。

### 5.2 四象限测试

```
               支持团队                    评价产品
         ┌─────────────────┬─────────────────┐
  手工为主 │ Q2: 功能测试    │ Q3: 探索性测试  │  手工为主
         │ 接口测试        │ 用户体验测试    │
         │ （测试主导）     │ Alpha/Beta 测试 │
         ├─────────────────┼─────────────────┤
  自动化  │ Q1: 单元测试    │ Q4: 性能测试    │  自动化
         │ 组件测试        │ 安全测试        │
         │ （开发负责）     │ 可靠性测试      │
         └─────────────────┴─────────────────┘
```

- **Q1**：开发负责，测试协助
- **Q2**：测试核心工作（接口自动化、功能自动化）
- **Q3**：手工探索性测试、用户体验
- **Q4**：专项测试（性能、安全）

### 5.3 每个迭代的测试活动

| Sprint 阶段 | 测试活动 |
|------------|---------|
| Planning | 需求评审、用例设计、任务拆分 |
| 开发前期 | 接口自动化（与开发并行） |
| 开发中期 | UI 自动化、集成测试 |
| 开发后期 | 探索性测试、回归测试 |
| Review | 验收测试、展示结果 |
| Retrospective | 回顾测试过程、改进 |

### 5.4 冒烟测试与回归测试

**冒烟测试（Smoke Test）：**

- 每个构建自动执行
- 覆盖核心流程（登录、下单、支付）
- 失败则阻塞后续测试

**回归测试（Regression Test）：**

- 每个 Sprint 结束执行
- 覆盖所有自动化用例
- 确保新功能不影响老功能

## 六、持续测试

### 6.1 持续集成中的测试

```
代码提交 → 自动构建 → 单元测试 → 接口测试 → 部署测试环境 → UI 测试 → 报告
```

每个阶段都有测试，失败则阻塞后续。

### 6.2 测试门禁（Quality Gate）

```yaml
# 示例：Jenkins 流水线门禁
quality_gates:
  - name: 单元测试通过率
    threshold: 95%
    current: 98%    # ✅
  
  - name: 接口测试通过率
    threshold: 90%
    current: 92%    # ✅
  
  - name: 代码覆盖率
    threshold: 70%
    current: 65%    # ❌ 阻塞发布
  
  - name: 严重缺陷数
    threshold: 0
    current: 1      # ❌ 阻塞发布
```

### 6.3 测试报告与反馈

**每日：**

- 自动化测试结果通知（钉钉/企业微信）
- 失败用例当天修复

**每 Sprint：**

- 测试覆盖率报告
- 缺陷统计
- 遗留风险

## 七、敏捷测试实践

### 7.1 实践一：结对测试

测试人员与开发人员结对工作：

- 开发写代码时，测试写用例
- 开发提交前，测试先验证
- 减少后期返工

### 7.2 实践二：三 Amigos 会议

需求讨论时，三方一起：

```
产品（PO）：定义需求
开发：评估实现方案
测试：补充异常场景、验收标准
```

产出：明确的用户故事 + 验收标准。

### 7.3 实践三：探索性测试

每个 Sprint 预留时间做探索性测试：

```
时间盒：1-2 小时
目标：发现自动化覆盖不到的问题
方法：
  - 基于经验猜测可能出错的地方
  - 尝试非常规操作
  - 组合不同功能
  - 边界值、异常输入
产出：发现的 Bug + 新增的自动化用例
```

### 7.4 实践四：Definition of Done（DoD）

团队共同定义"完成"的标准：

```
一个用户故事"完成"的条件：
- [ ] 代码完成并通过 Code Review
- [ ] 单元测试通过
- [ ] 接口自动化用例通过
- [ ] UI 自动化用例通过（如有 UI 变更）
- [ ] 无 P0/P1 缺陷
- [ ] 验收标准全部满足
- [ ] 文档更新（如有必要）
```

### 7.5 实践五：缺陷分析与预防

每个 Sprint 分析缺陷：

```
缺陷分布：
├── 需求理解偏差（30%）→ 加强需求评审
├── 边界场景遗漏（25%）→ 补充边界用例
├── 集成问题（20%）→ 加强接口测试
├── 回归缺陷（15%）→ 扩大自动化覆盖
└── 其他（10%）→ 具体分析
```

## 八、常见问题与应对

### 8.1 迭代太快，测试来不及

**应对：**

- 接口测试先于 UI 测试
- 自动化覆盖核心流程
- 探索性测试聚焦高风险区域
- 与 PO 协商调整范围

### 8.2 需求频繁变更

**应对：**

- 用例设计模块化，易于调整
- 自动化用例参数化
- 接受变更，拥抱敏捷精神
- 变更影响分析及时同步

### 8.3 开发不写单元测试

**应对：**

- 在 DoD 中明确要求
- Code Review 检查覆盖率
- 测试人员协助开发写单元测试
- 用 SonarQube 等工具监控

### 8.4 自动化维护成本高

**应对：**

- Page Object 模式
- 数据驱动减少重复
- 定期清理无效用例
- 开发配合加 data-testid

### 8.5 测试环境不稳定

**应对：**

- Docker 容器化环境
- Mock 外部依赖
- 环境健康检查脚本
- 与运维协作保障环境

## 动手任务：评审 3 个含糊用户故事，产出 Given-When-Then 验收标准与迭代测试策略

> 这是本教程的收尾练习。请**独立完成**，不要先看参考答案。目标不是"把故事改通顺"，
> 而是**把一句不可测的话，变成一组别人能照着验收、能照着写自动化脚本的条件**。

### 任务背景

你是「快团」社区团购团队的测试工程师。Sprint 22 的 **Sprint Planning** 明天上午开，
PO 在 Product Backlog 里丢了 3 个用户故事，都只有一句话，没有验收标准。
团队要求你在 Planning 前完成一次**三 Amigos**（PO + 开发 + 测试）前的准备：
把不可测之处挑出来、把验收标准写出来、把本迭代的测试策略和 DoD 定出来。
**Sprint 周期为 2 周，测试可用人力 1 人（你），总投入 5 人日。**

### 任务数据

**第一部分：待评审的 3 个用户故事（PO 原文，一字未改）**

```text
US-101（故事点：3）
作为用户，我想要分享一下团购链接，以便朋友能一起买。

US-102（故事点：5）
作为用户，我想要在提货点快速核销我的订单，以便我不排长队。

US-103（故事点：8）
作为用户，我想要团长能改单，以便临时加购或者退掉不要的东西。
```

**第二部分：本迭代上下文（来自团队工作区）**

| 项目 | 内容 |
|------|------|
| Sprint 周期 | 2 周（Sprint 22：3 月 4 日 ~ 3 月 15 日） |
| 团队速率 | 上一迭代完成 26 故事点；本迭代承诺 24 故事点 |
| 已有自动化 | 接口自动化 180 条（Pytest + Requests，CI 每次提交执行）；UI 自动化 20 条（Playwright，仅冒烟核心流程） |
| 现存问题 | 上一迭代回归缺陷 2 个，均为"改单"相关；环境为共享测试环境，团购链路依赖第三方支付沙箱，偶发超时 |
| 相关角色 | PO：张 XX；开发：李 XX、王 XX；团长（业务方）：分布在 400 个自提点，多为兼职、年龄偏大 |
| 提货点设备 | 安卓扫码枪（型号 A，系统 Android 9）+ 团长个人手机（iOS / 安卓混杂），部分点位网络为 4G |
| 已有合规约束 | 核销记录需留存 3 年可追溯；退款金额必须与订单一一对应 |

**第三部分：可参考的业务规则片段（需求文档摘录，存在冲突）**

```text
《分享规则 v1.0》：分享链接有效期 24 小时。
《分享规则 v1.0》：分享链接被打开后，用户可以正常下单。
《团购协议》：成团失败自动全额退款，退款 T+1 到账。
《核销说明》第 2 条：一码一核销，核销后不可撤销。
《核销说明》第 5 条：核销后 30 分钟内允许团长申请撤销，需人工审核。
《改单规则》：成团前允许改单。
《改单规则》：成团后如需改单，联系客服处理。
```

### 任务要求

请依次完成：

1. **逐个故事做可测性评审**：对 US-101、US-102、US-103 各写一份评审结论，必须包含：
   - **INVEST 逐项判定**（Independent / Negotiable / Valuable / Estimable / Small / Testable），
     每项给"通过 / 存疑 / 不通过"和一句理由。
   - **至少 2 处"不可测"的具体措辞**（引用原句），并说明"为什么测不了"
     （是缺边界？缺对象？还是缺判据？）。
   - **至少 3 个必须问 PO 的澄清问题**，每个问题要写成"二选一或给出数值"的形式，
     不能问"你能详细说说吗"。

2. **为每个故事写 Given-When-Then 验收标准**：
   - US-101：≥5 条；US-102：≥6 条；US-103：≥8 条。
   - **每条至少覆盖一个异常/边界场景**，且必须能从"任务数据"里找到依据
     （例如网络 4G、iOS/安卓混杂、Android 9 扫码枪、兼职团长）。
   - 每条 Given-When-Then 后面用一行注明 **"验收方式"**：自动化 / 手工 / 探索，
     并说明理由（≤20 字）。

3. **指出需求文档中的矛盾并给出取舍建议**（至少 1 处，Clue 在"任务数据"第三部分）。

4. **写本迭代的测试策略表**：
   - 逐项列出"测什么 / 用什么方式（接口自动化 / UI 自动化 / 手工 / 探索）/ 谁负责 /
     预计工时 / 依赖"。
   - 明确 **测试金字塔的配比**（本迭代新增用例中单元 : 接口 : UI 的目标比例及理由）。
   - 明确**本迭代不测什么**（做减法的部分），并说明风险由谁承担。

5. **写本迭代的 DoD**（Definition of Done）：≥8 条，其中至少 3 条是**可机器校验**的
   （例如覆盖率阈值、CI 门禁、缺陷等级），不能全是"完成""通过"这类软描述。

6. **准备三 Amigos 会议议程**：30 分钟，写出议程分配（分钟）与每个议题的
   **预期产出物**，并说明每个故事由谁主讲。

### 完成标准

- [ ] 每个故事的 INVEST 判定都给了理由，**"Testable = 不通过"必须能指回一条
      具体的模糊措辞**，不能只说"描述不清"。
- [ ] 澄清问题都是**可判定**的：PO 回答"是 / 否 / 数值"就能结束讨论。
      出现"请补充细节""你觉得呢"这类开放式问题即不达标。
- [ ] 每条 Given-When-Then 的 Given 里都能找到**具体对象与具体状态**
      （如"团长账号权限为'仅核销'"），不能只有"When 用户操作"。
- [ ] US-102 的验收标准里出现了**"一码一核销"与"30 分钟内可撤销"这对矛盾**
      的处理方式（至少一条 Then 明确撤销后的核销状态）。
- [ ] 每条验收标准都有"验收方式"标注，且标注理由与自动化现状一致
      （只有 20 条 UI 自动化的团队，不应该把大半 UI 场景标成"自动化"）。
- [ ] 测试策略表的工时总和 ≤5 人日，且**与实际速率不矛盾**。
- [ ] DoD 中至少 3 条是机器可校验的（写明阈值或门禁名）。
- [ ] 不做清单写明了承担人——**没有承担人的"不做"等于埋雷**。
- [ ] 三 Amigos 议程的总时长正好 30 分钟，且每个议题都有产出物。

    **第 1 题：可测性评审要点（以 US-103 为例）**

    | INVEST 项 | 判定 | 理由 |
    |-----------|------|------|
    | Independent | 存疑 | "改单"依赖订单状态机（成团前/后）和退款链路，与 US-102 的核销耦合 |
    | Negotiable | 通过 | 交付形态可谈判（先支持"减数量"还是先支持"加购"） |
    | Valuable | 通过 | 团长侧高频诉求，直接减少客服工单 |
    | Estimable | 存疑 | "改单"改动面不明：改金额？改商品？改提货点？ |
    | Small | 不通过 | 5 人日团队里估 8 点，包含改单 + 退款 + 通知三件事，应拆 |
    | Testable | 不通过 | 缺"谁能改""什么状态能改""改了钱怎么退"三类判据 |

    引用原句的不可测点（每处都要说清"为什么测不了"）：

    ```text
    原句 1：「团长能改单」
      为什么测不了：没有指明"团长"是本人团长还是同点位任意团长
                    （权限对象缺失），也没指明改什么（字段缺失）——
                    我可以写出无限多种改法，也就无法判定哪一种是"对的"。

    原句 2：「以便临时加购或者退掉不要的东西」
      为什么测不了：这是价值陈述，不是行为描述。"退掉"没有说明资金
                    如何处理（原路退回？记入余额？），也没有边界
                    （部分退 / 全退 / 已核销还能不能退），无法写出预期。
    ```

    澄清问题要**二选一或给数值**，例如：

    ```text
    Q1：改单权限归属？
        A) 仅下单人所属团长本人可改  B) 同一自提点任一团长可改
        → 向 PO 张 XX 确认（直接决定权限测试矩阵是 1 条还是 N² 条）

    Q2：成团后改单，资金是"原路退回（T+1）"还是"退至账户余额（实时）"？
        → 向 PO + 财务确认（决定退款用例的预期金额与到账时间断言）

    Q3：改单允许的次数上限？
        A) 不限  B) 每单 1 次  C) 每单 3 次
        → 向 PO 确认（决定边界用例和并发用例的设计）
    ```

    **第 2 题：Given-When-Then 示例（挑最容易被漏的几条）**

    US-102（核销）——注意它必须处理"一码一核销 vs 30 分钟可撤销"的矛盾：

    ```gherkin
    Scenario: 扫码枪在弱网下重复扫码只核销一次
      Given 订单 O-1001 状态为"待核销"，核销码为 8 位数字
      And 团长账号权限为"仅核销"
      And 安卓扫码枪 A 位于 4G 弱网环境（丢包率 > 20%）
      When 团长连续扫码 3 次
      Then 系统只产生 1 条核销记录，核销时间为首次成功时间
      And 后 2 次返回"该订单已核销"，不产生新记录
    # 验收方式：接口自动化（幂等逻辑在后端，UI 层无法可靠模拟丢包）

    Scenario: 核销后 30 分钟内撤销，核销记录必须可追溯
      Given 订单 O-1002 已于 10:00:00 被核销
      When 团长在 10:25:00 发起撤销
      Then 订单状态回退为"待核销"
      And 保留 1 条撤销记录（含操作人、时间、原核销记录 ID）
      And 原核销记录标记为"已撤销"而非删除
    # 验收方式：接口自动化 + 数据库校验（合规要求留存 3 年可追溯）

    Scenario: 超过 30 分钟不允许自助撤销
      Given 订单 O-1003 已于 10:00:00 被核销
      When 团长在 10:30:01 发起撤销
      Then 系统拒绝撤销并提示"已超过自助撤销时限，请联系客服"
      And 订单状态仍为"已核销"
    # 验收方式：接口自动化（纯边界判定，用时间模拟即可）
    ```

    矛盾点与取舍（第 3 题）：

    ```text
    冲突原文：《核销说明》第 2 条"核销后不可撤销"
              《核销说明》第 5 条"核销后 30 分钟内允许团长申请撤销"

    影响：两条规则同时存在时，"不可撤销"到底指"客人不可撤"还是
          "任何人都不可撤"无法判定；如果实现只按第 2 条做，团长撤销功能
          会整块失效；如果只按第 5 条做，合规上的"不可篡改"就有缺口。

    建议取舍：第 2 条限定为"客户端/用户侧不可撤销"，第 5 条限定为
              "团长侧 30 分钟内可申请撤销且留痕"。撤销必须产生新记录，
              不得物理删除原核销记录，以满足"留存 3 年可追溯"。
    ```

    US-101（分享）——一个容易被写漏的点是**分享链接与成团状态的联动**：

    ```gherkin
    Scenario: 分享链接在 24 小时后失效
      Given 用户 U 于 3 月 4 日 10:00 生成分享链接 L
      When 朋友在 3 月 5 日 10:00:01 打开 L
      Then 页面提示"分享已过期"，并引导用户查看当前进行中的团
      And 不产生新订单
    # 验收方式：接口自动化（时间可 mock，边界值精确到秒）

    Scenario: 成团失败后分享链接仍可打开
      Given 团 G 已因人数不足成团失败并自动全额退款
      When 朋友打开该团的分享链接 L
      Then 页面提示"该团已结束"，明确展示退款说明（T+1 到账）
      And 允许用户浏览商品但不允许加入该团
    # 验收方式：手工（依赖退款与成团状态联动，链路长且沙箱不稳定）
    ```

    **第 4 题：测试策略与金字塔配比**

    本迭代的配比建议（要给出理由，不能只写数字）：

    ```text
    单元 : 接口 : UI = 70 : 25 : 5

    理由：本迭代三个故事的核心风险都在"规则判定"（幂等核销、改单资金、
    分享有效期），这类逻辑最适合放在接口层自动化——运行快、稳定、可 mock
    时间。UI 自动化现有 20 条已够冒烟，本迭代只补 1~2 条主链路
    （分享 → 下单 → 核销），因为带扫码枪的核销流程 UI 自动化成本高、
    且扫码枪设备无法在 CI 里模拟，强行 UI 自动化会变成长期维护负担。
    ```

    策略表片段（注意工时总和必须 ≤5 人日）：

    | 测什么 | 方式 | 负责 | 工时 | 依赖 |
    |--------|------|------|------|------|
    | 核销幂等与 30 分钟边界 | 接口自动化 | 测试 | 1.0 人日 | 核销接口契约冻结 |
    | 改单资金计算与退款 | 接口自动化 | 测试 + 开发 | 1.5 人日 | 退款沙箱可用 |
    | 分享链接有效期 | 接口自动化 | 测试 | 0.5 人日 | 时间 mock 能力 |
    | 扫码枪真机核销（Android 9 / iOS） | 手工 | 测试 | 0.5 人日 | 扫码枪 A 到位、自提点账号 |
    | 权限矩阵（团长本人 / 同点位） | 手工 | 测试 | 0.5 人日 | 权限配置完成 |
    | 弱网与并发核销 | 探索 | 测试 | 0.5 人日 | 弱网工具 |
    | 冒烟主链路 | UI 自动化 | 测试 | 0.5 人日 | 测试环境稳定 |
    | **合计** | | | **5.0 人日** | |

    **不做清单**（必须写承担人）：

    ```text
    1. 本次不做 400 个自提点的批量导入回归
       → 承担人：PO 张 XX（依据：导入逻辑本迭代未改动）

    2. 本次不做第三方支付沙箱之外的银行渠道真实退款验证
       → 承担人：开发 李 XX（依据：沙箱不稳定，真实渠道由运维抽检）

    3. 本次不做 iOS 全版本矩阵（只验证当前主流 2 个版本）
       → 承担人：测试（依据：团长设备以安卓为主，iOS 存量 < 5%）
    ```

    **第 5 题：DoD 示例（至少 3 条机器可校验）**

    ```text
    - [ ] 代码完成并通过 Code Review（≥1 名 reviewer 批准）
    - [ ] 单元测试通过，且本次改动模块行覆盖率 ≥ 70%      ← 机器校验（SonarQube 阈值）
    - [ ] 接口自动化用例全部通过                           ← 机器校验（CI 门禁：pytest 全绿）
    - [ ] 新增接口自动化用例 ≥ 15 条，且 CI 中无 skip      ← 机器校验（用例数断言）
    - [ ] UI 自动化冒烟（20 条）全部通过                   ← 机器校验（Playwright CI job）
    - [ ] 无 P0/P1 缺陷；P2 缺陷有明确的修复版本           ← 可校验（缺陷库查询）
    - [ ] 三条验收标准中的"异常场景"均已执行并留痕
    - [ ] 核销记录可追溯性验证通过（含撤销记录的 DB 校验）
    - [ ] 测试环境回归通过，无新增回归缺陷
    - [ ] 上线手册 / 团长操作说明已更新（如有面向团长的新行为）
    ```

    注意最后一条体现一个关键判断：**面向兼职老年团长的行为变更，文档更新属于 DoD**，
    因为"产品能用"和"团长会用"是两件事。

    **第 6 题：三 Amigos 议程（30 分钟）示例**

    | 分钟 | 议题 | 主讲 | 预期产出物 |
    |------|------|------|-----------|
    | 0-2 | 目标与规则说明 | SM / 测试 | 会议约定（每个故事只解决"测试性"问题） |
    | 2-10 | US-101 分享：澄清有效期与成团联动 | PO | 5 条验收标准定稿 |
    | 10-20 | US-102 核销：解决"一码一核销 vs 30 分钟撤销"矛盾 | 测试 | 矛盾取舍结论 + 6 条验收标准 |
    | 20-27 | US-103 改单：权限、资金、次数上限三问 | PO | 澄清问题答案 + 是否拆分的结论 |
    | 27-30 | 确认 DoD 与不做清单 | 全组 | DoD 定稿、不做清单及承担人 |

    关键判断：**US-103 估 8 点，很可能在会上被判为"需要拆分"**——这正是三 Amigos
    在 Planning 前的价值：与其在 Sprint 中途发现做不完，不如在 30 分钟里拆掉它。
