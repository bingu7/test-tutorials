## 选择题

<div class="quiz-container" data-quiz-id="test-pyramid">

<div class="quiz-item" data-correct="0">
<div class="quiz-question">测试金字塔<strong>从下到上</strong>的正确顺序是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q1" value="0"> 单元测试 → 接口（服务）测试 → UI / E2E 测试</label>
<label class="quiz-option"><input type="radio" name="q1" value="1"> UI / E2E 测试 → 接口（服务）测试 → 单元测试</label>
<label class="quiz-option"><input type="radio" name="q1" value="2"> 接口（服务）测试 → 单元测试 → UI / E2E 测试</label>
<label class="quiz-option"><input type="radio" name="q1" value="3"> 单元测试 → UI / E2E 测试 → 接口（服务）测试</label>
</div>
<div class="quiz-explanation">💡 金字塔底宽顶窄：越往下数量越多、执行越快、成本越低；越往上数量越少、执行越慢、维护越贵。接口层处在中间，是收益和成本最平衡的一层</div>
</div>

<div class="quiz-item" data-correct="2">
<div class="quiz-question">为什么不能把测试全部交给 UI 自动化？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q2" value="0"> UI 自动化工具授权费用普遍更高</label>
<label class="quiz-option"><input type="radio" name="q2" value="1"> UI 自动化无法断言页面上显示的文字</label>
<label class="quiz-option"><input type="radio" name="q2" value="2"> 执行慢、稳定性差、维护成本高，问题反馈也最滞后</label>
<label class="quiz-option"><input type="radio" name="q2" value="3"> UI 自动化只能由开发人员编写</label>
</div>
<div class="quiz-explanation">💡 UI 层要经历完整链路的渲染和交互，脚本对页面结构极其敏感，一处样式改动就可能让一批用例失败。大量 UI 用例会让回归时间失控、误报频发，反而削弱团队对自动化的信任</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">折扣规则、金额计算这类分支组合很多的业务逻辑，最适合放在哪一层验证？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q3" value="0"> UI 层，通过页面操作逐个验证</label>
<label class="quiz-option"><input type="radio" name="q3" value="1"> 单元层，直接覆盖各种输入组合</label>
<label class="quiz-option"><input type="radio" name="q3" value="2"> 手工探索，靠经验抽查</label>
<label class="quiz-option"><input type="radio" name="q3" value="3"> 性能测试，通过高并发暴露问题</label>
</div>
<div class="quiz-explanation">💡 分支组合最容易出错、也最需要穷举，而单元测试执行成本最低，可以在毫秒级跑完几十种组合。放到 UI 层等于用最贵的资源做最该由底层承担的事</div>
</div>

<div class="quiz-item" data-correct="3">
<div class="quiz-question">手工测试和探索式测试在分层策略中的位置是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q4" value="0"> 已经被自动化完全取代，可以省略</label>
<label class="quiz-option"><input type="radio" name="q4" value="1"> 只在 UI 层做，替代部分 UI 自动化用例</label>
<label class="quiz-option"><input type="radio" name="q4" value="2"> 只在项目上线后做，用于收集用户反馈</label>
<label class="quiz-option"><input type="radio" name="q4" value="3"> 独立于金字塔存在，用来发现自动化覆盖不到的问题</label>
</div>
<div class="quiz-explanation">💡 自动化擅长"验证已经想到的"，探索式测试擅长"发现还没想到的"——易用性、交互细节、异常路径、跨模块组合问题。两者是互补关系，不是替代关系</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">"把所有手工用例都转成 UI 脚本"这一做法的典型问题是什么？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q5" value="0"> 会让测试用例数量变少，覆盖度下降</label>
<label class="quiz-option"><input type="radio" name="q5" value="1"> 维护成本远超收益，脚本很快变成负担</label>
<label class="quiz-option"><input type="radio" name="q5" value="2"> 会让缺陷数量上升</label>
<label class="quiz-option"><input type="radio" name="q5" value="3"> 会导致无法再使用测试管理工具</label>
</div>
<div class="quiz-explanation">💡 手工用例里大量是一次性验证、低频路径和需要主观判断的内容，转成脚本后每次需求变更都要跟着改，投入产出比极低。自动化要挑"稳定、重复、高价值"的场景</div>
</div>

<div class="quiz-item" data-correct="0">
<div class="quiz-question">决定一个测试点该放在哪一层，主要依据是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q6" value="0"> 风险高低、变更频率和执行成本</label>
<label class="quiz-option"><input type="radio" name="q6" value="1"> 团队里谁的脚本写得更熟练</label>
<label class="quiz-option"><input type="radio" name="q6" value="2"> 客户是否要求提供自动化覆盖率报告</label>
<label class="quiz-option"><input type="radio" name="q6" value="3"> 用例在测试管理工具里的编号顺序</label>
</div>
<div class="quiz-explanation">💡 分层的本质是资源分配：高风险、逻辑复杂、频繁回归的内容尽量下沉到便宜的层；只有"必须验证真实链路"的部分才留在 UI 层</div>
</div>

<div class="quiz-item" data-correct="2">
<div class="quiz-question">在 CI/CD 中，比较合理的分层运行策略是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q7" value="0"> 每次提交都把单元、接口、UI 全套跑一遍，保证绝对安全</label>
<label class="quiz-option"><input type="radio" name="q7" value="1"> 只在发版当天跑一次完整回归</label>
<label class="quiz-option"><input type="radio" name="q7" value="2"> 每次提交跑单元和接口测试，UI / E2E 定时或发布前运行</label>
<label class="quiz-option"><input type="radio" name="q7" value="3"> 只跑 UI 测试，因为最接近用户真实操作</label>
</div>
<div class="quiz-explanation">💡 分层运行的核心是"反馈速度匹配触发频率"：提交级流水线要快，所以放单元和接口；UI / E2E 慢，放在每日构建或发布前跑，既控住风险又不拖慢开发</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">相比 UI 层，接口层做自动化测试的主要优势是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q8" value="0"> 能覆盖页面布局和视觉问题</label>
<label class="quiz-option"><input type="radio" name="q8" value="1"> 执行更快、更稳定，且能覆盖前端绕过的场景</label>
<label class="quiz-option"><input type="radio" name="q8" value="2"> 不需要任何测试数据</label>
<label class="quiz-option"><input type="radio" name="q8" value="3"> 可以直接替代安全测试</label>
</div>
<div class="quiz-explanation">💡 接口层绕过了浏览器渲染，执行速度通常比 UI 快一个数量级，也不受页面结构变动影响。更重要的是，直接调用接口才能验证前端已经做过的校验在服务端是否同样成立</div>
</div>

<div class="quiz-item" data-correct="3">
<div class="quiz-question">落地分层策略时提到的"最小自动化集"指的是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q9" value="0"> 一套只在下班后运行的夜间用例</label>
<label class="quiz-option"><input type="radio" name="q9" value="1"> 由一名成员独立完成的最小脚本集合</label>
<label class="quiz-option"><input type="radio" name="q9" value="2"> 只覆盖单个模块的全部自动化用例</label>
<label class="quiz-option"><input type="radio" name="q9" value="3"> 用最少用例覆盖核心业务流程关键路径的集合</label>
</div>
<div class="quiz-explanation">💡 起步阶段不要追求覆盖率数字，先用少量用例守住"登录、下单、支付"这类断了就影响生意的链路，跑稳之后再逐步扩面</div>
</div>

<div class="quiz-item" data-correct="0">
<div class="quiz-question">单元测试的典型特征是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q10" value="0"> 执行快、相互隔离、不依赖外部环境和数据</label>
<label class="quiz-option"><input type="radio" name="q10" value="1"> 必须连接真实数据库才能运行</label>
<label class="quiz-option"><input type="radio" name="q10" value="2"> 需要缺陷管理系统中存在对应编号</label>
<label class="quiz-option"><input type="radio" name="q10" value="3"> 需要人工逐条点击确认结果</label>
</div>
<div class="quiz-explanation">💡 单元测试对数据库、网络等外部依赖要用打桩或 Mock 隔离，这样才能毫秒级执行、结果稳定，也才能在每次提交时都跑一遍</div>
</div>

<div class="quiz-item" data-correct="2">
<div class="quiz-question">按照落地步骤，开展分层建设的第一步应该是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q11" value="0"> 先采购自动化测试平台和云测设备</label>
<label class="quiz-option"><input type="radio" name="q11" value="1"> 直接把现有的 UI 脚本拆成单元测试</label>
<label class="quiz-option"><input type="radio" name="q11" value="2"> 列出核心业务流程，再按风险排序</label>
<label class="quiz-option"><input type="radio" name="q11" value="3"> 要求开发团队先把覆盖率提到 90%</label>
</div>
<div class="quiz-explanation">💡 先看清"业务上什么最不能出问题"，才谈得上选择层级和投入顺序。跳过这一步直接上工具，很容易做出规模很大但没人看的用例集</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">"冰淇淋甜筒"反模式描述的是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q12" value="0"> 单元测试过多，UI 测试几乎为零</label>
<label class="quiz-option"><input type="radio" name="q12" value="1"> UI 用例数量最多，单元测试最少，金字塔被倒置</label>
<label class="quiz-option"><input type="radio" name="q12" value="2"> 只做手工测试，完全不做自动化</label>
<label class="quiz-option"><input type="radio" name="q12" value="3"> 只做性能测试，忽略功能测试</label>
</div>
<div class="quiz-explanation">💡 冰淇淋甜筒是金字塔倒过来：大量 UI 脚本压顶、底层空洞。表现就是回归时间长、误报多、维护成本失控，团队最终对自动化失去信心</div>
</div>
