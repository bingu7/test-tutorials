## 选择题

<div class="quiz-container" data-quiz-id="ci-basics">

<div class="quiz-item" data-correct="1">
<div class="quiz-question">持续集成（CI）的核心实践是什么？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q1" value="0"> 每月合并一次代码</label>
<label class="quiz-option"><input type="radio" name="q1" value="1"> 开发人员频繁地将代码集成到共享分支，每次集成自动触发构建和测试</label>
<label class="quiz-option"><input type="radio" name="q1" value="2"> 只在发布前进行一次集成测试</label>
<label class="quiz-option"><input type="radio" name="q1" value="3"> 将所有代码放在一个文件中</label>
</div>
<div class="quiz-explanation">💡 持续集成强调开发人员至少每天一次将代码集成到主干分支，每次集成自动触发编译、单元测试和接口测试，尽早发现和修复集成问题，避免"集成地狱"</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">以下关于 CI 和 CD 的描述，哪个是正确的？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q2" value="0"> CI 是持续集成，CD 只指持续部署</label>
<label class="quiz-option"><input type="radio" name="q2" value="1"> CI 是持续集成，CD 可以指持续交付或持续部署</label>
<label class="quiz-option"><input type="radio" name="q2" value="2"> CI 和 CD 是完全相同的概念</label>
<label class="quiz-option"><input type="radio" name="q2" value="3"> CI 指代码审查，CD 指代码部署</label>
</div>
<div class="quiz-explanation">💡 CD 有两种含义：持续交付确保代码随时可发布，但需要人工审批后部署；持续部署则完全自动化，代码通过测试后自动部署到生产环境</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">在 Jenkins 声明式 Pipeline 中，以下哪个关键字用于定义流水线的各个阶段？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q3" value="0"> steps</label>
<label class="quiz-option"><input type="radio" name="q3" value="1"> stage</label>
<label class="quiz-option"><input type="radio" name="q3" value="2"> node</label>
<label class="quiz-option"><input type="radio" name="q3" value="3"> job</label>
</div>
<div class="quiz-explanation">💡 Jenkins 声明式 Pipeline 使用 pipeline → stages → stage 结构。stage 定义流水线的各个阶段，steps 定义阶段内的具体操作，node 是脚本式 Pipeline 中的概念</div>
</div>

<div class="quiz-item" data-correct="0">
<div class="quiz-question">以下 Jenkinsfile 语法中，哪个是正确的声明式 Pipeline 结构？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q4" value="0"> pipeline { stages { stage('Build') { steps { echo 'Building' } } } }</label>
<label class="quiz-option"><input type="radio" name="q4" value="1"> job { steps { echo 'Building' } }</label>
<label class="quiz-option"><input type="radio" name="q4" value="2"> build { task('Build') { run { echo 'Building' } } }</label>
<label class="quiz-option"><input type="radio" name="q4" value="3"> workflow { phase('Build') { action { echo 'Building' } } }</label>
</div>
<div class="quiz-explanation">💡 Jenkins 声明式 Pipeline 必须以 pipeline 块开始，包含 stages 块，每个阶段用 stage 定义，具体操作放在 steps 块中</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">以下哪种方式可以自动触发 Jenkins Pipeline 执行？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q5" value="0"> 只能手动点击"Build Now"</label>
<label class="quiz-option"><input type="radio" name="q5" value="1"> 配置 Webhook，当代码推送到 Git 仓库时自动触发</label>
<label class="quiz-option"><input type="radio" name="q5" value="2"> 每天定时手动执行</label>
<label class="quiz-option"><input type="radio" name="q5" value="3"> 需要重启 Jenkins 服务才能执行</label>
</div>
<div class="quiz-explanation">💡 Jenkins 支持多种自动触发方式：Git Webhook、定时构建、轮询 SCM、其他 Pipeline 触发。Webhook 是最常用的方式，实现真正的持续集成</div>
</div>

<div class="quiz-item" data-correct="0">
<div class="quiz-question">在 GitHub Actions 中，一个 Workflow 文件应该放在哪个目录下？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q6" value="0"> .github/workflows/</label>
<label class="quiz-option"><input type="radio" name="q6" value="1"> .ci/pipelines/</label>
<label class="quiz-option"><input type="radio" name="q6" value="2"> jenkins/</label>
<label class="quiz-option"><input type="radio" name="q6" value="3"> actions/config/</label>
</div>
<div class="quiz-explanation">💡 GitHub Actions 的 Workflow 文件必须放在仓库的 .github/workflows/ 目录下，使用 YAML 格式编写，通过 on 字段定义触发条件</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">在 GitHub Actions 中，以下哪个 on 配置可以在代码推送到 main 分支时触发 Workflow？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q7" value="0"> on: click</label>
<label class="quiz-option"><input type="radio" name="q7" value="1"> on: push: branches: [main]</label>
<label class="quiz-option"><input type="radio" name="q7" value="2"> on: schedule</label>
<label class="quiz-option"><input type="radio" name="q7" value="3"> on: manual</label>
</div>
<div class="quiz-explanation">💡 GitHub Actions 使用 on 字段定义触发事件。on: push: branches: [main] 表示当代码推送到 main 分支时触发，还可以使用 pull_request、schedule、workflow_dispatch 等</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">在 GitHub Actions 中，以下关于 Job 和 Step 的描述，哪个是正确的？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q8" value="0"> 一个 Step 包含多个 Job</label>
<label class="quiz-option"><input type="radio" name="q8" value="1"> 一个 Job 包含多个 Step，不同 Job 默认并行执行</label>
<label class="quiz-option"><input type="radio" name="q8" value="2"> Job 和 Step 是相同的概念</label>
<label class="quiz-option"><input type="radio" name="q8" value="3"> Step 必须使用 Docker 容器</label>
</div>
<div class="quiz-explanation">💡 GitHub Actions 的结构是 Workflow → Job → Step。不同 Job 默认并行执行（可用 needs 设置依赖），同一个 Job 内的 Step 按顺序串行执行</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">在 CI/CD 中使用 Docker 的主要优势是什么？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q9" value="0"> 只是为了减少代码量</label>
<label class="quiz-option"><input type="radio" name="q9" value="1"> 保证构建和测试环境的一致性，实现"一次构建，到处运行"</label>
<label class="quiz-option"><input type="radio" name="q9" value="2"> Docker 会自动编写测试用例</label>
<label class="quiz-option"><input type="radio" name="q9" value="3"> Docker 可以替代所有 CI/CD 工具</label>
</div>
<div class="quiz-explanation">💡 Docker 容器化将应用及其依赖打包在一起，解决了环境不一致问题。在 CI/CD 中可以使用 Docker 镜像作为构建环境，也便于快速创建和销毁测试环境</div>
</div>

<div class="quiz-item" data-correct="2">
<div class="quiz-question">以下 Dockerfile 指令中，哪个用于指定基础镜像？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q10" value="0"> RUN</label>
<label class="quiz-option"><input type="radio" name="q10" value="1"> COPY</label>
<label class="quiz-option"><input type="radio" name="q10" value="2"> FROM</label>
<label class="quiz-option"><input type="radio" name="q10" value="3"> CMD</label>
</div>
<div class="quiz-explanation">💡 FROM 指令指定构建镜像的基础镜像，是 Dockerfile 的第一条指令。RUN 执行命令，COPY 复制文件，CMD 指定容器启动时的默认命令</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">一个标准的 CI/CD 流水线通常包含以下哪些阶段？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q11" value="0"> 只有代码编写</label>
<label class="quiz-option"><input type="radio" name="q11" value="1"> 构建 → 单元测试 → 集成测试 → 部署</label>
<label class="quiz-option"><input type="radio" name="q11" value="2"> 只有部署</label>
<label class="quiz-option"><input type="radio" name="q11" value="3"> 编写文档 → 代码审查 → 发布</label>
</div>
<div class="quiz-explanation">💡 标准的 CI/CD 流水线通常包括：代码提交 → 构建 → 单元测试 → 集成/接口测试 → 代码质量检查 → 部署到测试环境 → 验收测试 → 部署到生产环境。每个阶段都可能设置质量门禁</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">在 CI/CD 流程中，构建制品（Artifacts）应该存储在哪里？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q12" value="0"> 开发人员的本地电脑</label>
<label class="quiz-option"><input type="radio" name="q12" value="1"> 制品仓库（如 Nexus、Harbor）进行统一管理</label>
<label class="quiz-option"><input type="radio" name="q12" value="2"> Git 代码仓库中</label>
<label class="quiz-option"><input type="radio" name="q12" value="3"> 随意放在临时目录</label>
</div>
<div class="quiz-explanation">💡 构建制品应存储在专用的制品仓库中，这样可以版本化管理、控制访问权限、避免 Git 仓库臃肿，并且方便在不同环境间传递和部署</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">质量门禁（Quality Gate）在 CI/CD 中的作用是什么？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q13" value="0"> 限制开发人员的代码提交频率</label>
<label class="quiz-option"><input type="radio" name="q13" value="1"> 在流水线的某个阶段设置通过条件，不满足则阻止流程继续</label>
<label class="quiz-option"><input type="radio" name="q13" value="2"> 只用于检查代码格式</label>
<label class="quiz-option"><input type="radio" name="q13" value="3"> 限制 CI/CD 工具的使用次数</label>
</div>
<div class="quiz-explanation">💡 质量门禁是在 CI/CD 流水线中设置的检查点，定义了代码必须满足的条件。不满足条件时流水线会失败，阻止问题代码进入下一阶段，确保软件质量</div>
</div>

<div class="quiz-item" data-correct="0">
<div class="quiz-question">在 CI/CD 流水线中集成代码质量扫描工具，以下哪个是常用的代码质量平台？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q14" value="0"> SonarQube</label>
<label class="quiz-option"><input type="radio" name="q14" value="1"> Photoshop</label>
<label class="quiz-option"><input type="radio" name="q14" value="2"> Microsoft Word</label>
<label class="quiz-option"><input type="radio" name="q14" value="3"> Chrome 浏览器</label>
</div>
<div class="quiz-explanation">💡 SonarQube 是最流行的代码质量和安全扫描平台，支持多种编程语言，可以检测代码异味、Bug、安全漏洞和测试覆盖率，通常集成在 CI 流水线中作为质量门禁的一部分</div>
</div>

<div class="quiz-item" data-correct="0">
<div class="quiz-question">在 Jenkins 声明式 Pipeline 中，如何实现多个阶段并行执行？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q15" value="0"> 在 stage 内部使用 parallel 块</label>
<label class="quiz-option"><input type="radio" name="q15" value="1"> 创建多个 Jenkinsfile</label>
<label class="quiz-option"><input type="radio" name="q15" value="2"> 在 post 块中配置</label>
<label class="quiz-option"><input type="radio" name="q15" value="3"> 使用 input 关键字</label>
</div>
<div class="quiz-explanation">💡 Jenkins 声明式 Pipeline 支持在 stage 内部使用 parallel 块并行执行多个分支。例如可以同时在不同浏览器上运行 UI 测试，或同时执行单元测试和接口测试，提高流水线执行效率</div>
</div>
