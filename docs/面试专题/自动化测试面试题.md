# 自动化测试面试题

自动化测试面试不会只问“会不会 Selenium”。更常见的是问你为什么做自动化、怎么选场景、怎么保证稳定、失败怎么排查。

## 什么样的用例适合自动化？

推荐回答：

```text
适合自动化的是稳定、重复执行、业务价值高、人工执行成本高的场景，比如登录、下单、查询、核心接口回归。
不适合自动化的是需求频繁变化、一次性验证、强依赖人工判断或验证码很复杂的场景。
```

## 自动化测试框架一般包含哪些模块？

可以回答：

- 用例层：组织测试用例。
- 请求或页面封装层：封装接口请求或页面操作。
- 数据层：管理测试数据。
- 配置层：环境地址、账号、超时时间。
- 断言层：判断结果是否符合预期。
- 报告层：生成 Allure、HTML 等报告。
- 日志层：记录失败原因。
- CI 集成：在流水线中自动运行。

## Selenium 和 Playwright 怎么选？

```text
如果公司已有 Selenium 框架，我会优先维护现有框架，因为迁移成本高。
如果是新项目，我更倾向 Playwright，因为它自动等待能力强，调试工具和 trace 对定位问题比较友好。
但最终要看团队技术栈、浏览器要求和维护成本。
```

## 为什么不要大量使用 sleep？

推荐回答：

```text
sleep 是固定等待，页面快时浪费时间，页面慢时仍可能失败。
更推荐显式等待或框架内置自动等待，等待某个元素出现、可点击或接口完成。
```

## 元素定位不稳定怎么办？

处理思路：

- 优先使用稳定属性：`id`、`name`、`data-testid`、可访问名称。
- 避免依赖容易变化的层级 XPath。
- 和开发约定测试专用属性。
- 对动态列表先定位容器，再定位目标元素。
- 失败时保存截图和页面 HTML。

## 自动化用例失败怎么排查？

可以按顺序回答：

```text
先看失败日志和截图，确认失败步骤。
再判断是环境问题、数据问题、定位问题、等待问题还是业务缺陷。
如果本地能复现，就进一步查看接口、数据库和页面状态。
如果只是偶现，要看是否有并发数据污染或等待不稳定。
```

## 自动化覆盖率是不是越高越好？

推荐回答：

```text
不是。自动化要关注收益和维护成本。
核心、稳定、重复执行的场景优先自动化；变化频繁或人工判断成本低的场景不一定值得自动化。
覆盖率高但经常失败，会降低团队信任。
```
