# 项目经验表达

很多新手学了不少工具，但面试时说项目只会说“我负责功能测试和接口测试”。这种表达太空泛，面试官很难判断你到底做过什么。

## 推荐表达结构

```text
项目背景
  -> 我的职责
  -> 测试范围
  -> 使用工具
  -> 关键测试点
  -> 发现的问题
  -> 最终结果
```

## 电商项目表达示例

不推荐：

```text
我做过电商项目，负责写用例、测接口、提 Bug。
```

推荐：

```text
我做过一个电商下单流程测试，主要负责购物车、订单创建和支付状态流转。
测试前我先根据需求拆了测试点，包括商品库存、优惠券、收货地址、订单金额、支付回调和超时取消。
执行时用 Postman 验证接口，用数据库校验订单状态和库存变化。
其中发现过一个问题：支付回调重复发送时，订单状态被重复更新，可能导致后续发货逻辑异常。提交缺陷后开发增加了幂等校验，我回归验证通过。
最后输出了测试用例、缺陷记录和测试报告。
```

## 接口自动化项目表达示例

```text
我做过一个接口自动化回归项目，主要覆盖登录、用户信息、订单查询和订单创建接口。
框架使用 Python、Requests、Pytest 和 Allure。
我把基础请求方法封装成公共方法，把环境地址和账号放到配置文件中，用 YAML 管理测试数据。
断言方面不仅校验状态码，还校验业务码、关键字段和数据库状态。
后面把自动化命令接入 Jenkins，每次构建后自动运行，并生成 Allure 报告。
```

## 回答项目难点

面试官常问：“项目里遇到过什么难点？”

不要回答：

```text
没什么难点。
```

可以回答：

```text
当时接口自动化最大的问题是测试数据不稳定。比如订单创建依赖商品库存和用户地址，数据被其他同学改动后用例会失败。
后来我把测试数据分成固定基础数据和用例运行时创建的数据，运行前先准备数据，运行后清理部分数据，同时给断言增加更明确的失败提示。
这样用例稳定性明显提升。
```

## STAR 表达法

| 部分 | 问自己 |
|------|--------|
| Situation | 当时是什么项目或场景 |
| Task | 你负责什么任务 |
| Action | 你具体做了什么 |
| Result | 结果是什么，有什么收益 |

## 项目表达检查清单

- [ ] 是否说清楚业务场景。
- [ ] 是否说清楚自己负责的范围。
- [ ] 是否提到测试点，而不只是工具名。
- [ ] 是否有具体缺陷或问题处理例子。
- [ ] 是否能说明最终产出。
- [ ] 是否避免夸大，比如没做过性能测试就不要说负责性能优化。
