# 项目经验表达

很多新手学了不少工具，但面试时说项目只会说"我负责功能测试和接口测试"。这种表达太空泛，面试官很难判断你到底做过什么。

## 推荐表达结构

```text
项目背景 → 我的职责 → 测试范围 → 使用工具 → 关键测试点 → 发现的问题 → 最终结果
```

## 电商项目表达示例

不推荐：

```text
我做过电商项目，负责写用例、测接口、提 Bug。
```

推荐：

```text
项目：电商下单流程测试
职责：购物车、订单创建和支付状态流转

测试前：
- 根据需求拆测试点：商品库存、优惠券、收货地址、订单金额、支付回调、超时取消

执行时：
- 用 Postman 验证接口
- 用数据库校验订单状态和库存变化

发现的问题：
- 支付回调重复发送时，订单状态被重复更新，可能导致后续发货逻辑异常
- 提交缺陷后开发增加了幂等校验，我回归验证通过

最终产出：测试用例、缺陷记录、测试报告
```

## 接口自动化项目表达示例

```text
项目：接口自动化回归
覆盖范围：登录、用户信息、订单查询、订单创建接口

技术栈：Python + Requests + Pytest + Allure

框架设计：
- 基础请求方法封装成公共方法
- 环境地址和账号放到配置文件
- 用 YAML 管理测试数据

断言策略：
- 不仅校验状态码，还校验业务码、关键字段和数据库状态

CI 集成：
- 接入 Jenkins，每次构建后自动运行，生成 Allure 报告
```

## 回答项目难点

面试官常问："项目里遇到过什么难点？"

不要回答：

```text
没什么难点。
```

可以回答：

```text
问题：接口自动化最大的问题是测试数据不稳定
  - 订单创建依赖商品库存和用户地址
  - 数据被其他同学改动后用例会失败

解决方案：
  - 测试数据分成固定基础数据和用例运行时创建的数据
  - 运行前先准备数据，运行后清理部分数据
  - 给断言增加更明确的失败提示

结果：用例稳定性明显提升
```

## STAR 表达法

| 部分 | 问自己 |
|------|--------|
| Situation | 当时是什么项目或场景 |
| Task | 你负责什么任务 |
| Action | 你具体做了什么 |
| Result | 结果是什么，有什么收益 |

## 项目表达检查清单

- [ ] 是否说清楚业务场景
- [ ] 是否说清楚自己负责的范围
- [ ] 是否提到测试点，而不只是工具名
- [ ] 是否有具体缺陷或问题处理例子
- [ ] 是否能说明最终产出
- [ ] 是否避免夸大，比如没做过性能测试就不要说负责性能优化

## Web 自动化项目表达示例

```text
项目：Web 自动化回归
覆盖范围：登录、商品搜索、加入购物车、下单

技术栈：Playwright + Pytest + Allure
框架：Page Object 模式，每个页面封装成一个类

最大的挑战：
- 元素定位不稳定，商品列表的 DOM 结构经常变化
- 解决：跟前端协商加了 data-testid 属性，稳定性明显提升

CI 集成：
- 接入 GitHub Actions，每次提测前自动跑一轮回归
- 失败用例自动截图和保存 Trace
```

## 性能测试项目表达示例

```text
项目：电商大促前性能测试
目标：验证系统在 1000 并发下的稳定性

我的职责：
- 设计压测场景：首页浏览、商品搜索、下单支付
- 用 JMeter 编写脚本

发现的问题：
- 商品搜索接口在 500 并发时响应时间从 200ms 飙升到 3 秒
- 排查后发现是数据库缺少索引，全表扫描导致
- 加索引后响应时间稳定在 300ms 以内

最终产出：性能测试报告（TPS、响应时间、错误率、瓶颈分析）
```

## 面试官追问怎么回答

| 追问 | 回答思路 |
|------|---------|
| "你们团队几个人？" | 说清楚测试团队规模和你的角色，不要夸大 |
| "你独立负责还是协作？" | 诚实说明哪些是你独立做的，哪些是协作的 |
| "为什么选这个技术栈？" | 说出对比和权衡，比如"对比了 Selenium，选 Playwright 因为自动等待更好" |
| "遇到的最大困难？" | 用 STAR 法：场景→任务→行动→结果，重点说你怎么解决的 |
| "有什么可以改进的？" | 展示自我反思能力，比如"如果重来我会先搭好数据工厂" |
| "你学到了什么？" | 说技术收获和非技术收获（沟通、协作、时间管理） |

## 常见追问的"坑"

不要这样回答：

```text
面试官：你们自动化覆盖率多少？
你：100%。

（没有项目能做到 100%，面试官会追问细节然后露馅）
```

推荐这样回答：

```text
核心接口覆盖率大概 70%，UI 层只覆盖了 5 条核心流程。

覆盖率不是目标，重点是覆盖了最有业务价值的场景。
我们定期 review 用例，把维护成本高但价值低的用例下掉。
```

## 项目表达检查清单（补充）

- [ ] 是否准备了 2-3 个不同类型的项目（功能测试、自动化、性能）
- [ ] 是否能说出项目的时间周期和团队规模
- [ ] 是否准备了至少 2 个"难点+解决方案"的故事
- [ ] 是否能说出项目的不足和改进方向
- [ ] 是否避免说"我们团队"而忘记说"我做了什么"
- [ ] 是否准备了面试官可能追问的问题和回答
