## 新手导读

很多人写的"自动化框架"，本质是**一堆脚本放在文件夹里**：能跑，但改一个接口要动十个文件，加一条用例要复制粘贴。

框架设计的全部目的只有一句话：

> **让"加用例""改环境""换数据"这些高频操作，成本尽可能低。**

判断你的框架好不好，回答这三个问题就够了：

| 问题 | 好框架的回答 | 坏框架的回答 |
|------|--------------|--------------|
| 接口地址变了，要改几处？ | 1 处（配置文件） | 每一条用例里都有 |
| 加一条新用例，要写多少行？ | 5-10 行（调业务层方法） | 50 行（含请求、鉴权、断言、日志） |
| 前端改了个 id，要改几处？ | 1 处（页面类里） | 所有用到这个元素的用例 |

**第一遍学习重点掌握：分层架构的思想**。设计模式是工具，分层是骨架——先把骨架搞对。

!!! warning "先破除一个误区"
    框架不是越复杂越好。一个只有 30 条用例的项目，硬套"微服务架构 + 插件机制 + 数据工厂"，维护成本远高于收益。

    **框架复杂度应该匹配项目规模。** 本教程会标注每个实践的适用规模。

### 版本与维护说明

| 项目 | 说明 |
|------|------|
| 适用范围 | Python + Pytest 技术栈为主，设计思想可迁移到 Java + TestNG、JS + Jest |
| 使用建议 | 不要照抄结构，按你的项目规模选取需要的部分 |
| 更新提醒 | Pytest、Playwright、Requests 的 API 会随版本变化，具体用法请查阅官方文档 |

## 一、为什么需要框架设计

### 1.1 没有设计的脚本会长成什么样

```python
# 三个月前的第一条用例
def test_login():
    r = requests.post("http://test.example.com/api/login",
                      json={"user": "test01", "pwd": "123456"})
    assert r.status_code == 200
    assert r.json()["code"] == 0

# 三个月后，第 80 条用例
def test_create_order():
    # 又写了一遍登录，地址还写错了环境
    r1 = requests.post("http://test.example.com/api/login",
                       json={"user": "test01", "pwd": "123456"})
    token = r1.json()["data"]["token"]
    r2 = requests.post("http://test.example.com/api/order",
                       json={"sku": "1001", "num": 1},
                       headers={"Authorization": "Bearer " + token})
    assert r2.status_code == 200
    # 断言写得很松，业务码没校验
    assert r2.json()["code"] == 0
    # 没有日志，失败后不知道请求发的是什么
```

问题清单：

| 症状 | 后果 |
|------|------|
| 环境地址硬编码 | 切测试环境要全局搜索替换，容易漏 |
| 登录逻辑重复 | 登录接口一改，80 条用例全挂 |
| 无统一断言 | 有人断言状态码，有人断言业务码，标准不一 |
| 无日志 | 失败后无法定位是"请求发错了"还是"服务端有问题" |
| 用例之间耦合 | 只能按顺序跑，无法单独执行、无法并行 |

### 1.2 框架要解决的六件事

```text
1. 环境隔离     → 一套代码跑多个环境（dev/test/staging）
2. 认证复用     → 登录一次，处处可用；失效自动续期
3. 数据分离     → 测试数据不写在代码里
4. 断言统一     → 所有用例用同一套断言标准
5. 结果可读     → 失败时能一眼看出请求、响应、断言差异
6. 易于扩展     → 加用例、加模块不改动已有代码
```

!!! abstract "一句话总结框架的价值"
    **框架不是让测试跑起来，而是让测试跑得久。** 写出来能跑只值 20 分，半年后还能维护才是 100 分。

## 二、分层架构

这是框架设计的骨架，也是最该先搞对的部分。

### 2.1 五层结构

```text
┌─────────────────────────────────────────────┐
│  用例层 Test Cases                          │  只描述"测什么"
│  test_login.py / test_order.py              │
├─────────────────────────────────────────────┤
│  业务层 Business / Service                   │  封装"怎么操作"
│  login_service.py / order_service.py        │  一个方法 = 一个业务动作
├─────────────────────────────────────────────┤
│  页面/接口层 Page / API                      │  封装"单个页面或接口"
│  login_page.py / order_api.py               │  元素定位、请求参数
├─────────────────────────────────────────────┤
│  数据层 Data                                 │  提供测试数据
│  data/*.yaml, *.json, 数据构造函数            │
├─────────────────────────────────────────────┤
│  基础层 Base / Core                          │  与业务无关的通用能力
│  http_client.py / logger.py / assert_util.py │  请求封装、日志、断言、DB
└─────────────────────────────────────────────┘
```

### 2.2 各层职责与边界

| 层 | 该做什么 | 不该做什么 |
|----|----------|-----------|
| 用例层 | 组织测试步骤、断言业务结果 | 不写 HTTP 请求、不写 SQL、不写定位表达式 |
| 业务层 | 组合多个接口/页面完成一个业务动作 | 不写断言（断言属于用例层） |
| 页面/接口层 | 封装单个页面元素或单个接口调用 | 不组合业务逻辑 |
| 数据层 | 提供数据、管理数据文件 | 不包含业务判断 |
| 基础层 | 通用能力，与业务无关 | 不含任何业务语义 |

!!! warning "最常见的分层错误"
    **把断言写进业务层。** 业务层的职责是"执行动作"，不是"判断对错"。

    ```python
    # ❌ 错误：业务层里做断言
    def create_order(sku, num):
        r = api.post_order(sku, num)
        assert r["code"] == 0        # 断言不该在这里
        return r

    # ✅ 正确：业务层只返回结果
    def create_order(sku, num):
        return api.post_order(sku, num)
    ```

    为什么？因为不同用例对同一个动作的预期可能不同。比如"库存不足时下单"，你期望的就是**失败**。断言写在业务层，这条用例就没法写了。

### 2.3 对比：同一件事，两种写法

```python
# ❌ 无分层：用例层什么都干
def test_create_order_success():
    r1 = requests.post(BASE + "/api/login",
                       json={"user": "u1", "pwd": "p1"})
    token = r1.json()["data"]["token"]
    r2 = requests.post(BASE + "/api/order",
                       json={"sku": "1001", "num": 1},
                       headers={"Authorization": f"Bearer {token}"})
    assert r2.status_code == 200
    assert r2.json()["code"] == 0
```

```python
# ✅ 有分层：用例层只表达意图
def test_create_order_success():
    login_service.login_as("normal_user")          # 业务层
    resp = order_service.create_order(sku="1001", num=1)   # 业务层
    assert_util.assert_business_success(resp)      # 基础层
```

第二种写法，面试官一眼就知道你**真的搭过框架**——因为它体现了"关注点分离"。

## 四、核心层的设计要点

### 4.1 配置管理：环境隔离

**不要**在每个文件里写 `BASE_URL = "http://test..."`。

```yaml
# config/config.yaml
dev:
  base_url: "http://dev-api.example.com"
  db:
    host: "dev-mysql"
    port: 3306
    name: "test_db"

test:
  base_url: "http://test-api.example.com"
  db:
    host: "test-mysql"
    port: 3306
    name: "test_db"

staging:
  base_url: "http://staging-api.example.com"
```

```python
# config/settings.py
import os
import yaml

class Settings:
    def __init__(self, env: str | None = None):
        # 优先取命令行/环境变量，默认 dev
        self.env = env or os.getenv("TEST_ENV", "dev")
        path = os.path.join(os.path.dirname(__file__), "config.yaml")
        with open(path, encoding="utf-8") as f:
            self._cfg = yaml.safe_load(f)[self.env]

    @property
    def base_url(self) -> str:
        return self._cfg["base_url"]

    @property
    def db(self) -> dict:
        return self._cfg["db"]

settings = Settings()
```

**切换环境只需一条命令：**

```bash
TEST_ENV=staging pytest testcases/       # Linux/macOS
$env:TEST_ENV="staging"; pytest testcases/   # PowerShell
pytest testcases/ --env=staging          # 或用 pytest 自定义参数
```

!!! tip "敏感信息不要进配置文件"
    数据库密码、测试账号密码不要明文写在 `config.yaml` 并提交到 Git。正确做法：

    ```python
    # 从环境变量或密钥管理服务读取
    db_password = os.getenv("DB_PASSWORD")
    ```

    如果团队规模小、实在要用配置文件，至少做到：
    1. 把 `config.local.yaml` 加入 `.gitignore`
    2. 提交一份 `config.example.yaml` 作为模板
    3. CI 里通过环境变量/Secrets 注入

### 4.2 请求封装：一个类解决四个问题

```python
# core/http_client.py
import logging
import time
import requests

logger = logging.getLogger(__name__)

class HttpClient:
    """统一请求封装：日志、重试、Token 注入、统一解析"""

    def __init__(self, base_url: str, timeout: int = 10, retries: int = 2):
        self.base_url = base_url.rstrip("/")
        self.timeout = timeout
        self.retries = retries
        self.session = requests.Session()
        self._token: str | None = None

    def set_token(self, token: str):
        self._token = token

    def _headers(self, extra: dict | None = None) -> dict:
        headers = {"Content-Type": "application/json"}
        if self._token:
            headers["Authorization"] = f"Bearer {self._token}"
        if extra:
            headers.update(extra)
        return headers

    def request(self, method: str, path: str, **kwargs) -> requests.Response:
        url = f"{self.base_url}/{path.lstrip('/')}"
        kwargs.setdefault("timeout", self.timeout)
        kwargs["headers"] = self._headers(kwargs.pop("headers", None))

        last_exc = None
        for attempt in range(1, self.retries + 1):
            try:
                logger.info("→ %s %s | body=%s", method.upper(), url,
                            kwargs.get("json") or kwargs.get("params"))
                start = time.time()
                resp = self.session.request(method, url, **kwargs)
                cost = (time.time() - start) * 1000
                logger.info("← %s | %d | %.0fms | %s", url, resp.status_code,
                            cost, resp.text[:500])
                return resp
            except (requests.ConnectionError, requests.Timeout) as e:
                last_exc = e
                logger.warning("请求失败（第 %d 次）：%s", attempt, e)
                time.sleep(1)

        raise RuntimeError(f"请求重试 {self.retries} 次仍失败：{last_exc}")

    # 便捷方法
    def get(self, path, **kw):
        return self.request("GET", path, **kw)

    def post(self, path, **kw):
        return self.request("POST", path, **kw)
```

**这个类一次性解决了：**

| 问题 | 解决方式 |
|------|----------|
| 环境地址硬编码 | `base_url` 从配置注入 |
| 请求无日志 | 发请求和响应都打印（含耗时） |
| Token 手动传 | `set_token()` 后自动注入所有请求 |
| 网络抖动导致失败 | 自动重试 |
| 连接未复用 | 用 `requests.Session()` 复用连接 |

### 4.3 统一断言：让失败信息自己说话

```python
# core/assert_util.py
class BusinessAssert:
    """统一断言：失败时输出完整上下文，而不是干巴巴的 assert"""

    @staticmethod
    def assert_business_success(resp: requests.Response):
        body = resp.json()
        assert resp.status_code == 200, (
            f"HTTP 状态码错误：期望 200，实际 {resp.status_code}\n"
            f"响应体：{body}"
        )
        assert body.get("code") == 0, (
            f"业务码错误：期望 0，实际 {body.get('code')}\n"
            f"错误信息：{body.get('message')}\n"
            f"完整响应：{body}"
        )

    @staticmethod
    def assert_field(resp, field: str, expected):
        actual = resp.json().get("data", {}).get(field)
        assert actual == expected, (
            f"字段 {field} 不匹配：期望 {expected!r}，实际 {actual!r}\n"
            f"完整响应：{resp.json()}"
        )
```

!!! tip "为什么断言信息值得专门设计"
    ```
    ❌ 默认断言的报错：
    AssertionError: assert 1 == 0

    ✅ 设计后的报错：
    AssertionError: 业务码错误：期望 0，实际 1
    错误信息：库存不足
    完整响应：{'code': 1, 'message': '库存不足', 'data': None}
    ```

    第三条让你**不用复现就知道原因**。在 CI 里跑失败时，这个差别意味着"看一眼就知道"和"本地重跑一遍"。

### 4.4 会话级 Token 管理

不要每条用例都登录一次（慢且浪费），也不要写死 token（会过期）。

```python
# conftest.py
import pytest
from config.settings import settings
from core.http_client import HttpClient
from service.login_service import LoginService

@pytest.fixture(scope="session")
def client():
    """全局唯一的 HTTP 客户端，整个测试会话复用"""
    return HttpClient(settings.base_url)

@pytest.fixture(scope="session", autouse=True)
def auth(client):
    """会话级登录：整个测试只登录一次"""
    token = LoginService(client).login("normal_user", "pwd123")
    client.set_token(token)
    return token
```

**处理 Token 过期（真实项目一定会遇到）：**

```python
class LoginService:
    def __init__(self, client):
        self.client = client

    def login(self, user: str, pwd: str) -> str:
        resp = self.client.post("/api/login", json={"user": user, "pwd": pwd})
        return resp.json()["data"]["token"]

    def ensure_valid(self, resp):
        """检测到鉴权失效时自动重新登录并重放请求"""
        if resp.status_code == 401:
            token = self.login("normal_user", "pwd123")
            self.client.set_token(token)
            return True
        return False
```

!!! warning "Token 过期是用例批量失败的头号原因"
    批量运行时，跑到第 300 条 token 过期了，后面几十条全挂——这不是发现了缺陷，是**框架缺陷**。

    面试时把这一点讲出来（"我遇到过 token 过期导致用例批量失败，后来做了会话管理和自动续期"），是很有说服力的实战细节。

## 五、设计模式在测试中的应用

!!! abstract "先说清楚：不要为了用模式而用模式"
    下面每个模式都对应一个**真实的痛点**。如果项目里没有这个痛点，就不要引入——过度设计比不设计更难维护。

### 5.1 Page Object（PO）模式

**解决的问题**：前端改一个元素 id，所有用到它的用例都要改。

```python
# pages/base_page.py
class BasePage:
    def __init__(self, page):
        self.page = page

    def click(self, locator: str):
        self.page.click(locator)

    def fill(self, locator: str, text: str):
        self.page.fill(locator, text)

    def text_of(self, locator: str) -> str:
        return self.page.inner_text(locator)
```

```python
# pages/login_page.py
from pages.base_page import BasePage

class LoginPage(BasePage):
    # 定位表达式集中管理，只在这里出现一次
    USER_INPUT = "#username"
    PWD_INPUT = "#password"
    SUBMIT_BTN = "button[type=submit]"
    ERROR_MSG = ".error-tip"

    def open(self):
        self.page.goto("https://example.com/login")
        return self

    def login_as(self, user: str, pwd: str):
        self.fill(self.USER_INPUT, user)
        self.fill(self.PWD_INPUT, pwd)
        self.click(self.SUBMIT_BTN)
        return self

    def error_text(self) -> str:
        return self.text_of(self.ERROR_MSG)
```

```python
# 用例层：只表达业务意图，不出现任何定位表达式
def test_login_wrong_password(page):
    LoginPage(page).open().login_as("u1", "wrong_pwd")
    assert "密码错误" in LoginPage(page).error_text()
```

**收益**：前端把 `#username` 改成 `#user-name`，只改 `LoginPage` 一处。

### 5.2 工厂模式（Factory）

**解决的问题**：需要按类型创建不同的页面对象或测试数据。

```python
# pages/page_factory.py
from pages.login_page import LoginPage
from pages.order_page import OrderPage

class PageFactory:
    _registry = {
        "login": LoginPage,
        "order": OrderPage,
    }

    @classmethod
    def get(cls, name: str, page):
        if name not in cls._registry:
            raise ValueError(f"未注册的页面：{name}")
        return cls._registry[name](page)
```

**更常见的用法是测试数据工厂：**

```python
# data/order_factory.py
import random
import time

class OrderFactory:
    """按场景构造测试数据，避免用例里散落随机数据逻辑"""

    @staticmethod
    def normal_order(sku: str = "1001", num: int = 1) -> dict:
        return {"sku": sku, "num": num,
                "trade_no": f"TEST{int(time.time()*1000)}{random.randint(100,999)}"}

    @staticmethod
    def over_stock_order(sku: str = "1001") -> dict:
        """超库存场景：数量取一个极大值"""
        return {"sku": sku, "num": 99999,
                "trade_no": f"TEST{int(time.time()*1000)}"}

    @staticmethod
    def forbidden_order() -> dict:
        """非法参数场景"""
        return {"sku": "", "num": -1, "trade_no": ""}
```

```python
# 用例层：数据构造意图清晰
def test_over_stock(order_service):
    resp = order_service.create_order(**OrderFactory.over_stock_order())
    BusinessAssert.assert_business_fail(resp, code=1001)
```

### 5.3 单例模式（Singleton）

**解决的问题**：全局唯一的配置、客户端、数据库连接，避免重复创建。

```python
# core/db_client.py
class DBClient:
    _instance = None

    def __new__(cls, *args, **kwargs):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._init_conn()
        return cls._instance

    def _init_conn(self):
        import pymysql
        from config.settings import settings
        db = settings.db
        self.conn = pymysql.connect(host=db["host"], port=db["port"],
                                    user=db["user"], password=db["password"],
                                    database=db["name"], charset="utf8mb4")

    def query(self, sql: str):
        with self.conn.cursor() as cur:
            cur.execute(sql)
            return cur.fetchall()
```

!!! tip "Python 里更推荐的做法"
    单例在 Python 中不一定要用 `__new__`。**用 Pytest fixture（`scope="session"`）更符合 Python 习惯**，既实现了"全局唯一"，又不用手写单例：

    ```python
    @pytest.fixture(scope="session")
    def db():
        client = DBClient(settings.db)
        yield client
        client.close()
    ```

    面试时说明这个取舍，比机械套用单例模式更能体现你的判断力。

### 5.4 建造者模式（Builder）

**解决的问题**：构造一个字段很多、只有少数变动的请求对象。

```python
# data/order_builder.py
class OrderBuilder:
    def __init__(self):
        self._data = {
            "sku": "1001", "num": 1, "coupon": None,
            "address_id": 1, "pay_type": "alipay",
        }

    def sku(self, v):        self._data["sku"] = v; return self
    def num(self, v):        self._data["num"] = v; return self
    def with_coupon(self, v): self._data["coupon"] = v; return self
    def pay_by(self, v):     self._data["pay_type"] = v; return self
    def build(self):         return dict(self._data)
```

```python
# 用例层：一眼看出这条用例和默认值的差异
def test_order_with_coupon(order_service):
    payload = (OrderBuilder().num(2).with_coupon("CUT20").build())
    resp = order_service.create_order(**payload)
    BusinessAssert.assert_business_success(resp)
```

**收益**：链式调用让"这条用例改了什么"变得极其明显，比写一个 20 字段的字典清晰得多。

### 5.5 策略模式（Strategy）

**解决的问题**：同一个动作有多种实现，运行时按需切换。

```python
# core/auth_strategy.py
class TokenAuth:
    def apply(self, headers: dict, credential: str):
        headers["Authorization"] = f"Bearer {credential}"

class CookieAuth:
    def apply(self, headers: dict, credential: str):
        headers["Cookie"] = credential

class ApiKeyAuth:
    def apply(self, headers: dict, credential: str):
        headers["X-API-Key"] = credential

# 使用：按接口文档选择鉴权方式
AUTH_STRATEGIES = {"token": TokenAuth(), "cookie": CookieAuth(), "apikey": ApiKeyAuth()}
```

!!! tip "在自动化里最实用的场景"
    **多端自动化**：同一套业务流程，在 Web / App / API 三个端各有实现。

    ```python
    class RegisterFlow:
        def __init__(self, driver):   # driver 是 WebDriver / AppiumDriver / ApiDriver
            self.driver = driver
        def run(self): self.driver.register(...)
    ```

    用例层不变，只换 driver——这就是策略模式的应用。

## 六、数据驱动设计

### 6.1 为什么数据要外置

```python
# ❌ 数据写在代码里
def test_login():
    for user, pwd, expect in [
        ("u1", "p1", 0),
        ("u1", "wrong", 1002),
        ("", "p1", 1003),
    ]:
        ...
```

问题：加一条用例要改代码、要跑全量、非技术人员无法维护。

```yaml
# data/login_data.yaml
- case_name: "正常登录"
  user: "normal_user"
  pwd: "pwd123"
  expect_code: 0
- case_name: "密码错误"
  user: "normal_user"
  pwd: "wrong_pwd"
  expect_code: 1002
- case_name: "用户名为空"
  user: ""
  pwd: "pwd123"
  expect_code: 1003
```

```python
# 用例层：一个函数覆盖所有数据行
import pytest
import yaml
from pathlib import Path

def load_cases(file: str) -> list:
    path = Path(__file__).parent.parent / "data" / file
    with open(path, encoding="utf-8") as f:
        return yaml.safe_load(f)

@pytest.mark.parametrize("case", load_cases("login_data.yaml"),
                         ids=lambda c: c["case_name"])
def test_login(client, case):
    resp = client.post("/api/login",
                       json={"user": case["user"], "pwd": case["pwd"]})
    BusinessAssert.assert_code(resp, case["expect_code"])
```

!!! tip "`ids=lambda c: c["case_name"]` 这个小技巧很值钱"
    不加 `ids`，报告里显示的是 `test_login[case0]`、`test_login[case1]`；
    加了之后显示 `test_login[正常登录]`、`test_login[密码错误]`。

    **报告可读性直接影响你排查失败的速度**，也是面试时能体现细节意识的地方。

### 6.2 数据分层的三级策略

这是解决"用例不稳定"的核心方法：

| 层级 | 数据 | 特点 | 例子 |
|------|------|------|------|
| L1 基础数据 | 环境初始化时写死的 | 长期不变，所有用例共享 | 商品、分类、基础配置 |
| L2 运行时数据 | 用例执行前创建、执行后清理 | 保证每条用例独立 | 下单用的优惠券、地址 |
| L3 只读数据 | 绝不修改 | 只能查 | 字典表、配置表 |

```python
# L2：用例级数据准备与清理
@pytest.fixture
def temp_coupon(db):
    """为当前用例创建一个专属优惠券，用完删除"""
    coupon_id = db.insert("INSERT INTO coupon(code, amount) VALUES('TEST_CUT20', 20)")
    yield "TEST_CUT20"
    db.execute("DELETE FROM coupon WHERE id = %s", coupon_id)
```

!!! warning "为什么"用例不能互相依赖""
    ```
    ❌ 用例 A 创建订单，用例 B 去查这个订单
    → A 失败则 B 也失败（误报）；B 无法单独跑；无法并行执行

    ✅ 每条用例自己准备数据、自己清理
    → 可单独跑、可并行、失败一定是真问题
    ```

    面试问"自动化用例不稳定怎么优化"，这就是标准答案之一。

## 七、可维护性优化

### 7.1 常见的六个维护痛点与解法

| 痛点 | 根本原因 | 解法 |
|------|----------|------|
| 环境切换要改很多处 | 配置硬编码 | 配置层 + 环境变量 |
| 登录接口一改全挂 | 登录逻辑重复 | 业务层封装 + 会话级 fixture |
| 前端改 id 全挂 | 定位散落 | PO 模式，定位集中 |
| 失败看不出原因 | 无日志/断言信息弱 | 请求日志 + 带上下文的断言 |
| 用例互相影响 | 数据共享、顺序依赖 | 数据分层 + 用例级 fixture |
| 跑得太慢 | 串行执行、重复登录 | 会话复用 + 并行执行 |

### 7.2 并行执行

```ini
# pytest.ini
[pytest]
addopts = -v --tb=short
markers =
    smoke: 冒烟测试
    regression: 回归测试
```

```bash
# 安装 pytest-xdist，4 个进程并行
pip install pytest-xdist
pytest testcases/ -n 4
```

!!! warning "并行的前提是用例无状态"
    如果用例之间共享数据、有先后依赖，并行跑必然失败。
    **先把数据隔离做好，再上并行**——顺序不能反。

### 7.3 失败重试的正确姿势

```bash
pip install pytest-rerunfailures
pytest testcases/ --reruns 2 --reruns-delay 1
```

!!! danger "重试是把双刃剑"
    ```
    ✅ 合理用途：区分"环境抖动"和"真实缺陷"
    ❌ 危险用途：掩盖真实的并发/时序缺陷
    ```

    一个"5 次中 2 次失败"的用例，重试 2 次后可能通过——但这**恰恰说明系统存在竞态条件**，是真实缺陷。

    **正确做法**：重试通过后要有标记和统计。如果一个用例长期靠重试通过，必须单独分析，不能当作正常。

### 7.4 框架的自我测试

!!! abstract "一个容易被忽略但很加分的点"
    框架本身也是代码，也会出错。可以做基础的"框架自检"：

    ```python
    def test_framework_can_reach_env(client):
        """环境连通性自检：跑用例前先确认环境可达"""
        resp = client.get("/api/health")
        assert resp.status_code == 200, "测试环境不可达，请先检查环境"

    def test_framework_assert_util_works():
        """自检断言工具本身的行为正确"""
        ...
    ```

    在 CI 里把自检放在最前面——**环境问题一眼定位，不用怀疑脚本**。

## 八、面试怎么讲框架设计

框架设计是自动化岗和测试开发岗的**必问题**，也是最能拉开差距的题。

### 8.1 回答框架

```text
1. 先说背景和约束
   "项目有 30+ 接口，回归频率是每天一次，团队 3 个测试同学维护"

2. 说分层
   "分了五层：用例层、业务层、接口层、数据层、基础层，
    用例层只表达业务意图，不出现请求细节"

3. 说关键设计（挑 2-3 个讲透，不要面面俱到）
   "基础层封了统一的 HttpClient，解决了三个问题：
    环境隔离靠配置注入、Token 靠会话级管理自动续期、
    网络抖动靠自动重试"

4. 说数据策略
   "数据分三级：基础数据环境初始化、用例级数据用 fixture
    创建和清理、只读数据不修改"

5. 说收益（用数字）
   "新增用例从 50 行降到 10 行左右，冗余代码降低 40%；
    回归时间从手工 2 小时压缩到 8 分钟"

6. 说不足和改进
   "目前的不足是还没有做用例级的用例选择机制，
    回归全量跑较慢，下一步想按代码变更范围做智能回归"
```

!!! tip "最后一句话是加分项"
    **主动说不足**，体现的不是缺点，而是你的判断力和技术视野。面试官最怕的是"觉得自己的实现完美"的人。

### 8.2 高频追问及应对

| 追问 | 回答要点 |
|------|----------|
| 为什么这么分层？ | 关注点分离：改环境不影响用例，改页面不影响业务 |
| 断言为什么不在业务层？ | 同一动作在不同用例预期不同（如库存不足时下单期望失败） |
| 用例不稳定怎么排查？ | 先看是脚本问题/数据问题/环境问题/真实缺陷，四类归因 |
| 覆盖率多少？ | 说具体比例和范围，**绝不说 100%** |
| 怎么降低维护成本？ | 分层 + PO + 数据外置 + 断言上下文 + 定期清理低价值用例 |
| 怎么和 CI 集成？ | 提交触发、失败通知、报告归档、并行执行缩短时间 |
| 有没有设计模式的应用？ | 举 1-2 个真实的，说明解决了什么痛点（不要罗列） |

## 九、动手任务：重构一个脚本集为分层框架

### 任务背景

下面是一个"能用但难维护"的接口测试脚本集。请把它重构成分层框架。

```python
# 现有脚本（痛点：环境硬编码、登录重复、无日志、断言弱）
import requests

def test_login_ok():
    r = requests.post("http://test-api.example.com/api/login",
                      json={"user": "u1", "pwd": "p1"})
    assert r.json()["code"] == 0

def test_order_ok():
    r1 = requests.post("http://test-api.example.com/api/login",
                       json={"user": "u1", "pwd": "p1"})
    token = r1.json()["data"]["token"]
    r2 = requests.post("http://test-api.example.com/api/order",
                       json={"sku": "1001", "num": 1},
                       headers={"Authorization": "Bearer " + token})
    assert r2.json()["code"] == 0

def test_order_over_stock():
    r1 = requests.post("http://test-api.example.com/api/login",
                       json={"user": "u1", "pwd": "p1"})
    token = r1.json()["data"]["token"]
    r2 = requests.post("http://test-api.example.com/api/order",
                       json={"sku": "1001", "num": 99999},
                       headers={"Authorization": "Bearer " + token})
    assert r2.json()["code"] == 1001
```

### 任务要求

1. **分层重构**：按"配置层 / 基础层 / 接口层 / 业务层 / 用例层"拆分，每个文件的职责写在文件头部注释里
2. **环境隔离**：支持 `dev` / `test` 两个环境，通过环境变量切换，地址不出现在代码中
3. **消除重复**：登录只做一次（会话级 fixture），且支持 token 失效自动续期
4. **统一断言**：断言失败时输出业务码、错误信息和完整响应
5. **加日志**：每次请求打印方法、URL、请求体、响应码、耗时
6. **数据外置**：把下单场景的数据放到 YAML，用 `parametrize` 驱动，并让报告显示中文用例名
7. **数据隔离**：为下单用例准备独立的测试数据（可用 fixture 模拟创建与清理）

### 提交物

| 产出 | 说明 |
|------|------|
| 目录结构 | 树形展示，含每个文件的职责说明 |
| 关键代码 | 至少包含 `http_client.py`、`config.yaml`、`conftest.py`、一个用例文件 |
| 对比说明 | 用表格说明重构前后"改环境""加用例""改字段"的成本差异 |
| 500 字说明 | 讲清你的分层理由，以及你认为当前的不足 |

### 完成标准

- [ ] 用例层不出现任何 URL、headers、requests 调用
- [ ] 切换环境不需要修改任何测试代码
- [ ] 登录逻辑只在一处实现，且能自动续期
- [ ] 断言失败信息包含完整上下文，不看日志也能定位
- [ ] 数据在 YAML 中，报告显示中文用例名
- [ ] 能说清每一层的边界，特别是"断言为什么不在业务层"
- [ ] 主动指出了至少 1 个当前方案的不足

## 附录：速查表

### 五层职责

```text
用例层    只表达"测什么"（组织步骤、断言结果）
业务层    封装"怎么操作"（一个方法 = 一个业务动作，不做断言）
接口层    封装"单个接口/页面"（请求参数、元素定位）
数据层    提供测试数据（YAML/JSON/工厂函数）
基础层    通用能力（请求、日志、断言、数据库），与业务无关
```

### 设计模式适用场景

```text
Page Object   前端元素定位集中管理          → 所有 UI 自动化
Factory       按类型创建对象/构造测试数据    → 多场景数据
Singleton     全局唯一资源（配置/连接）      → 优先用 fixture 替代
Builder       字段多、只改少数几个           → 复杂请求体
Strategy      同一动作多种实现               → 多端自动化、多种鉴权
```

### 数据三级分层

```text
L1 基础数据    环境初始化写死，长期不变，共享
L2 运行时数据  用例级 fixture 创建 + 清理，保证独立
L3 只读数据    绝不修改，只查
```

### 维护成本对照

```text
改环境   1 处（配置）       vs  每条用例里都有
加用例   5-10 行（调业务层） vs  50 行（全流程手写）
改定位   1 处（页面类）      vs  所有相关用例
```
