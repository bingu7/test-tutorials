## 选择题

<div class="quiz-container" data-quiz-id="mobile-testing">

<div class="quiz-item" data-correct="2">
<div class="quiz-question">相比 Web 测试，移动端测试特有的关注点是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q1" value="0"> 需要验证页面元素的正确性</label>
<label class="quiz-option"><input type="radio" name="q1" value="1"> 需要验证接口返回的数据</label>
<label class="quiz-option"><input type="radio" name="q1" value="2"> 设备碎片化、网络环境多变、系统权限、安装升级与推送</label>
<label class="quiz-option"><input type="radio" name="q1" value="3"> 需要验证用户登录功能</label>
</div>
<div class="quiz-explanation">💡 移动端多出了几个 Web 没有的维度：几十种机型与系统版本、随时波动的网络、运行时会动态询问的系统权限、覆盖安装与卸载重装、以及依赖厂商通道的推送。这些恰恰是缺陷最集中的地方</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">想模拟"2G 弱网"环境测试 App 的表现，常用做法是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q2" value="0"> 把手机放进电梯或地下室等信号差的场所</label>
<label class="quiz-option"><input type="radio" name="q2" value="1"> 用 Charles / Fiddler 的网络限制（Throttling）功能设置带宽、延迟和丢包率</label>
<label class="quiz-option"><input type="radio" name="q2" value="2"> 关闭 App 的缓存功能后重新测试</label>
<label class="quiz-option"><input type="radio" name="q2" value="3"> 降低手机屏幕亮度以模拟低性能状态</label>
</div>
<div class="quiz-explanation">💡 真实弱网不可复现、无法量化，所以要用代理工具人为构造：设定带宽（如 50-100 kbps）、延迟（300-500ms）和丢包率。这样才能稳定复现问题、也能横向对比不同版本的表现</div>
</div>

<div class="quiz-item" data-correct="3">
<div class="quiz-question">下列哪一项是弱网环境下<strong>最典型</strong>的缺陷？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q3" value="0"> 页面配色在不同机型上不一致</label>
<label class="quiz-option"><input type="radio" name="q3" value="1"> 应用图标在低分辨率屏幕上模糊</label>
<label class="quiz-option"><input type="radio" name="q3" value="2"> 后台待机时流量持续消耗</label>
<label class="quiz-option"><input type="radio" name="q3" value="3"> 请求超时后无任何提示，用户重复点击导致重复下单</label>
</div>
<div class="quiz-explanation">💡 弱网会同时暴露两类问题：反馈缺失（转圈不停、白屏、没有网络异常提示）和幂等性缺陷（重复提交、重复下单、重复扣款）。后者风险最高，通常需要在需求阶段就确认防重方案</div>
</div>

<div class="quiz-item" data-correct="0">
<div class="quiz-question">测试"断网恢复"场景时，重点要验证什么？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q4" value="0"> 网络恢复后数据能否正确同步、操作是否可以重试且不重复</label>
<label class="quiz-option"><input type="radio" name="q4" value="1"> 断网时 App 是否直接退出</label>
<label class="quiz-option"><input type="radio" name="q4" value="2"> 断网时是否能继续使用所有在线功能</label>
<label class="quiz-option"><input type="radio" name="q4" value="3"> 断网后是否需要重新安装 App</label>
</div>
<div class="quiz-explanation">💡 断网恢复是移动端最容易出数据问题的路径：本地缓存的草稿能否补传、提交中断的订单状态是否一致、会不会重复发送。测的时候要"断网 → 操作 → 恢复 → 核对数据"完整走一遍</div>
</div>

<div class="quiz-item" data-correct="2">
<div class="quiz-question">设计移动端兼容性测试矩阵，比较合理的思路是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q5" value="0"> 把所有在售机型都买回来逐台测试</label>
<label class="quiz-option"><input type="radio" name="q5" value="1"> 只测试最新的旗舰机型，保证性能体验</label>
<label class="quiz-option"><input type="radio" name="q5" value="2"> 结合用户市场占有率、系统版本分布和分辨率，选取有代表性的机型组合</label>
<label class="quiz-option"><input type="radio" name="q5" value="3"> 随便挑两款手机，主要靠开发自测</label>
</div>
<div class="quiz-explanation">💡 机型无穷无尽，但用户分布是集中的。按后台统计的市场占有率和系统版本占比选主流机型，再用少量低端机覆盖性能下限、用高分辨率机型覆盖 UI 适配，才是在有限成本下覆盖最多风险的方案</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">关于真机测试与云测平台的选择，下列说法正确的是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q6" value="0"> 云测平台可以完全替代真机，不需要再买设备</label>
<label class="quiz-option"><input type="radio" name="q6" value="1"> 云测适合覆盖大量机型做批量回归，真机适合排查需要真实交互的问题</label>
<label class="quiz-option"><input type="radio" name="q6" value="2"> 云测平台的测试结果一定比真机准确</label>
<label class="quiz-option"><input type="radio" name="q6" value="3"> 真机测试只能做手工测试，无法跑自动化脚本</label>
</div>
<div class="quiz-explanation">💡 云测的优势是机型多、成本低、适合批量跑兼容性回归；但音频、摄像头、传感器、震动、发热、真实网络切换等场景，云测很难真实还原，需要真机补位。两者是配合关系</div>
</div>

<div class="quiz-item" data-correct="3">
<div class="quiz-question">Android 上出现 ANR 的典型原因是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q7" value="0"> 手机电量低于 20%</label>
<label class="quiz-option"><input type="radio" name="q7" value="1"> 应用被用户手动切换到后台</label>
<label class="quiz-option"><input type="radio" name="q7" value="2"> 图片分辨率过高导致内存不足</label>
<label class="quiz-option"><input type="radio" name="q7" value="3"> 主线程被耗时操作阻塞，长时间无响应</label>
</div>
<div class="quiz-explanation">💡 ANR = Application Not Responding，本质是主线程（UI 线程）被网络请求、大文件读写、复杂计算等耗时操作卡住。图片过多导致内存不足属于 OOM，是另一类问题</div>
</div>

<div class="quiz-item" data-correct="0">
<div class="quiz-question">移动端测试"后台待机流量"，合理的预期是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q8" value="0"> 静置一段时间后后台流量应接近 0，持续消耗通常意味着异常上报或轮询</label>
<label class="quiz-option"><input type="radio" name="q8" value="1"> 后台驻留时持续产生流量是正常现象</label>
<label class="quiz-option"><input type="radio" name="q8" value="2"> 后台流量无法通过工具测量</label>
<label class="quiz-option"><input type="radio" name="q8" value="3"> 只要不影响前台使用就不必关注</label>
</div>
<div class="quiz-explanation">💡 用户对"偷跑流量"非常敏感，这类问题常常直接变成投诉和差评。测试时把 App 切到后台静置一段时间，再观察流量增量，就能发现无节制的轮询、心跳过密或日志上报过多</div>
</div>

<div class="quiz-item" data-correct="2">
<div class="quiz-question">获取 Android 崩溃日志，最常用的方式是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q9" value="0"> 让开发重新编译一个带日志的版本</label>
<label class="quiz-option"><input type="radio" name="q9" value="1"> 截图崩溃弹窗即可，不需要日志</label>
<label class="quiz-option"><input type="radio" name="q9" value="2"> 通过 adb logcat 抓取，或从崩溃收集平台按设备与时间查找</label>
<label class="quiz-option"><input type="radio" name="q9" value="3"> 重启手机后系统会自动保存崩溃原因</label>
</div>
<div class="quiz-explanation">💡 崩溃日志里的异常类型和堆栈是开发定位问题的关键线索，直接决定这个缺陷能不能被快速修掉。缺陷报告里带上崩溃时间点和设备信息，能让开发在崩溃平台上精准捞到那条记录</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">覆盖升级（在旧版本基础上装新版本）测试，最需要关注的是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q10" value="0"> 安装包体积是否变小</label>
<label class="quiz-option"><input type="radio" name="q10" value="1"> 原有用户数据是否保留、登录态是否正常、本地数据库能否平滑迁移</label>
<label class="quiz-option"><input type="radio" name="q10" value="2"> 升级后图标是否更换</label>
<label class="quiz-option"><input type="radio" name="q10" value="3"> 升级提示文案是否美观</label>
</div>
<div class="quiz-explanation">💡 全新安装永远是最干净的路径，最容易出问题的是"带着历史数据升级"：本地库表结构变更、缓存格式不兼容、旧 token 失效。测的时候要先在旧版本造好数据，再覆盖安装验证数据完整性</div>
</div>

<div class="quiz-item" data-correct="3">
<div class="quiz-question">推送通知测试需要覆盖的场景中，下列哪项<strong>不属于</strong>重点？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q11" value="0"> 推送到达率与延迟</label>
<label class="quiz-option"><input type="radio" name="q11" value="1"> 点击推送后能否正确跳转到目标页面</label>
<label class="quiz-option"><input type="radio" name="q11" value="2"> 免打扰模式下、通知权限被关闭时的表现</label>
<label class="quiz-option"><input type="radio" name="q11" value="3"> 推送文案的字数统计是否符合运营规范</label>
</div>
<div class="quiz-explanation">💡 推送的核心风险在"送不到"和"点错地方"：不同厂商通道的到达率差异很大，App 在前台/后台/被杀进程时点击跳转行为也不同。文案字数属于运营侧规范，不是技术测试重点</div>
</div>

<div class="quiz-item" data-correct="0">
<div class="quiz-question">测试系统权限时，除了"允许"和"拒绝"，还必须覆盖哪种情况？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q12" value="0"> 永久拒绝后在设置中重新开启，以及"仅本次允许"这类临时授权</label>
<label class="quiz-option"><input type="radio" name="q12" value="1"> 用户从不点击任何权限弹窗</label>
<label class="quiz-option"><input type="radio" name="q12" value="2"> 用户连续点击弹窗十次</label>
<label class="quiz-option"><input type="radio" name="q12" value="3"> 权限弹窗的字体大小是否合适</label>
</div>
<div class="quiz-explanation">💡 权限状态是有"记忆"的：拒绝一次可能只影响本次，拒绝两次可能变成永久拒绝且不再弹窗；"仅本次允许"在下一次启动时又会重新询问。这些状态组合最容易出现"功能静默失效却没有任何提示"的问题</div>
</div>
