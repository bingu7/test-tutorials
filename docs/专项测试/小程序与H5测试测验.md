## 选择题

<div class="quiz-container" data-quiz-id="miniprogram-h5">

<div class="quiz-item" data-correct="2">
<div class="quiz-question">小程序上线前，必须执行的一项检查是"关闭开发者工具里的『不校验合法域名』选项后再跑一遍"。原因是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q1" value="0"> 关闭后运行速度更接近线上环境</label>
<label class="quiz-option"><input type="radio" name="q1" value="1"> 开启时会自动屏蔽部分网络请求</label>
<label class="quiz-option"><input type="radio" name="q1" value="2"> 开启时工具会跳过域名白名单校验，导致新域名漏配、http 接口等线上必现问题在测试阶段被掩盖</label>
<label class="quiz-option"><input type="radio" name="q1" value="3"> 关闭后才能使用真机调试</label>
</div>
<div class="quiz-explanation">💡 这是小程序测试最经典的一类线上事故：测试环境一切正常，上线后请求全部失败——因为新接口的域名没加进微信后台白名单，或者误用了 http。体验版默认不校验域名，所以这个坑必须靠"手动关闭校验"主动暴露。这一条几乎每个小程序团队都踩过</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">用户在购物车页面提交订单成功后返回购物车，发现商品数量还是旧的。最可能的原因是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q2" value="0"> 接口返回数据错误</label>
<label class="quiz-option"><input type="radio" name="q2" value="1"> 数据加载逻辑写在了 onLoad 里，而返回页面时只触发 onShow，不触发 onLoad</label>
<label class="quiz-option"><input type="radio" name="q2" value="2"> 本地缓存未清理</label>
<label class="quiz-option"><input type="radio" name="q2" value="3"> 微信版本兼容性问题</label>
</div>
<div class="quiz-explanation">💡 `onLoad` 只在页面首次加载时执行一次，`onShow` 每次页面显示都会执行。从页面 B 返回页面 A 时，A 只触发 `onShow`——所以"数据要实时刷新"的逻辑必须放在 `onShow` 里，或返回时主动刷新。"在页面 A 操作后回到页面 B，B 的数据是否更新"是一条能覆盖大量缺陷的通用测试思路</div>
</div>

<div class="quiz-item" data-correct="3">
<div class="quiz-question">关于小程序登录链路中的 code，下列理解正确的是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q3" value="0"> code 可以长期保存，随时用来换 openid</label>
<label class="quiz-option"><input type="radio" name="q3" value="1"> code 由小程序服务端生成并下发给前端</label>
<label class="quiz-option"><input type="radio" name="q3" value="2"> 前端可以直接用 code 换到 openid</label>
<label class="quiz-option"><input type="radio" name="q3" value="3"> code 由 wx.login 获取、5 分钟有效、只能用一次，需由服务端配合 appid 和 secret 换取 openid</label>
</div>
<div class="quiz-explanation">💡 三个关键点：时效性（5 分钟）、一次性（重复使用应失败）、交换方必须是服务端（secret 不能放在前端，否则泄露）。测试时最有价值的一个动作是：抓包拿到 code，用工具重放一次，验证服务端是否正确拒绝了重复使用</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">测试小程序支付时，必须验证"支付回调幂等性"的核心原因是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q4" value="0"> 微信要求所有回调必须返回 200</label>
<label class="quiz-option"><input type="radio" name="q4" value="1"> 微信的支付通知会重复推送，若不幂等会导致重复扣款、重复发货等资损或业务事故</label>
<label class="quiz-option"><input type="radio" name="q4" value="2"> 幂等性能提升支付速度</label>
<label class="quiz-option"><input type="radio" name="q4" value="3"> 不幂等会导致页面样式错乱</label>
</div>
<div class="quiz-explanation">💡 微信的异步通知机制在超时或未收到正确应答时会重复推送。实际测试方法很直接：抓包获取支付回调请求，用工具重复发送多次，观察订单状态、库存和账务是否被重复处理。**这是资损级缺陷，优先级最高**</div>
</div>

<div class="quiz-item" data-correct="2">
<div class="quiz-question">小程序的页面栈最多可以有多少层？超过后应该怎么办？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q5" value="0"> 5 层，超过后只能关闭小程序</label>
<label class="quiz-option"><input type="radio" name="q5" value="1"> 15 层，超过后微信自动清理最早页面</label>
<label class="quiz-option"><input type="radio" name="q5" value="2"> 10 层，超过后无法再 navigateTo，需使用 redirectTo 或由业务层做兜底处理</label>
<label class="quiz-option"><input type="radio" name="q5" value="3"> 没有限制，可以无限跳转</label>
</div>
<div class="quiz-explanation">💡 10 层是小程序的硬限制。测试点是：连续跳转超过 10 层时会发生什么？业务是否有兜底？从深层页面能否正常返回？这属于平台约束测试，容易漏测但线上真实存在（例如商品详情→店铺→商品→店铺……反复跳转）</div>
</div>

<div class="quiz-item" data-correct="0">
<div class="quiz-question">页面上"实付金额"显示错误。要快速判断是前端渲染问题还是数据处理问题，最高效的工具是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q6" value="0"> AppData 面板——查看页面 data 中 payAmount 的值是否正确</label>
<label class="quiz-option"><input type="radio" name="q6" value="1"> Storage 面板——检查本地缓存</label>
<label class="quiz-option"><input type="radio" name="q6" value="2"> 只看截图，交给开发自己判断</label>
<label class="quiz-option"><input type="radio" name="q6" value="3"> 卸载重装小程序</label>
</div>
<div class="quiz-explanation">💡 AppData 面板实时显示页面 data 的真实值，能一步切开问题边界：**data 里的值正确但页面显示错 → WXML 绑定/渲染问题；data 本身的值就错 → 数据处理或接口问题**。缺陷报告里带上这个判断，开发无法打回，也体现了你的定位能力</div>
</div>

<div class="quiz-item" data-correct="3">
<div class="quiz-question">下列关于小程序运行时长的理解，正确的是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q7" value="0"> onReady 在 onLoad 之前执行</label>
<label class="quiz-option"><input type="radio" name="q7" value="1"> onUnload 表示页面被隐藏，数据仍保留</label>
<label class="quiz-option"><input type="radio" name="q7" value="2"> onHide 与 onShow 是一对，onUnload 与 onReady 是一对</label>
<label class="quiz-option"><input type="radio" name="q7" value="3"> onUnload 表示页面被销毁出栈，此时应清理定时器与监听，避免内存泄漏和 setData 报错</label>
</div>
<div class="quiz-explanation">💡 顺序是 `onLoad → onShow → onReady → onHide → onUnload`。`onHide` 只是页面隐藏（数据保留，可再次 onShow），`onUnload` 才是页面销毁。**页面销毁后如果还有异步回调或定时器在跑，就会触发 setData 报错或内存泄漏**——这是性能与稳定性测试的必查项</div>
</div>

<div class="quiz-item" data-correct="2">
<div class="quiz-question">小程序的同域名并发请求上限大约是多少？这与哪类缺陷直接相关？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q8" value="0"> 5 个；与页面样式错乱相关</label>
<label class="quiz-option"><input type="radio" name="q8" value="1"> 20 个；与本地缓存写入失败相关</label>
<label class="quiz-option"><input type="radio" name="q8" value="2"> 10 个；与首页同时发起过多请求导致部分模块空白相关</label>
<label class="quiz-option"><input type="radio" name="q8" value="3"> 没有限制</label>
</div>
<div class="quiz-explanation">💡 同域名并发上限约 10 个。典型场景是首页多个模块各自请求数据，一次性发出 12 个请求，超出上限的部分会排队或失败，表现为"页面某个模块空白"。测试思路：数一数首屏发出了多少个请求，并关注网络较慢时的表现</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">关于"模拟器测试通过"与"真机测试"的关系，正确的理解是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q9" value="0"> 模拟器能通过就不需要真机测试</label>
<label class="quiz-option"><input type="radio" name="q9" value="1"> 真机可能存在模拟器没有的问题，如布局错乱（刘海屏/分辨率）、支付无法在模拟器验证、权限弹窗、真实网络差异</label>
<label class="quiz-option"><input type="radio" name="q9" value="2"> 真机测试只是为了截图好看</label>
<label class="quiz-option"><input type="radio" name="q9" value="3"> 真机测试只在 iOS 上需要</label>
</div>
<div class="quiz-explanation">💡 最关键的一点：**微信支付在模拟器中无法完成**，必须在真机验证。此外刘海屏安全区域、系统字体、真实网络下的证书与代理问题、系统授权弹窗，都只有真机才能覆盖。核心流程与支付相关用例必须真机验证</div>
</div>

<div class="quiz-item" data-correct="3">
<div class="quiz-question">想验证"列表页性能问题"，下列哪种缺陷描述最有价值？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q10" value="0"> 列表页很卡，需要优化</label>
<label class="quiz-option"><input type="radio" name="q10" value="1"> 列表页加载慢，比别的页面慢</label>
<label class="quiz-option"><input type="radio" name="q10" value="2"> 列表页体验不好，用户可能不喜欢</label>
<label class="quiz-option"><input type="radio" name="q10" value="3"> iPhone 12 真机上冷启动首页可交互耗时 3.8s（标准 < 2s）；Performance 面板显示 setData 调用 6 次，其中一次传入 180 条商品数据耗时 900ms</label>
</div>
<div class="quiz-explanation">💡 性能缺陷的价值在于**可定位**。前三种描述开发只能回你"我再看看"；第四种直接指向了优化点（setData 数据量过大、应做分页或虚拟列表）。性能测试的产出必须是**数值 + 复现环境 + 耗时分布**，而不是形容词</div>
</div>

<div class="quiz-item" data-correct="0">
<div class="quiz-question">H5 页面发布新版本后，App 内的 WebView 仍显示旧页面。这类问题的测试要点是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q11" value="0"> 验证版本号机制与强制刷新机制是否生效，并覆盖"新 H5 + 旧 App / 旧 H5 + 新 App"的跨版本组合</label>
<label class="quiz-option"><input type="radio" name="q11" value="1"> 这不是测试问题，属于运维配置问题</label>
<label class="quiz-option"><input type="radio" name="q11" value="2"> 只需要卸载重装 App 即可，无需专门测试</label>
<label class="quiz-option"><input type="radio" name="q11" value="3"> 只要清除浏览器缓存就能解决</label>
</div>
<div class="quiz-explanation">💡 WebView 缓存导致的"H5 发版不生效"是混合开发的高频线上事故，因为缓存策略由原生端控制，H5 测不到。必须验证两点：**缓存版本号或时间戳机制**，以及**跨版本兼容**（用户不升级 App 的情况下能否正常使用新版 H5）。同类问题还有 JSBridge 方法改名导致的调用失败</div>
</div>

<div class="quiz-item" data-correct="2">
<div class="quiz-question">关于小程序 UI 自动化的务实策略，下列建议最合理的是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q12" value="0"> 用 Airtest 图像识别覆盖所有页面，实现 100% UI 自动化</label>
<label class="quiz-option"><input type="radio" name="q12" value="1"> 小程序不适合自动化，完全依赖手工</label>
<label class="quiz-option"><input type="radio" name="q12" value="2"> 优先做接口层自动化（业务逻辑大量在后端），UI 自动化只覆盖主要的一两条核心链路</label>
<label class="quiz-option"><input type="radio" name="q12" value="3"> 必须用 Appium 驱动微信，因为它是唯一稳定方案</label>
</div>
<div class="quiz-explanation">💡 小程序的业务逻辑大部分在后端接口，接口自动化**成本低、稳定、收益大**。UI 层变化频繁，用 miniprogram-automator 覆盖"登录→下单"这类核心链路即可。图像识别方案（Airtest）虽然跨端，但稳定性差、执行慢，不适合作为主力</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">用 miniprogram-automator 做断言时，为什么推荐断言 page.data() 而不是页面上的文本？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q13" value="0"> 因为 page.data() 执行速度更快</label>
<label class="quiz-option"><input type="radio" name="q13" value="1"> 因为断言数据状态更稳定——UI 文案改一个字用例就会失败，而数据状态直接反映真实业务逻辑</label>
<label class="quiz-option"><input type="radio" name="q13" value="2"> 因为文本断言在 Android 上不支持</label>
<label class="quiz-option"><input type="radio" name="q13" value="3"> 因为 page.data() 能自动修复失败的用例</label>
</div>
<div class="quiz-explanation">💡 这是自动化稳定性的通用原则：**断言越靠近数据层，越稳定**。页面文案调整（如"立即购买"改成"马上抢购"）不该导致用例失败，因为业务逻辑没变。同理由此延伸到接口自动化的原则——断言业务码和关键字段，而不是整段响应文本</div>
</div>
