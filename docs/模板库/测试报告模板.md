# 测试报告模板

测试报告的作用是帮助项目成员判断：这次测试做了什么、结果如何、还有哪些风险、是否建议上线。

## 报告结构

| 模块 | 内容 |
|------|------|
| 项目概述 | 本次测试对象、版本、时间、负责人 |
| 测试范围 | 已测试功能和未测试功能 |
| 测试环境 | 环境地址、浏览器、设备、数据库、构建版本 |
| 测试执行情况 | 用例总数、通过、失败、阻塞、未执行 |
| 缺陷统计 | 按严重程度、状态、模块统计 |
| 主要问题 | 影响较大的缺陷和处理结果 |
| 遗留风险 | 未修复问题、未覆盖范围、外部依赖 |
| 测试结论 | 是否通过、是否建议上线、上线条件 |

## 测试结论写法

| 结论 | 示例 |
|------|------|
| 通过 | 核心流程已验证通过，P0/P1 缺陷已关闭，建议按计划上线 |

```text
测试结论：有条件通过，建议产品确认遗留文案问题后上线。
```

## 结论写法对比

以下是测试结论的反面示例和正面示例，供参考。

### 反面示例（不推荐）

```text
测试通过，可以上线。
```

**问题：** 没有数据支撑，不清楚测了多少、覆盖率如何、有没有遗留问题。一旦上线后出问题，无法追溯测试结论的依据。

### 正面示例（推荐）

```text
本次测试执行用例 180 条，通过 168 条，通过率 93.3%。发现缺陷 18 个，
Critical 2 个已全部修复并回归通过，Major 5 个已修复 4 个（剩余 1 个预计
2026-06-08 回归完成）。遗留 Minor/Suggestion 缺陷 4 个，不影响核心交易
流程。测试结论：有条件通过，建议 BUG-210 回归通过后上线。
```

**要点：**
- 用具体数字说明执行情况和通过率
- 按严重程度分类说明缺陷状态
- 明确遗留问题的影响范围
- 给出可执行的上线条件

## 提交前检查清单

- [ ] 数据是否真实，不能凭感觉写。
- [ ] 执行情况表中的数字是否与缺陷统计、结论描述一致。
- [ ] 是否说明未测试范围及原因。
- [ ] 是否把高风险问题单独列出。
- [ ] 缺陷统计表是否有合计行。
- [ ] 是否给出明确结论（通过 / 有条件通过 / 不通过）。
- [ ] 是否说明遗留问题由谁确认、何时处理。
- [ ] 结论是否用数据支撑，而不是简单写"测试通过"。
- [ ] 是否有签字确认栏（测试、开发、产品）。
- [ ] 报告日期是否为测试结束日期。
