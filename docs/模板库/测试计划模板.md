# 测试计划模板

测试计划的作用是提前说清楚：测什么、不测什么、谁来测、什么时候测、风险在哪里。它不是形式文档，而是项目开始前的约定。

## 基础模板

| 模块 | 内容 |
|------|------|
| 项目名称 | 例如：商城优惠券功能测试 |
| 测试负责人 | 负责整体进度和质量结论的人 |
| 需求来源 | 需求文档、原型、接口文档、会议纪要 |
| 测试范围 | 本次明确要测试的功能 |
| 不测试范围 | 本次不覆盖的内容，避免后续扯皮 |
| 测试类型 | 功能、接口、兼容性、性能、安全、回归 |
| 测试环境 | 测试环境地址、数据库、账号、版本 |
| 测试数据 | 需要准备的账号、订单、商品、权限 |
| 排期计划 | 用例设计、执行、缺陷修复、回归、报告时间 |
| 准入条件 | 什么时候可以开始测试 |
| 准出条件 | 满足什么条件可以上线或交付 |
| 风险与应对 | 可能影响测试的风险和解决办法 |

## 示例

| 模块 | 示例内容 |
|------|----------|
| 项目名称 | 商城优惠券领取与使用功能 |
| 测试范围 | 优惠券列表、领取、下单使用、过期失效、退款返还 |
| 不测试范围 | 优惠券后台配置页面本次不测，只使用已有配置数据 |
| 测试类型 | 功能测试、接口测试、数据库校验、回归测试 |
| 测试环境 | `https://test-shop.example.com`，测试库 `shop_test` |
| 测试数据 | 普通用户、会员用户、已领取用户、库存为 0 的优惠券 |
| 准入条件 | 需求评审完成，测试环境部署成功，主流程可访问 |
| 准出条件 | P0/P1 缺陷全部关闭，核心用例 100% 通过，无阻塞风险 |
| 风险与应对 | 支付回调不稳定，提前准备模拟支付接口 |

## 准入条件示例

- [ ] 需求文档或原型已确认。
- [ ] 开发提测范围清楚。
- [ ] 测试环境可以访问。
- [ ] 基础测试账号可用。
- [ ] 关键接口文档已提供。
- [ ] 数据库表结构或字段说明已确认。

## 准出条件示例

- [ ] 核心业务流程测试通过。
- [ ] 严重和阻塞缺陷已修复并回归通过。
- [ ] 遗留缺陷已评估影响并得到确认。
- [ ] 测试报告已输出。
- [ ] 上线检查项已完成。

## 常见错误

| 错误写法 | 问题 |
|----------|------|
| 测试范围：测试全部功能 | 太空泛，无法判断是否覆盖 |
| 测试环境：测试环境 | 没有地址、账号、版本，无法复现 |
| 风险：暂无 | 很多项目都有风险，不写不代表没有 |
| 准出条件：测试通过 | 没有明确通过标准 |
