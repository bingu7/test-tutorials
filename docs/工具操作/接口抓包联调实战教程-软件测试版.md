## 新手导读

这篇教程是把 Fiddler、Postman、Python 串起来的实战流程。基础薄弱时不要三件工具一起学乱，按顺序来：先抓到真实请求，再用 Postman 复现，最后考虑自动化。

你需要完成的最小闭环是：

1. 在页面或 App 上操作一次业务。
2. 用 Fiddler 找到对应接口。
3. 把接口复制到 Postman 并发送成功。
4. 根据响应设计测试点。
5. 选择稳定接口改写成 Python 自动化。

只要这个闭环跑通，你就真正理解了“抓包联调”的价值。

## 二、第一阶段：抓包分析

### 2.1 为什么先抓包

- 接口文档可能不全或过时
- 抓包能看到 **真实的请求/响应**
- 了解接口调用顺序和依赖关系
- 发现隐藏接口（前端直接调的、埋点接口）

### 2.2 Fiddler 抓包步骤

**Step 1：配置 Fiddler**

1. 打开 Fiddler → `Tools` → `Options` → `HTTPS`
2. 勾选 `Decrypt HTTPS traffic`
3. 勾选 `Ignore server certificate errors`
4. `Connections` → 勾选 `Allow remote computers to connect`
5. 记住端口：默认 `8888`

**Step 2：配置过滤器**

只抓目标域名，避免干扰：

`Filters` → 勾选 `Use Filters` → `Hosts` → `Show only the following Hosts`：

```
*.example.com; api.example.com
```

**Step 3：操作 App / 网页**

正常操作被测系统，Fiddler 自动记录所有请求。

**Step 4：分析请求**

在会话列表中找到目标接口，查看：

- **Inspectors** → **WebForms**：请求参数
- **Inspectors** → **JSON**：响应数据
- **Inspectors** → **Headers**：请求头（Token、Cookie）
- **Statistics**：响应时间

### 2.3 导出请求到 Postman

**方式 1：复制 cURL（推荐）**

Fiddler 右键请求 → `Copy` → `Copy as cURL` → Postman 点击 `Import` → 粘贴 cURL → 自动解析。

**方式 2：导出 HAR 文件**

Fiddler → `File` → `Export Sessions` → `Selected Sessions` → 选 `HTTPArchive (.har)` → 在 Postman 中 `Import` 导入该 HAR 文件。

**方式 3：复制原始请求**

Fiddler 选中请求 → `Inspectors` → `Raw` → 复制全文 → Postman 手动构造。

### 2.4 分析业务流程

抓包后整理接口调用链：

```
1. POST /api/login          → 获取 token
2. GET  /api/user/info       → 获取用户信息（需 token）
3. GET  /api/products        → 商品列表（公开）
4. POST /api/cart/add        → 加购物车（需 token）
5. POST /api/order/create    → 创建订单（需 token）
6. POST /api/order/pay       → 支付（需 token + orderId）
```

记录每个接口的：

- 请求方法、URL
- 必填参数
- 鉴权方式（Token/Cookie/无）
- 依赖关系（哪个接口的输出是下一个的输入）

## 三、第二阶段：接口调试

### 3.1 在 Postman 中重建请求

**Step 1：创建 Collection**

按业务模块组织：`电商系统-用户模块`、`电商系统-订单模块`。

**Step 2：配置环境变量**

创建 `测试环境`：

| Variable | Value |
|----------|-------|
| base_url | https://api-test.example.com |
| username | testuser |
| password | 123456 |
| token | （登录后自动填充） |

**Step 3：逐个创建请求**

从 Fiddler 导入或手动创建，参数用变量引用：

```
POST {{base_url}}/api/login
Body: {"username":"{{username}}","password":"{{password}}"}
```

### 3.2 链式请求（依赖接口串联）

**登录接口的 Tests 脚本：**

```javascript
// 登录成功后自动保存 token
pm.test("登录成功", function () {
    const json = pm.response.json();
    pm.expect(json.code).to.eql(0);
    pm.environment.set("token", json.data.token);
});
```

**后续接口的 Header：**

```
Authorization: Bearer {{token}}
```

### 3.3 设计测试用例

基于抓包分析，为每个接口设计用例：

| 维度 | 测试点 |
|------|--------|
| 正常流程 | 正确参数返回预期结果 |
| 必填校验 | 缺少必填字段 |
| 参数类型 | 类型错误（字符串传数字） |
| 边界值 | 长度上下限、数值上下限 |
| 业务规则 | 状态流转、权限校验 |
| 异常场景 | 不存在的 ID、过期数据 |
| 安全 | SQL 注入、XSS、越权 |

### 3.4 断言脚本

```javascript
// 状态码
pm.response.to.have.status(200);

// 业务 code
const json = pm.response.json();
pm.expect(json.code).to.eql(0);

// 字段存在
pm.expect(json.data.token).to.be.a("string");

// 响应时间
pm.expect(pm.response.responseTime).to.be.below(1000);

// 响应包含
pm.expect(pm.response.text()).to.include("成功");
```

### 3.5 Collection Runner 批量执行

1. 点击 Collection → `Run collection`
2. 选择环境
3. 配置迭代次数（数据驱动时 > 1）
4. 加载数据文件（CSV/JSON）
5. 点击 `Run`

### 4.1 什么时候转自动化

| 条件 | 是否转 |
|------|--------|
| 接口稳定，频繁回归 | ✅ 转 |

### 4.4 核心代码

**config.yaml：**

```yaml
  base_url: https://api-test.example.com
  username: testuser
```

**request_util.py：**

```python
import requests

class RequestUtil:
    def __init__(self):
        self.session = requests.Session()
    
    def get(self, url, **kwargs):
        return self.session.get(url, timeout=30, **kwargs)
    
    def post(self, url, **kwargs):
        return self.session.post(url, timeout=30, **kwargs)

http = RequestUtil()
```

**conftest.py：**

```python
import pytest
import yaml
from common.request_util import http

config = yaml.safe_load(open("config/config.yaml", encoding="utf-8"))
env = config[config["env"]]

@pytest.fixture(scope="session")
def base_url():
    return env["base_url"]

@pytest.fixture(scope="session")
def login_token(base_url):
    resp = http.post(f"{base_url}/api/login", json={
        "username": env["username"],
        "password": env["password"]
    })
    return resp.json()["data"]["token"]
```

**test_login.py：**

```python
import pytest
from common.request_util import http

class TestLogin:
    
    def test_login_success(self, base_url):
        resp = http.post(f"{base_url}/api/login", json={
            "username": "testuser",
            "password": "123456"
        })
        assert resp.status_code == 200
        assert resp.json()["code"] == 0
        assert "token" in resp.json()["data"]
    
    def test_login_wrong_password(self, base_url):

            "username": "testuser",
            "password": "wrong"
        })
        assert resp.json()["code"] == 1001
```

## 五、实战案例

### 5.1 案例：电商下单完整链路

**Step 1：Fiddler 抓包**

抓到接口链：

```
1. POST /api/login           → token
2. GET  /api/products        → 商品列表
3. POST /api/cart/add        → 加购物车
4. POST /api/order/create    → 创建订单
5. GET  /api/order/{id}      → 查询订单
```

**Step 2：Postman 调试**

- 逐个接口建请求
- 写 Tests 脚本串联（登录存 token → 后续带 token）
- 验证每个接口的正常/异常场景

**Step 3：Python 自动化**

```python
def test_full_order_flow(base_url, login_token):
    headers = {"Authorization": f"Bearer {login_token}"}
    
    # 查询商品
    resp = http.get(f"{base_url}/api/products", headers=headers)
    product_id = resp.json()["data"]["list"][0]["id"]
    
    # 加购物车
    resp = http.post(f"{base_url}/api/cart/add", headers=headers,
                     json={"productId": product_id, "quantity": 1})
    assert resp.json()["code"] == 0
    
    # 创建订单
    resp = http.post(f"{base_url}/api/order/create", headers=headers,
                     json={"addressId": 1})
    assert resp.json()["code"] == 0
    order_id = resp.json()["data"]["orderId"]
    
    # 查询订单
    resp = http.get(f"{base_url}/api/order/{order_id}", headers=headers)
    assert resp.json()["data"]["status"] == "WAIT_PAY"
```

### 5.2 案例：Bug 复现与定位

**场景：** 用户反馈"下单后订单页看不到订单"。

**Step 1：Fiddler 抓包**

- 用户操作下单流程
- 抓到 `/api/order/create` 返回 200，code=0
- 但 `/api/order/list` 返回空列表

**Step 2：Postman 复现**

- 直接调 `/api/order/create`，拿到 orderId
- 调 `/api/order/list`，确认查不到
- 调 `/api/order/{orderId}`，确认订单存在

**Step 3：定位**

- 订单创建成功但列表查不到 → 可能是缓存问题或查询条件问题
- 进一步抓包发现 list 接口多了个默认过滤参数 `status=PAID`
- 订单状态是 `WAIT_PAY`，被过滤了 → **Bug 确认**

## 六、常见问题排查

### 6.1 Fiddler 抓不到请求

- 检查是否勾选 `Capture Traffic`
- 检查 App 是否走了代理
- 检查是否被过滤器排除
- HTTPS 是否解密开启

### 6.2 Postman 请求与实际不一致

- 检查 Headers 是否完整（特别是 Content-Type）
- 检查 Body 格式（JSON vs form-data）
- 检查环境变量是否生效

### 6.3 自动化用例偶发失败

- 网络抖动：加重试机制
- 数据冲突：用独立测试数据
- 接口变更：及时更新用例
- 依赖服务不稳定：Mock 外部依赖

### 6.4 Token 过期

```python
# conftest.py 中用 session 级 fixture，整轮测试只登录一次

    resp = http.post(f"{base_url}/api/login", json={...})
```

## 动手任务：用抓包证据判定「前端说没返回、后端说返回了」的责任方

> 这是本教程的收尾练习。请**独立完成**，不要先看参考答案。目标不是"打开抓包工具看到流量"，而是**用报文证据把责任方钉死**，并能说清联调的排查顺序。

### 任务背景

上线前回归时，产品在测试环境点击「提交订单」，页面上只弹出一个**空白的错误提示**。前端同学说："接口根本没返回，我看 Network 里一片红。"后端同学说："日志里接口 200 返回了，`code = 0`，订单都落库了。"

双方各执一词，会开了 40 分钟没有结论。你要做的是：**抓到双方都在场的证据（完整请求报文 + 完整响应报文）**，判定是"请求没发出去 / 参数不对 / 服务端真的没回 / 前端拿到但解析失败"中的哪一种，并给出可复用的联调排查顺序。

### 任务准备

| 项目 | 内容 |
|------|------|
| 环境 | 测试环境 `https://api-test.eshop.example.com` |
| 前端页面 | `https://h5-test.eshop.example.com/order/confirm` |
| 被测接口 | `POST /api/order/create` |
| 抓包工具 | Fiddler / Charles（任选其一，需能抓到 HTTPS；App 或 H5 均可） |
| 复现账号 | `testuser / 123456`（已登录，token 有效） |

**Fiddler 过滤设置（只留目标接口，避免噪声）：**

```text
Filters → Hosts: 显示以下主机
  api-test.eshop.example.com
Filters → Request Headers → Show only if URL contains
  /api/order/create
```

**关键复现信息：**

| 项 | 值 |
|----|-----|
| 触发操作 | 订单确认页点击「提交订单」 |
| 前端请求体 | `{"addressId": 1001, "items": [{"skuId": 90001, "quantity": 2}]}` |
| 预期响应 | `{"code": 0, "message": "success", "data": {"orderId": ...}}` |
| 前端表现 | 弹空白错误提示，页面停留在确认页 |
| 后端自述 | 日志显示 `POST /api/order/create 200`、`code=0`、订单表新增 1 条 |
| 抓包注意 | 抓包列表里会有多条同 URL 的会话，需按时间戳与本次点击对齐；无关的静态资源会话一律剔除 |

**排查顺序参考表（做题时用于逐层给证据，不是答案）：**

| 层 | 看什么 | 需要交付的证据 |
|----|--------|----------------|
| ① 请求是否发出 | 抓包列表里有没有这条 `POST /api/order/create` | 会话列表截图或文本 |
| ② 请求是否正确 | 请求头 `Content-Type`、`Authorization`；请求体字段与类型 | 请求报文原文 |
| ③ 服务端是否响应 | 响应状态行 `HTTP/1.1 xxx`、响应头、响应体 | 响应报文原文 |
| ④ 前端是否处理 | 响应体 `code` / `message` 与页面提示是否对应 | 响应体 + 页面表现 |

### 任务要求

请依次完成，并**保留每个证据**：

1. **抓取完整报文**：抓到一次「提交订单」的完整会话，把**请求行 + 请求头（至少含 `Authorization`、`Content-Type`、`Content-Length`）+ 请求体**，以及**状态行 + 响应头（至少含 `Content-Type`、`Content-Length`、`Server`）+ 响应体**完整导出（Fiddler：右键 → Save → Session → as Text；Charles：右键 → Export）。
2. **逐层判定责任方**：按上面的排查顺序表逐层给证据，判定本次是**哪一层**出的问题（四选一：请求未发出 / 请求参数错误 / 服务端未正确响应 / 前端解析或渲染失败）。
3. **区分"HTTP 层正常"与"业务层正常"**：指出本次会话中 `status` 与 `code` 分别是什么，说明为什么**只看 HTTP 200 会误判**，并给出前端"空白错误提示"的最可能来源。
4. **给出可复用产出**：写一份**联调排查顺序清单（5 步以内）**，要求每一步都写明"看什么字段 / 什么位置"和"什么现象指向哪一方"，让下次再出现类似争执时可以照着走。

### 提交物

| 产出 | 要求 |
|------|------|
| 请求报文 | 请求行 + 完整请求头 + 请求体原文 |
| 响应报文 | 状态行 + 完整响应头 + 响应体原文 |
| 责任判定表 | 四层逐条填写：现象 → 证据 → 是否指向该层 → 结论 |
| 判定结论 | 一句话说清责任方，并给出依据（引用报文里的具体字段） |
| 联调排查顺序清单 | 不超过 5 步，每步写明"看哪里 + 什么现象指向谁" |
| 复盘建议 | 2-3 句：如何避免下一次同类"扯皮"（如统一 traceId、前端错误提示兜底） |

### 完成标准

- [ ] 能抓到完整的 HTTPS 请求 / 响应报文，并正确导出为文本或文件
- [ ] 能读懂请求行、状态行、请求头、响应头、请求体、响应体的结构，并指出 `Content-Type`、`Content-Length`、`Authorization` 的作用
- [ ] 能区分 **HTTP 状态码（如 200 / 502）** 与 **业务状态码（如 `code = 0` / `code = 1002`）**，不会用 HTTP 200 直接判定"接口成功"
- [ ] 能从报文证据判定责任方，而不是靠"谁声音大"
- [ ] 产出的排查清单可被任意前后端联调场景复用
- [ ] 能说明抓包时如何过滤噪声、如何把一次业务操作与对应的会话记录对齐

??? tip "参考答案与思路（先自己做完再看）"

    **第 1 题：完整报文（真实抓取结果）**

    请求：

    ```http
    POST /api/order/create HTTP/1.1
    Host: api-test.eshop.example.com
    Connection: keep-alive
    Content-Type: application/json
    Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1aWQiOjEwMDAxfQ.7Kd2...
    Accept: application/json, text/plain, */*
    Content-Length: 76
    Origin: https://h5-test.eshop.example.com

    {"addressId": 1001, "items": [{"skuId": 90001, "quantity": 2}]}
    ```

    响应：

    ```http
    HTTP/1.1 200 OK
    Server: nginx/1.24.0
    Date: Mon, 14 Sep 2026 10:20:31 GMT
    Content-Type: text/html; charset=utf-8
    Content-Length: 402
    Connection: keep-alive

    <html>
    <head><title>502 Bad Gateway</title></head>
    <body>
    <center><h1>502 Bad Gateway</h1></center>
    <hr><center>nginx/1.24.0</center>
    </body>
    </html>
    ```

    关键点：**响应体是 HTML 而不是 JSON**，且 `Content-Type` 是 `text/html`。这说明响应不是业务服务返回的，而是网关 / 代理层吐出的错误页。请求侧逐字校对过，`Content-Type`、`Authorization`、`Content-Length` 都没有丢字段的问题。

    **第 2 题：逐层判定**

    | 层 | 现象 | 证据 | 是否指向该层 |
    |----|------|------|--------------|
    | ① 请求是否发出 | 抓包列表中存在 `POST /api/order/create` | 会话列表有记录，时间戳与点击操作对齐 | 不指向：请求确实发出了 |
    | ② 请求是否正确 | 方法、路径、`Content-Type: application/json`、`Authorization` 均正常；Body 字段与前端定义一致，JSON 合法 | 请求报文原文 | 不指向：参数无问题 |
    | ③ 服务端是否响应 | 状态行是 `200`，但 `Content-Type: text/html`、响应体是 nginx 的 **502 Bad Gateway** 页面 | 响应报文原文 | **指向这一层** |
    | ④ 前端是否处理 | 前端按 JSON 解析响应，遇到 HTML 解析失败 → `code` 为 `undefined` → 拼接出空白提示 | 响应体 + 页面表现 | 不指向：只是次生表现 |

    结论：**责任在服务端链路（应用服务未正常返回，由 nginx 返回了 502 错误页）**。前端"空白提示"是次生问题——错误处理时没有对非 JSON 响应做兜底。

    注意：`HTTP/1.1 200` 是 nginx 自己吐出的响应行，**不能**据此认为"后端接口返回成功了"。后端自述的 `code=0` 需要核对是否来自**另一次**请求（例如用户点了多次，前几次成功、这次被网关拦下），对齐方式是用抓包时间戳去匹配后端日志时间。

    **第 3 题：HTTP 层 vs 业务层**

    ```text
    HTTP 状态：200（响应行由 nginx 返回，内容是 502 错误页）
    业务状态：不存在 code 字段（响应体是 HTML，不是 JSON）
    前端表现：JSON 解析失败 → 读 code/message 得到 undefined → 提示文案为空
    ```

    为什么只看 HTTP 200 会误判：这次会话严格来说连"业务接口返回"都不算，是网关错误页。**正确姿势是三个条件一起看**——HTTP 状态码正常 **且** `Content-Type` 是 `application/json` **且** 业务 `code` 符合约定。任何一条不满足，都不能判定"接口成功"。

    前端空白提示最可能来源：`catch` 分支里 `message` 取空，或者 `resp.data.message` 在解析失败时是 `undefined`，最终 `toast(undefined)` 渲染成空白。

    **第 4 题：联调排查顺序清单（可复用）**

    ```text
    1. 抓包列表有没有这条请求？
         没有 → 前端根本没发出（按钮未绑定 / 被前置校验拦住 / 请求被跨域或 CSP 拦截）
    2. 有请求，看请求行 + 请求头 + 请求体
         Content-Type 不是 application/json / Body 字段缺失或类型错 / Authorization 缺失或过期
         → 前端问题
    3. 请求正常，看响应行 + 响应头
         状态行 4xx（401/403/404）→ 鉴权或路由问题，找后端确认路径与 token
         状态行 5xx → 服务端异常，找后端查应用日志与网关日志
         状态行 200 但 Content-Type 不是 application/json → 极可能是网关 / 代理错误页
    4. 响应是合法 JSON，看业务字段
         code != 0 → 业务失败，按 message 追业务日志
         code == 0 但页面仍异常 → 前端解析 / 渲染问题
    5. 仍无法定位 → 用 traceId / 时间戳把抓包会话与后端日志对齐，双方一起看同一条记录
    ```

    复盘建议：

    > ① 在请求头统一带上 `X-Trace-Id`，前后端日志与抓包会话可一键对齐，避免"我这边是好的"式争论；
    > ② 前端对所有响应先判 `Content-Type`，非 JSON 一律提示"服务异常，请稍后重试"，不留空白提示；
    > ③ 联调类缺陷一律要求附抓包文件，作为提缺陷的强制附件项。
