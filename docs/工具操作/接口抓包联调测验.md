## 选择题

<div class="quiz-container" data-quiz-id="packet-debug-workflow">

<div class="quiz-item" data-correct="1">
<div class="quiz-question">接口抓包联调的完整工作流，正确的推进顺序是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q1" value="0"> 直接写自动化脚本 → 抓包验证 → 补充用例</label>
<label class="quiz-option"><input type="radio" name="q1" value="1"> 抓包分析 → Postman 接口调试 → 自动化落地</label>
<label class="quiz-option"><input type="radio" name="q1" value="2"> 先看接口文档 → 跳过抓包 → 直接压测</label>
<label class="quiz-option"><input type="radio" name="q1" value="3"> 先用 Postman 造数据 → 再让开发补文档</label>
</div>
<div class="quiz-explanation">💡 先抓包是为了拿到"系统实际发出的请求"，再在 Postman 里复现和扩展用例，最后把稳定下来的用例代码化。顺序颠倒很容易出现"脚本写得挺顺，但测的接口根本不是真实链路"</div>
</div>

<div class="quiz-item" data-correct="2">
<div class="quiz-question">为什么要先抓包分析，而不是直接照着接口文档写用例？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q2" value="0"> 接口文档里的参数都是错的</label>
<label class="quiz-option"><input type="radio" name="q2" value="1"> 抓包比看文档更省时间</label>
<label class="quiz-option"><input type="radio" name="q2" value="2"> 文档常常滞后或不完整，抓包能拿到真实的参数、请求头和鉴权方式</label>
<label class="quiz-option"><input type="radio" name="q2" value="3"> 只有抓包才能看到响应内容</label>
</div>
<div class="quiz-explanation">💡 文档漏写必填参数、签名规则、自定义请求头是老问题。抓包拿到的是"能跑通的真实请求"，直接导出到 Postman 就能复现，还能顺手发现文档与实际不一致的缺陷</div>
</div>

<div class="quiz-item" data-correct="0">
<div class="quiz-question">把 Fiddler 抓到的请求导出到 Postman 后，紧接着最该做的一件事是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q3" value="0"> 把 URL、Token 等写死的值抽成环境变量或集合变量</label>
<label class="quiz-option"><input type="radio" name="q3" value="1"> 立刻复制出几十个请求以增加覆盖面</label>
<label class="quiz-option"><input type="radio" name="q3" value="2"> 先删掉所有请求头，只保留 URL</label>
<label class="quiz-option"><input type="radio" name="q3" value="3"> 把响应内容改成固定值方便断言</label>
</div>
<div class="quiz-explanation">💡 导出后的请求里会残留具体环境的域名和当次会话的 token，直接使用的话换个环境就全挂。第一步就参数化，后面才能一键切换测试环境和用户身份</div>
</div>

<div class="quiz-item" data-correct="3">
<div class="quiz-question">"链式请求"指的是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q4" value="0"> 把同一个请求连续发送多次做压测</label>
<label class="quiz-option"><input type="radio" name="q4" value="1"> 用多个客户端同时发送同一请求</label>
<label class="quiz-option"><input type="radio" name="q4" value="2"> 把多个不相关的接口放在一个集合里批量执行</label>
<label class="quiz-option"><input type="radio" name="q4" value="3"> 把上一个接口的返回值提取成变量，作为下一个接口的入参</label>
</div>
<div class="quiz-explanation">💡 真实业务几乎都是链式的：登录拿 token → 查询商品拿 skuId → 加购 → 下单拿 orderId → 支付。用变量把返回值串起来，才能测出真实链路里的问题，比如依赖字段为空、状态未同步</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">Postman 里请求能通，但抓包工具怎么都抓不到这条请求，最可能的原因是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q5" value="0"> 抓包工具只能抓浏览器的流量</label>
<label class="quiz-option"><input type="radio" name="q5" value="1"> Postman 默认不走系统代理，需要在设置中单独配置代理地址和端口</label>
<label class="quiz-option"><input type="radio" name="q5" value="2"> HTTPS 请求一律无法被抓取</label>
<label class="quiz-option"><input type="radio" name="q5" value="3"> 必须重启 Fiddler 才能开始抓取</label>
</div>
<div class="quiz-explanation">💡 Postman 是独立客户端，默认不读取系统代理设置，所以抓包工具看不到它的流量。需要在 Postman 的 Proxy 设置里显式指定抓包工具的地址和端口，这一点在联调时非常容易踩坑</div>
</div>

<div class="quiz-item" data-correct="2">
<div class="quiz-question">Postman 里请求返回 400，但用抓包看到的真实请求是成功的。第一步应该做什么？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q6" value="0"> 直接判定为后端 Bug 并提交缺陷</label>
<label class="quiz-option"><input type="radio" name="q6" value="1"> 更换测试环境重新尝试</label>
<label class="quiz-option"><input type="radio" name="q6" value="2"> 把两个请求逐项比对：请求方法、URL、请求头、参数位置和取值</label>
<label class="quiz-option"><input type="radio" name="q6" value="3"> 把断言全部去掉再执行</label>
</div>
<div class="quiz-explanation">💡 差异通常藏在细节里：参数该放 body 却放进了 query、Content-Type 不对、少了签名头、Cookie 没带上。<code>params</code>、<code>form-data</code>、<code>x-www-form-urlencoded</code>、<code>raw JSON</code> 这几种提交方式的后果完全不同</div>
</div>

<div class="quiz-item" data-correct="0">
<div class="quiz-question">接口断言脚本应该重点断言什么？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q7" value="0"> HTTP 状态码，以及业务关键字段（如 code、msg、data 中的核心值）</label>
<label class="quiz-option"><input type="radio" name="q7" value="1"> 只断言状态码等于 200 就够了</label>
<label class="quiz-option"><input type="radio" name="q7" value="2"> 断言响应时间必须小于 100 毫秒</label>
<label class="quiz-option"><input type="radio" name="q7" value="3"> 断言整个响应字符串与某次运行的快照完全一致</label>
</div>
<div class="quiz-explanation">💡 只断言 200 会漏掉"接口通了但业务失败"的情况——很多系统失败时同样返回 200，靠 <code>code</code> 字段区分。而断言整个响应字符串过于脆弱，时间戳、ID 一变就失败</div>
</div>

<div class="quiz-item" data-correct="3">
<div class="quiz-question">Collection Runner 的主要价值是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q8" value="0"> 自动生成接口文档</label>
<label class="quiz-option"><input type="radio" name="q8" value="1"> 把 Postman 集合翻译成 Python 代码</label>
<label class="quiz-option"><input type="radio" name="q8" value="2"> 自动修复失败的接口请求</label>
<label class="quiz-option"><input type="radio" name="q8" value="3"> 按顺序批量执行整个集合，并汇总每轮的执行结果</label>
</div>
<div class="quiz-explanation">💡 Runner 让一组有依赖关系的请求能一键跑完，配合数据文件还能做数据驱动。它也是"要不要转自动化"的判断依据：如果这组用例每周都要手动跑，代码化的收益就很明显了</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">下列哪种情况最适合把 Postman 用例转成代码自动化？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q9" value="0"> 需求还在频繁变更、接口定义每天调整</label>
<label class="quiz-option"><input type="radio" name="q9" value="1"> 接口相对稳定，且需要频繁回归或在多环境重复执行</label>
<label class="quiz-option"><input type="radio" name="q9" value="2"> 只需要在本次版本验证一次</label>
<label class="quiz-option"><input type="radio" name="q9" value="3"> 用例结果需要人工主观判断</label>
</div>
<div class="quiz-explanation">💡 自动化的收益来自"重复执行 + 结果可自动断言"。接口还在天天变、或者只跑一次的场景，脚本写出来很快就得重写，投入产出比很低</div>
</div>

<div class="quiz-item" data-correct="2">
<div class="quiz-question">从 Postman 迁移到 Python 自动化时，下列映射关系正确的是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q10" value="0"> Postman 集合 → pytest 的 fixture</label>
<label class="quiz-option"><input type="radio" name="q10" value="1"> Tests 断言脚本 → conftest.py 配置文件</label>
<label class="quiz-option"><input type="radio" name="q10" value="2"> 环境变量 → 配置或 fixture，Tests 断言 → Python 的 assert</label>
<label class="quiz-option"><input type="radio" name="q10" value="3"> Pre-request Script → Allure 报告</label>
</div>
<div class="quiz-explanation">💡 结构上一一对应：Postman 集合对应测试用例集，环境变量对应配置或 fixture，Tests 对应断言，Pre-request Script 对应前置处理（如取 token）。理清映射关系，迁移就不是重写而是翻译</div>
</div>

<div class="quiz-item" data-correct="0">
<div class="quiz-question">自动化用例跑一段时间后大量报"未授权"，最有效的解决办法是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q11" value="0"> 在 conftest.py 中用 session 级 fixture 统一登录一次，并在 token 失效时刷新</label>
<label class="quiz-option"><input type="radio" name="q11" value="1"> 把每条用例里的 token 都改成固定不变的值</label>
<label class="quiz-option"><input type="radio" name="q11" value="2"> 让开发把 token 有效期改成一年</label>
<label class="quiz-option"><input type="radio" name="q11" value="3"> 遇到未授权就捕获异常直接跳过该用例</label>
</div>
<div class="quiz-explanation">💡 每条用例各自登录既慢又容易踩到有效期边界。用 session 级 fixture 全局登录一次，再把 token 注入请求头，是既快又稳的标准做法。改成永久有效或跳过用例，都是把风险藏起来而不是解决</div>
</div>

<div class="quiz-item" data-correct="3">
<div class="quiz-question">自动化用例偶发失败（同一脚本有时通过、有时失败），优先排查方向是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q12" value="0"> 直接把这条用例从回归集中删掉</label>
<label class="quiz-option"><input type="radio" name="q12" value="1"> 增加重试次数，让它自己变绿</label>
<label class="quiz-option"><input type="radio" name="q12" value="2"> 把断言放宽到几乎不校验业务结果</label>
<label class="quiz-option"><input type="radio" name="q12" value="3"> 检查用例间的数据依赖与执行顺序、环境稳定性，以及数据是否被上一轮污染</label>
</div>
<div class="quiz-explanation">💡 偶发失败几乎都指向三类根因：用例之间有隐式依赖（顺序一变就挂）、环境或数据不稳定、上一轮数据没清理。用重试掩盖问题，会让真正的不稳定一直留在系统里，最后没人再相信这份报告</div>
</div>
