# 性能测试案例

性能测试不是"跑个压测工具看数字"就行的。它需要明确目标、设计场景、准备数据、执行监控、定位瓶颈、输出结论。以下是电商系统大促前的性能测试全流程。

## 需求背景

电商系统即将迎来 618 大促，预计日活用户为平时的 10 倍。需要对核心接口进行性能测试，确保系统在高并发下稳定运行，不会出现页面打不开、下单失败、支付超时等问题。

## 测试目标

| 接口 | 指标 | 目标值 |
|------|------|--------|
| 首页 | TPS | ≥500 |
| 商品详情页 | TPS | ≥300 |
| 下单接口 | TPS | ≥200 |
| 支付接口 | TPS | ≥100 |
| 所有接口 | P95 响应时间 | <2s |
| 所有接口 | 错误率 | <0.1% |
| 所有接口 | CPU 使用率 | <80% |
| 所有接口 | 内存使用率 | <85% |

## 测试场景设计

性能测试分四个阶段，逐步逼近系统极限：

| 阶段 | 目的 | 并发用户数 | 持续时间 |
|------|------|------------|----------|
| 基准测试 | 获取单用户最优响应时间 | 1 | 10 分钟 |
| 负载测试 | 观察性能随并发增加的变化 | 50→100→200→500 | 每级 10 分钟 |
| 压力测试 | 找到系统极限，观察降级表现 | 500→1000→2000 | 每级 10 分钟 |
| 稳定性测试 | 验证长时间运行是否稳定 | 200 | 4 小时 |

## JMeter 脚本设计思路

```
测试计划
├── 线程组（Thread Group）
│   ├── 用户参数（CSV Data Set Config）—— 用户账号
│   ├── 首页请求（HTTP Request）
│   ├── 商品详情页请求（HTTP Request）
│   ├── 登录请求（HTTP Request）
│   ├── 下单请求（HTTP Request）
│   └── 支付请求（HTTP Request）
├── 监听器
│   ├── 聚合报告（Aggregate Report）
│   ├── 响应时间图（Response Time Graph）
│   └── TPS 图（Transactions Per Second）
└── 断言
    ├── 响应状态码 = 200
    └── 响应体包含"success"
```

关键点：
- 使用 CSV 文件管理测试账号，避免所有请求用同一个账号。
- 接口之间有依赖（下单需要先登录），要处理 token 传递。
- 商品 ID 和收货地址提前准备，避免动态生成带来的额外开销。
- 请求头要模拟真实浏览器（User-Agent、Cookie、Referer）。

## 测试数据准备

| 数据 | 说明 |
|------|------|
| 测试账号 | 500 个，CSV 文件管理 |
| 商品数据 | 数据库中有 10 万+商品，至少 1000 个在售 |
| 收货地址 | 每个账号预设 3 个地址 |
| 订单数据 | 历史订单 50 万条 |
| 测试环境 | 与生产环境同配置（4 核 8G × 3 台） |

## 测试执行过程

### 第一步：基准测试

单用户访问各接口，记录基线响应时间：
- 首页：150ms
- 商品详情页：200ms
- 下单：300ms
- 支付：500ms

### 第二步：负载测试（逐步加压）

逐步增加并发用户数，观察 TPS 和响应时间的变化：

| 并发数 | 首页 TPS | 首页 P95 | 下单 TPS | 下单 P95 | 错误率 |
|--------|----------|----------|----------|----------|--------|
| 50 | 480 | 180ms | 190 | 350ms | 0% |
| 100 | 495 | 350ms | 198 | 500ms | 0% |
| 200 | 500 | 800ms | 200 | 1.2s | 0% |
| 500 | 490 | 2.5s | 180 | 3.5s | 0.5% |

发现问题：并发 500 时，下单接口 P95 超过 2s 目标，错误率也上升了。

### 第三步：瓶颈定位

通过监控发现：
1. 数据库 CPU 占用 95%——存在慢查询。
2. 应用服务器 CPU 只有 60%——瓶颈不在应用层。
3. 慢查询日志发现下单接口执行了全表扫描的 SELECT 语句。

```sql
-- 原始查询（无索引，耗时 1.2s）
SELECT * FROM orders WHERE user_id = 10001 AND status = 'pending'
ORDER BY created_at DESC LIMIT 10;

-- 添加联合索引后（耗时 0.003s）
CREATE INDEX idx_orders_user_status ON orders(user_id, status, created_at);
```

### 第四步：优化后回归

添加索引后重新测试：

| 并发数 | 下单 TPS | 下单 P95 | 错误率 |
|--------|----------|----------|--------|
| 500 | 350 | 1.1s | 0% |
| 1000 | 300 | 1.8s | 0.05% |
| 2000 | 250 | 2.8s | 0.3% |

结论：优化后下单 TPS 提升 3 倍，500 并发下 P95 降到 1.1s，达标。

## 性能测试报告结论模板

```
一、测试概述
  - 测试时间：2024-05-20 ~ 2024-05-22
  - 测试环境：与生产同配置，4核8G × 3台
  - 测试工具：JMeter 5.6 + Grafana 监控

二、测试结果
  - 首页 TPS 达标：500（目标≥500）✅
  - 商品详情页 TPS 达标：350（目标≥300）✅
  - 下单接口 TPS 达标：350（目标≥200）✅（优化后）
  - 支付接口 TPS 达标：120（目标≥100）✅
  - P95 响应时间：全部 <2s ✅
  - 错误率：全部 <0.1% ✅

三、发现的问题
  1. 下单接口存在慢查询，加索引后 TPS 提升 3 倍
  2. 高并发下日志写入影响磁盘 IO，建议异步写入

四、建议
  1. 上线前完成索引优化并回归验证
  2. 大促期间开启限流，阈值设为 1500 并发
  3. 准备降级方案：非核心功能（推荐、评论）可临时关闭
```

## 经验总结

1. **性能测试要尽早做**：不要等上线前才发现瓶颈，开发阶段就该跑基准测试。
2. **环境要和生产一致**：用 1 核 2G 测出来的数据毫无参考价值。
3. **数据量要真实**：空表测出来的 TPS 没有意义，至少要有真实数据量的 1/10。
4. **监控比结果更重要**：只知道 TPS 低没用，要通过监控找到瓶颈在哪。
5. **逐步加压比直接打满更有价值**：能看到性能拐点在哪。

## 常见坑

- 只跑单接口压测，不跑混合场景。实际用户会同时访问首页、下单、支付。
- 测试数据都命中缓存，和真实场景不符。要模拟冷启动和缓存穿透。
- 压测机本身成为瓶颈。压测机的 CPU、带宽、连接数都要够。
- 忘记清理测试数据，影响后续测试轮次。
- 只看平均响应时间，不看 P95/P99。平均值会掩盖长尾问题。
- 性能测试报告只有数字没有结论，开发不知道怎么优化。

## 复盘问题

- TPS 和 QPS 有什么区别？什么时候用哪个？
- 为什么性能测试要用 P95 而不是平均响应时间？
- 如果数据库加了索引还是慢，还有什么优化思路？
- 限流、降级、熔断分别解决什么问题？
