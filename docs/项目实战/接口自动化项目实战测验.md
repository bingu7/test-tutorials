## 选择题

<div class="quiz-container" data-quiz-id="api-auto-project">

<div class="quiz-item" data-correct="1">
<div class="quiz-question">从 Postman 过渡到接口自动化，推荐的学习顺序是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q1" value="0"> 先搭好完整框架，再往框架里填用例</label>
<label class="quiz-option"><input type="radio" name="q1" value="1"> 先用 Postman 调通接口 → 改成 Python 代码 → 用 Pytest 管理用例 → 再加数据、断言、报告和 CI</label>
<label class="quiz-option"><input type="radio" name="q1" value="2"> 先写 Allure 报告配置，再补测试用例</label>
<label class="quiz-option"><input type="radio" name="q1" value="3"> 先做数据驱动，再写第一个请求</label>
</div>
<div class="quiz-explanation">💡 教程反复强调：框架是从重复代码中提炼出来的，不是第一天凭空设计出来的。一开始就搭大框架是新手最常见的卡点，容易堆出一堆难排查的错误</div>
</div>

<div class="quiz-item" data-correct="2">
<div class="quiz-question">"接口自动化 = 用代码代替 Postman"，那么一次自动化请求至少要判断哪些内容？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q2" value="0"> 只要接口有返回就算通过</label>
<label class="quiz-option"><input type="radio" name="q2" value="1"> 只要 HTTP 状态码是 200 就算通过</label>
<label class="quiz-option"><input type="radio" name="q2" value="2"> HTTP 状态码、业务 code、响应字段、数据库结果，以及异常场景是否被正确拒绝</label>
<label class="quiz-option"><input type="radio" name="q2" value="3"> 只要响应时间在阈值内就算通过</label>
</div>
<div class="quiz-explanation">💡 教程把"只断言状态码 200"列为典型新手错误：业务失败同样可能返回 200。所以必须同时看协议层、业务层、数据层，并确认异常场景确实被拒绝</div>
</div>

<div class="quiz-item" data-correct="0">
<div class="quiz-question">第一版自动化应该优先覆盖哪类接口？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q3" value="0"> P0/P1 且稳定、关键、高频的接口</label>
<label class="quiz-option"><input type="radio" name="q3" value="1"> 项目里的全部接口，越多越好</label>
<label class="quiz-option"><input type="radio" name="q3" value="2"> 变化频繁的后台配置接口</label>
<label class="quiz-option"><input type="radio" name="q3" value="3"> 依赖第三方支付的真实回调接口</label>
</div>
<div class="quiz-explanation">💡 教程主张第一阶段只覆盖 P0/P1 接口，优先做稳定流程。变化频繁的接口先保留手工验证，把所有接口都自动化会带来过高的维护成本</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">按照教程的目录结构，<code>common/</code> 目录应该放什么？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q4" value="0"> 测试用例</label>
<label class="quiz-option"><input type="radio" name="q4" value="1"> 请求封装、日志、通用断言等通用能力</label>
<label class="quiz-option"><input type="radio" name="q4" value="2"> 测试数据</label>
<label class="quiz-option"><input type="radio" name="q4" value="3"> 环境配置</label>
</div>
<div class="quiz-explanation">💡 教程的划分是：<code>common/</code> 放通用能力（client、logger、assert_utils），<code>data/</code> 放测试数据，<code>tests/</code> 放用例，<code>config/</code> 放环境配置，<code>utils/</code> 放数据库、Token 等工具函数</div>
</div>

<div class="quiz-item" data-correct="2">
<div class="quiz-question">为什么建议第一个用例"先不要急着封装"？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q5" value="0"> 封装之后用例就无法运行了</label>
<label class="quiz-option"><input type="radio" name="q5" value="1"> <code>requests</code> 库不支持类封装</label>
<label class="quiz-option"><input type="radio" name="q5" value="2"> 先跑通最简单的请求确认链路可用，再按"边写边运行"的节奏逐步抽出重复代码</label>
<label class="quiz-option"><input type="radio" name="q5" value="3"> 封装会让断言失效</label>
</div>
<div class="quiz-explanation">💡 教程建议每新增一个文件就执行一次 <code>pytest</code>，确认问题发生在哪一步。先写裸请求能快速验证环境、地址和账号是否可用，把问题挡在最前面</div>
</div>

<div class="quiz-item" data-correct="3">
<div class="quiz-question">生产环境的密码、Token、数据库密码为什么不建议写在 <code>config/env.yaml</code> 里？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q6" value="0"> YAML 不支持特殊字符</label>
<label class="quiz-option"><input type="radio" name="q6" value="1"> 配置文件会拖慢用例执行速度</label>
<label class="quiz-option"><input type="radio" name="q6" value="2"> 配置文件无法被 Python 读取</label>
<label class="quiz-option"><input type="radio" name="q6" value="3"> 敏感信息应使用环境变量或 CI Secret，避免随仓库泄露</label>
</div>
<div class="quiz-explanation">💡 教程的边界是：测试环境账号可以写在配置文件里，但生产环境密码、Token、数据库密码必须走环境变量或 CI Secret。这也是维护规范里"敏感信息泄露"这一行的处理方式</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">请求封装里使用 <code>requests.Session()</code> 的主要好处是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q7" value="0"> 自动生成 Allure 测试报告</label>
<label class="quiz-option"><input type="radio" name="q7" value="1"> 复用连接并统一维护 Header 等会话级配置，例如通过 <code>set_token</code> 注入 Token</label>
<label class="quiz-option"><input type="radio" name="q7" value="2"> 可以省掉断言步骤</label>
<label class="quiz-option"><input type="radio" name="q7" value="3"> 请求失败时会自动重试</label>
</div>
<div class="quiz-explanation">💡 教程的 <code>ApiClient</code> 用 Session 统一管理 base_url、timeout 和 Header，再提供 <code>set_token</code> 更新 Authorization。这样用例里只关注业务行为，不用每次都拼地址、传 Token</div>
</div>

<div class="quiz-item" data-correct="2">
<div class="quiz-question">数据驱动（例如 <code>data/login.yaml</code> 配合 <code>@pytest.mark.parametrize</code>）最适合什么场景？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q8" value="0"> 所有用例都必须数据驱动，否则不算自动化</label>
<label class="quiz-option"><input type="radio" name="q8" value="1"> 步骤繁多、前后依赖复杂的业务流程</label>
<label class="quiz-option"><input type="radio" name="q8" value="2"> 参数组合清晰的接口，例如登录的成功、密码错误、账号不存在</label>
<label class="quiz-option"><input type="radio" name="q8" value="3"> 只需要执行一次的一次性验证</label>
</div>
<div class="quiz-explanation">💡 教程提醒"复杂业务流程不要过度数据化，否则可读性会下降"。数据驱动的收益来自同一套步骤跑多组数据，参数越多、步骤越简单，收益越明显</div>
</div>

<div class="quiz-item" data-correct="0">
<div class="quiz-question">分层断言中，"业务层"断言指的是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q9" value="0"> 业务 code、message、关键字段</label>
<label class="quiz-option"><input type="radio" name="q9" value="1"> HTTP 状态码、响应时间、Content-Type</label>
<label class="quiz-option"><input type="radio" name="q9" value="2"> 数据库记录、库存、订单状态</label>
<label class="quiz-option"><input type="radio" name="q9" value="3"> 鉴权、越权、敏感字段</label>
</div>
<div class="quiz-explanation">💡 教程把断言分成四层：协议层看状态码和响应时间，业务层看业务 code 和关键字段，数据层看数据库落库结果，安全层看鉴权和越权。四层组合才能覆盖接口的真实质量</div>
</div>

<div class="quiz-item" data-correct="1">
<div class="quiz-question">创建订单接口只断言 <code>code == 0</code> 不够，还应该补充哪些校验？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q10" value="0"> 响应时间是否小于 100ms</label>
<label class="quiz-option"><input type="radio" name="q10" value="1"> 订单号不为空、订单金额正确、状态为待支付、库存被正确扣减、订单归属当前用户</label>
<label class="quiz-option"><input type="radio" name="q10" value="2"> 响应头是否包含 Set-Cookie</label>
<label class="quiz-option"><input type="radio" name="q10" value="3"> 服务端进程是否被重启过</label>
</div>
<div class="quiz-explanation">💡 这几项正是教程列举的创建订单校验清单。下单是资金和库存强相关的操作，只看业务码很容易放过"金额算错"或"库存没扣"这类严重问题</div>
</div>

<div class="quiz-item" data-correct="2">
<div class="quiz-question">把 Token 写死在脚本里会带来什么问题？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q11" value="0"> 会让用例执行速度明显变慢</label>
<label class="quiz-option"><input type="radio" name="q11" value="1"> 会导致 Allure 报告无法生成</label>
<label class="quiz-option"><input type="radio" name="q11" value="2"> Token 过期后全部用例失败，应改为通过登录接口动态获取</label>
<label class="quiz-option"><input type="radio" name="q11" value="3"> 会导致数据库连接失败</label>
</div>
<div class="quiz-explanation">💡 教程把"Token 写死"列为常见新手错误，改法是登录接口动态获取。否则 Token 一过期，整批用例集体报错，排查时很难分辨是脚本问题还是业务问题</div>
</div>

<div class="quiz-item" data-correct="3">
<div class="quiz-question">生成并查看 Allure 报告，正确的命令组合是？</div>
<div class="quiz-options">
<label class="quiz-option"><input type="radio" name="q12" value="0"> 执行 <code>pytest --html=report.html</code> 即可</label>
<label class="quiz-option"><input type="radio" name="q12" value="1"> 直接执行 <code>allure serve</code>，它会自动运行测试</label>
<label class="quiz-option"><input type="radio" name="q12" value="2"> 执行 <code>pytest -n auto</code> 打开图形报告</label>
<label class="quiz-option"><input type="radio" name="q12" value="3"> 先用 <code>pytest --alluredir=reports/allure-results</code> 产出结果，再用 <code>allure serve reports/allure-results</code> 查看</label>
</div>
<div class="quiz-explanation">💡 <code>--alluredir</code> 负责生成原始结果文件，<code>allure serve</code> 负责渲染成可浏览的报告，两步分工不同。配合 <code>@allure.feature</code>、<code>@allure.story</code> 和 <code>with allure.step</code> 才能让报告读出模块、用例名和失败原因</div>
</div>
