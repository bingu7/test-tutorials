# 电商系统测试实战

!!! info "概述"
    本项目以常见电商业务为背景，训练从需求分析到测试报告输出的完整流程。它适合作为第一阶段综合项目，用来串联测试理论、接口测试、数据库校验、抓包联调和自动化测试。

| 项目 | 说明 |
|------|------|
| 适合人群 | 已学完测试理论、SQL、接口基础，想练完整测试流程的新手 |
| 前置知识 | 测试点拆分、用例编写、Postman 基础、简单 SQL 查询 |

## 一、项目背景

假设团队正在开发一个简化版电商系统，核心目标是支持用户浏览商品、加入购物车、提交订单并完成支付。测试人员需要在上线前完成主流程验证、异常场景覆盖和关键数据校验。

如果你是新手，可以先把电商系统理解成一句话：

```text
用户找到想买的商品，把商品放进购物车，确认商品和金额后生成订单，最后完成支付。
```

测试人员要做的事，不是只点一遍页面，而是确认每一步在正常、异常、边界、权限和数据层面都没有明显问题。

### 业务角色

| 角色 | 主要行为 |
|------|----------|
| 游客 | 浏览商品、搜索商品、查看商品详情 |
| 注册用户 | 登录、加购物车、下单、查看订单 |
| 管理员 | 管理商品、查看订单、处理库存 |

### 核心模块

| 模块 | 说明 |
|------|------|
| 用户模块 | 注册、登录、退出、Token 鉴权 |
| 商品模块 | 商品列表、搜索、详情、上下架 |
| 购物车模块 | 添加商品、修改数量、删除商品 |
| 订单模块 | 创建订单、取消订单、查询订单 |
| 支付模块 | 发起支付、支付回调、支付状态查询 |
| 库存模块 | 下单扣减库存、取消恢复库存 |

## 二、新手先搞懂三个概念

### 2.1 业务流程

业务流程就是用户完成一件事的步骤。以下单为例：

```text
登录
  ↓
搜索商品
  ↓
进入商品详情
  ↓
加入购物车
  ↓
提交订单
  ↓
支付或取消订单
```

你先能把这个流程讲清楚，再去写测试点。

### 2.2 测试点

测试点是“我要检查什么”。例如“加入购物车”可以检查：

- 未登录能不能加购物车。
- 商品下架后能不能加购物车。
- 库存不足时能不能加购物车。
- 重复添加同一商品，数量是否累加。
- 加购成功后数据库有没有生成购物车记录。

### 2.3 测试用例

测试用例是把测试点变成可执行步骤。一个完整用例至少包含：

```text
编号
模块
场景
前置条件
操作步骤
预期结果
优先级
```

测试点偏“想法”，测试用例偏“执行”。

## 三、需求分析

以“用户下单”为例，可以拆成下面的业务规则：

1. 用户必须登录后才能创建订单。
2. 商品必须处于上架状态。
3. 商品库存必须大于购买数量。
4. 订单金额应等于商品单价乘以数量，再叠加优惠、运费等规则。
5. 创建订单成功后，库存应被扣减。
6. 支付成功后，订单状态应变为已支付。
7. 支付失败或超时后，订单状态不能误改为已支付。
8. 取消未支付订单后，库存应恢复。

测试时不要只验证页面提示，还要关注接口响应、数据库状态、库存变化和订单状态流转。

## 四、从需求到测试点：完整示例

假设需求写的是：

```text
用户登录后，可以把上架且有库存的商品加入购物车，并提交订单。订单创建成功后，系统扣减库存，订单状态为待支付。
```

新手不要急着写用例，先问问题：

| 问题 | 为什么要问 |
|------|------------|
| 用户没登录怎么办 | 涉及鉴权 |
| 商品下架怎么办 | 涉及商品状态 |
| 库存不足怎么办 | 涉及边界和数据一致性 |
| 重复提交怎么办 | 涉及幂等和重复扣库存 |
| 创建订单失败时库存是否恢复 | 涉及事务一致性 |
| 用户能否查看别人订单 | 涉及越权 |

然后把问题转成测试点：

| 需求点 | 测试点 |
|--------|--------|
| 用户登录后才能下单 | 未登录下单、Token 过期下单、正常登录下单 |
| 商品必须上架 | 下架商品不可下单 |
| 商品必须有库存 | 库存为 0、库存不足、库存刚好等于购买数量 |
| 创建订单扣库存 | 订单成功后库存减少，订单失败后库存不变 |
| 订单状态待支付 | 创建后状态正确，不能直接变成已支付 |

最后再写测试用例。这个过程就是需求分析到测试设计的核心。

## 八、测试用例设计

| 编号 | 模块 | 场景 | 前置条件 | 操作步骤 | 预期结果 | 优先级 |
|------|------|------|----------|----------|----------|--------|
| TC001 | 登录 | 正确账号密码登录 | 用户已注册且状态正常 | 输入账号密码并提交 | 登录成功，返回 Token | P0 |
| TC002 | 登录 | 密码错误 | 用户已注册 | 输入正确账号和错误密码 | 登录失败，提示账号或密码错误 | P0 |
| TC003 | 商品 | 商品详情查看 | 商品已上架 | 打开商品详情页 | 展示名称、价格、库存、图片 | P0 |
| TC004 | 购物车 | 添加上架商品 | 用户已登录，商品有库存 | 点击加入购物车 | 添加成功，购物车数量增加 | P0 |
| TC005 | 购物车 | 添加超过库存数量 | 用户已登录，库存为 5 | 添加数量 6 | 添加失败或提示库存不足 | P0 |

| TC008 | 订单 | 库存不足创建订单 | 商品库存不足 | 提交订单 | 创建失败，库存不扣减 | P0 |
| TC009 | 支付 | 支付成功回调 | 订单待支付 | 模拟支付成功回调 | 订单状态变为已支付 | P1 |
| TC010 | 订单 | 取消未支付订单 | 订单待支付 | 点击取消订单 | 状态变为已取消，库存恢复 | P1 |

### 用例怎么写得更清楚

新手常见问题是“步骤太粗”。例如：

```text
错误写法：提交订单，查看结果。
```

更好的写法：

```text
1. 使用正常账号登录系统。
2. 搜索库存充足的上架商品。
3. 将商品加入购物车。
4. 在购物车中勾选该商品并点击结算。
5. 确认收货地址和金额后提交订单。
6. 查看订单详情和数据库订单记录。
```

预期结果也要具体：

```text
错误写法：订单正常。
正确写法：订单创建成功，订单状态为待支付，订单金额正确，库存减少 1。
```

## 九、接口测试设计

### 9.1 核心接口清单

| 接口 | 方法 | 关注点 |
|------|------|--------|
| `/api/login` | POST | 参数校验、Token、错误提示 |
| `/api/products` | GET | 分页、筛选、搜索 |
| `/api/products/{id}` | GET | 商品存在、上下架、库存展示 |
| `/api/cart` | POST | 鉴权、库存、重复添加 |
| `/api/orders` | POST | 鉴权、库存扣减、金额计算 |
| `/api/orders/{id}` | GET | 订单归属、越权访问 |
| `/api/orders/{id}/cancel` | POST | 状态校验、库存恢复 |

### 9.2 创建订单接口用例

| 场景 | 请求数据 | 预期 |
|------|----------|------|
| 正常下单 | 有效商品、数量小于库存 | 返回订单号，状态为待支付 |
| 未登录下单 | 不带 Token | 返回 401 |
| 商品不存在 | 商品 ID 不存在 | 返回商品不存在 |
| 商品下架 | 商品状态为下架 | 返回商品不可购买 |
| 库存不足 | 购买数量大于库存 | 返回库存不足 |
| 重复提交 | 同一请求短时间重复提交 | 不应重复扣库存或重复创建订单 |

### 9.3 断言重点

接口测试不要只断言状态码，还要断言：

- 响应业务码是否正确。
- 错误信息是否明确。
- 订单金额是否正确。
- 库存是否按预期变化。
- 用户是否只能访问自己的订单。

## 十、数据库校验

### 10.1 常见表设计

| 表 | 用途 |
|----|------|
| `users` | 用户信息 |
| `products` | 商品信息 |
| `cart_items` | 购物车明细 |
| `orders` | 订单主表 |
| `order_items` | 订单明细 |
| `inventory` | 库存信息 |

### 10.2 校验 SQL 示例

```sql
-- 查询订单主表
SELECT id, user_id, status, total_amount
FROM orders
WHERE id = 10001;

-- 查询订单明细
SELECT order_id, product_id, quantity, price
FROM order_items
WHERE order_id = 10001;

-- 查询商品库存
SELECT product_id, stock
FROM inventory
WHERE product_id = 20001;
```

### 10.3 数据校验重点

| 场景 | 校验点 |
|------|--------|
| 创建订单成功 | 订单主表、订单明细、库存扣减一致 |
| 创建订单失败 | 不应生成脏订单，不应扣减库存 |
| 支付成功 | 订单状态、支付时间、支付流水一致 |
| 取消订单 | 订单状态取消，库存恢复 |

### 数据库校验怎么做

新手可以按“操作前查一次、操作后查一次”的方式练：

```text
Step 1：下单前查询商品库存，例如库存是 10。
Step 2：提交 1 件商品订单。
Step 3：下单后再次查询库存，应该变成 9。
Step 4：查询订单表，应该新增一条待支付订单。
Step 5：查询订单明细表，商品 ID、数量、价格应该正确。
```

如果接口返回成功，但数据库没有变化，说明可能存在数据写入问题。  
如果数据库变化了，但接口返回失败，说明可能存在事务或异常处理问题。

## 十一、缺陷示例

### 缺陷 1：库存不足仍能创建订单

| 字段 | 内容 |
|------|------|
| 标题 | 库存不足时仍能创建订单并扣减库存 |
| 严重级别 | 严重 |
| 前置条件 | 商品库存为 1 |
| 复现步骤 | 登录用户，购买数量输入 2，提交订单 |
| 实际结果 | 订单创建成功，库存变为负数 |
| 期望结果 | 提示库存不足，不创建订单，不扣库存 |
| 定位建议 | 检查创建订单接口的库存校验和事务处理 |

### 缺陷 2：用户可查看他人订单

| 字段 | 内容 |
|------|------|
| 标题 | 修改订单 ID 后可查看其他用户订单详情 |
| 严重级别 | 严重 |
| 前置条件 | 用户 A 和用户 B 均存在订单 |
| 复现步骤 | 用户 A 登录后请求用户 B 的订单 ID |
| 实际结果 | 返回用户 B 的订单详情 |
| 期望结果 | 返回无权限或订单不存在 |
| 定位建议 | 检查订单查询接口是否校验 `user_id` 归属 |

### 12.1 执行概况

| 项目 | 结果 |

### 12.2 风险结论

- 订单创建存在库存一致性风险，需要修复后回归。
- 订单详情存在越权访问风险，属于上线阻塞问题。
- 支付回调异常场景覆盖不足，需要补充超时、重复回调和签名错误场景。

### 12.3 上线建议

当前不建议直接上线。需要优先修复库存不足下单和订单越权问题，完成回归测试后再评估发布。

## 动手任务：从一条线上反馈做到上线建议

> 这是本教程的收尾练习。请**独立完成**，不要先看参考答案。目标不是背测试用例模板，而是能把一个模糊的线上投诉，拆成可执行的测试点、可复现的证据和可拍板的结论。

### 任务背景

周一上午运营在群里反馈：「有用户下了 2 件商品，每件 199 元，订单金额显示成了 199 元，客服手动改单才发货。」

你手上只有这条反馈、一段需求摘要和一个测试环境。研发说「大概率是前端显示问题」，但你还没验证。你需要自己判断这是显示缺陷还是金额算错，会不会造成少收款，以及今天能不能上线。

**需求摘要（节选）**：

- 商品支持单品促销价，也支持「满 300 减 50」的订单级优惠券。
- 优惠券按**商品应付金额（数量 × 单价）之和**计算门槛，不叠加运费。
- 订单实付金额 = 商品应付金额 − 优惠金额 + 运费。
- 优惠券每用户每活动限用 1 张。

### 任务准备

测试环境数据库（测试库可直接查询，禁止在生产执行任何写操作）：

```sql
-- 商品表
CREATE TABLE product (
  id          BIGINT PRIMARY KEY,
  title       VARCHAR(100),
  unit_price  DECIMAL(10,2)   -- 单品促销价
);

-- 订单表
CREATE TABLE orders (
  id             BIGINT PRIMARY KEY,
  user_id        BIGINT,
  total_amount   DECIMAL(10,2),   -- 商品应付金额
  discount_amount DECIMAL(10,2),  -- 优惠金额
  freight        DECIMAL(10,2),
  pay_amount     DECIMAL(10,2),   -- 实付金额
  coupon_id      BIGINT NULL,
  status         VARCHAR(20)
);

-- 订单明细
CREATE TABLE order_item (
  id          BIGINT PRIMARY KEY,
  order_id    BIGINT,
  product_id  BIGINT,
  quantity    INT,
  price       DECIMAL(10,2),      -- 下单时成交单价
  item_amount DECIMAL(10,2)       -- 小计
);
```

??? tip "参考答案与思路（先自己做完再看）"

    **第 1 题：测试点清单**

    核心是把反馈里的「2 件 × 199 元」翻译成**金额计算链路**，而不是只测一个场景。

    | 序号 | 测试点 | 设计方法 | 预期结果 |
    |------|--------|----------|----------|
    | 1 | 同一商品买 1 件（199.00） | 边界值（门槛下） | total=199.00, discount=0, pay=199.00+运费 |
    | 2 | 同一商品买 2 件（398.00） | 主场景复现 | total=398.00, discount=50, pay=348.00+运费 |
    | 3 | 凑单恰好 300.00 | 边界值（门槛上） | discount=50（门槛为「满」即 ≥） |
    | 4 | 凑单 299.00 | 边界值（门槛下 1 分） | discount=0 |
    | 5 | 凑单 300.01 | 边界值（门槛上 1 分） | discount=50 |
    | 6 | 不同单价商品混合（199 + 88 = 287） | 等价类 | discount=0 |
    | 7 | 不同单价商品混合（199 × 2 + 88 = 486） | 等价类 | discount=50 |
    | 8 | 优惠券重复使用 | 状态迁移 | 第二次下单券失效或报错 |
    | 9 | 同一用户并发下两单 | 并发 | 只有一单享受优惠 |
    | 10 | 买数量 0 / 负数 / 超大值 | 异常边界 | 参数校验拦截 |
    | 11 | 库存为 0 商品（P1003） | 业务规则 | 下单被拒，不产生订单 |
    | 12 | 金额字段落库与响应一致 | 数据一致性 | 三个字段算术自洽 |

    门槛判定最容易被写错的是「满 300」到底是 `>` 还是 `>=`——需求写「满 300 减 50」，按中文语义是 `>= 300`，第 3、4 题就是在锁这个点。

    **第 2 题：接口验证**

    ```bash
    curl -s -X POST 'http://test-env/api/order/create' \
      -H 'Content-Type: application/json' \
      -H 'Authorization: Bearer <token>' \
      -d '{"items":[{"productId":"P1001","quantity":2}],"couponId":9001}'
    ```

    关键不是看 HTTP 200，而是把响应里的三个字段代进公式验算：

    ```text
    total_amount    = 199.00 × 2            = 398.00
    discount_amount = 满 300 减 50          = 50.00
    pay_amount      = 398.00 - 50.00 + 0.00 = 348.00
    ```

    如果实测返回 `pay_amount = 199.00`，且 `total_amount = 398.00`，说明**计算没算错，是取值取错了**（取成了单件价）。这时可以把范围从「计算逻辑」收窄到「字段映射 / 前端取值」。

    **第 3 题：SQL 校验**

    ```sql
    -- 1) 主表金额算术关系
    SELECT id, total_amount, discount_amount, freight, pay_amount,
           ROUND(total_amount - discount_amount + freight, 2) AS expect_pay,
           CASE WHEN pay_amount = ROUND(total_amount - discount_amount + freight, 2)
                THEN 'OK' ELSE 'MISMATCH' END AS pay_check
    FROM orders WHERE id = ?;

    -- 2) 明细小计与 数量×单价 是否一致
    SELECT id, order_id, quantity, price, item_amount,
           ROUND(quantity * price, 2) AS expect_item,
           CASE WHEN item_amount = ROUND(quantity * price, 2)
                THEN 'OK' ELSE 'MISMATCH' END AS item_check
    FROM order_item WHERE order_id = ?;

    -- 3) 明细之和 = 主表 total_amount
    SELECT o.id, o.total_amount, SUM(i.item_amount) AS sum_items
    FROM orders o JOIN order_item i ON i.order_id = o.id
    WHERE o.id = ?
    GROUP BY o.id, o.total_amount;
    ```

    三条 SQL 分别对应「主表自洽 / 明细自洽 / 主从一致」三层。三层全 OK，说明**服务端和数据库都对**，问题只可能在展示层。

    **第 4 题：缺陷定性与上线建议**

    判断路线：

    ```text
    响应体 pay_amount 正确 + 数据库 pay_amount 正确
        → 缺陷在展示层（前端取值/格式化），资金无损，S2~S3，可排期修复
    
    响应体 pay_amount 正确 + 数据库 pay_amount 错误
        → 缺陷在数据层（写库逻辑），资金有损，S1~S2，必须阻断上线并筛历史订单
    
    响应体 pay_amount 就错
        → 缺陷在接口/服务层，资金有损，S1，阻断上线
    
    三层都对，但并发下出现优惠重复
        → 并发控制缺陷，S1~S2，阻断上线（资损可被利用）
    ```

    参考结论（按「三层全对」假设）：

    - 缺陷层级：**展示层**（订单确认页或订单详情页直接用了 `order_item.price` 渲染总价，未使用 `orders.pay_amount`）。
    - 是否资损：**无**，实收金额正确。
    - 影响范围：**所有多件下单用户**的订单详情展示。
    - 严重程度：**S3**（误导用户 + 产生客服成本，不造成资金损失）。
    - 上线建议：**可带险上线**，修复展示取值后回归；上线前需跑一次「历史订单金额展示抽样（≥ 100 单）」，确认无其他展示分支漏改。

    最不该出现的结论是「建议研发排查」——测试的价值就体现在这一步能把范围钉死到具体层级。
