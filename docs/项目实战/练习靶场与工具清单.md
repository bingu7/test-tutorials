# 练习靶场与工具清单

学接口测试、自动化测试最大的障碍不是"不会写脚本"，而是**没有一个可以随便折腾的被测对象**。

公司系统不能乱测，自己的电脑上又起不动一套电商系统。这一页解决这个问题：给你一批**实测可用**的公开靶场，配上具体练什么、哪里有坑。

!!! abstract "这一页怎么用"
    - 想练**接口测试基础** → 从 [restful-booker](#lab-restful-booker) 开始
    - 想练**鉴权与 Token** → restful-booker 或 [dummyjson](#lab-dummyjson)
    - 想练**自动化框架** → 任意一个 + 你自己的分层结构
    - 想练**完整业务链路**（下单/支付/幂等）→ 公开靶场都不够，见 [第九节](#lab-fallback)

!!! warning "先记住一条最重要的"
    下面这些靶场里，**大部分"写操作"是假成功**：接口返回 `201 Created` 和一个新 id，但你用这个 id 去查，会得到 `404`。

    这**不是靶场的缺陷**，而是你理解错了它的行为。这个认知差别，恰好是接口测试最核心的一课：**写入接口返回成功，不等于数据真的写进去了。**

## 一、靶场选型速查表

下表的每一行都经过实际请求验证（验证时间见页脚）。

| 靶场 | 鉴权 | 写入真持久化 | 最适合练 | 已知坑 |
|------|------|--------------|----------|--------|

| [reqres](#lab-reqres) | ⚠️ 假 Token | ❌ 否 | 分页、延迟模拟、错误码 | 写入是假成功 |
| [jsonplaceholder](#lab-jsonplaceholder) | ❌ | ❌ 否 | 最基础的 CRUD 概念 | 写入是假成功 |

    - **只选一个**：选 **restful-booker**，它是唯一同时具备"真持久化 + 真鉴权"的完整靶场

    - **要验证请求构造对不对**：用 **httpbin**（它会把你的请求原样回显）

## 二、restful-booker：最推荐的接口练习靶场 { #lab-restful-booker }

```
Base URL: https://restful-booker.herokuapp.com
```

这是一个酒店预订系统的简化 API，是业界最经典的接口测试练习靶场。**它最大的价值是：写入的数据真的会被保存。**

### 2.1 接口清单

| 方法 | 路径 | 说明 | 需要鉴权 |
|------|------|------|----------|
| POST | `/auth` | 登录获取 Token | — |
| GET | `/ping` | 健康检查 | — |
| GET | `/booking` | 查询所有预订 id 列表 | — |
| GET | `/booking/{id}` | 查询单个预订详情 | — |
| POST | `/booking` | 创建预订 | — |
| PUT | `/booking/{id}` | 全量更新 | ✅ |
| PATCH | `/booking/{id}` | 部分更新 | ✅ |
| DELETE | `/booking/{id}` | 删除 | ✅ |

### 2.2 登录获取 Token

```bash
curl -X POST https://restful-booker.herokuapp.com/auth \
  -H "Content-Type: application/json" \
  -d '{"username": "admin", "password": "password123"}'
```

响应：

```json
{"token": "253affc07ff07cc"}
```

这个 Token 不是 Bearer 格式，而是通过 **Cookie** 传递：

```bash
# 更新预订时带 Token 的方式
curl -X PUT https://restful-booker.herokuapp.com/booking/1 \
  -H "Content-Type: application/json" \
  -H "Cookie: token=253affc07ff07cc" \
  -d '{"firstname":"Updated","lastname":"Probe","totalprice":123,"depositpaid":true,
       "bookingdates":{"checkin":"2026-01-01","checkout":"2026-01-05"}}'
```

!!! warning "这里是最容易踩的坑"
    ```
    ❌ 错误做法：把 token 当成 Bearer 放进 Authorization 头
       → 服务端不认，PUT 返回 403

    ✅ 正确做法：Cookie: token=<你的token>
    ```

    **这个坑本身就是很好的测试经验**：不同系统的鉴权方式不同（Bearer / Cookie / API Key / 自定义头），必须看接口文档确认，**不能凭经验假设**。

### 2.3 ⚠️ 缺 Accept 头会返回 418

这是这个靶场最著名的"怪脾气"，实测结果：

| 请求头 | 结果 |
|--------|------|
| 不带 `Accept` | **418 I'm a Teapot** |
| `Accept: application/json` | 200，返回 JSON |
| `Accept: application/xml` | 200，**返回 XML** |
| `Accept: text/html` | **418 I'm a Teapot** |

```bash
# 会返回 418
curl https://restful-booker.herokuapp.com/booking/1

# 正常返回 200 + JSON
curl -H "Accept: application/json" https://restful-booker.herokuapp.com/booking/1
```

!!! abstract "为什么会这样？"
    418 是 HTTP 协议里一个半开玩笑的保留状态码（"我是个茶壶"，出自 1998 年的愚人节 RFC）。这个靶场用它来表示"**我无法提供你要求的响应格式**"。

    从测试角度看，它其实演示了一个真实场景：**服务端会根据 `Accept` 头做内容协商（Content Negotiation）**。同一个 URL，客户端的 `Accept` 不同，返回的格式不同（JSON / XML / 拒绝）。

    **测试启示**：写接口用例时，`Accept` 头应该作为一个参数化变量去覆盖，而不是永远固定成 JSON。

### 2.4 练习任务

**任务 A：设计鉴权测试用例（5 条以上）**

围绕 `DELETE /booking/{id}`，覆盖以下场景：

1. 不带 Token → 期望 403
2. 带正确 Token → 期望 201/200
3. 带**错误** Token → 期望 403
4. 带**过期或格式错误**的 Token → 期望 403
5. 把 Token 放在 `Authorization: Bearer` 头（错误位置）→ 观察实际结果，与文档对比

**任务 B：完整 CRUD 闭环 + 数据校验**

```text
步骤：
1. POST /booking 创建一条预订，记录返回的 bookingid
2. GET /booking/{id} 读回，逐字段比对与创建时是否一致
3. PUT /booking/{id} 修改 firstname，带 Token
4. GET 再次读回，确认 firstname 已变更、其他字段未被意外清空
5. DELETE /booking/{id}，带 Token
6. GET /booking/{id}，确认返回 404
```

!!! tip "第 4 步是重点"
    **PUT 是全量更新**——如果你漏传某个字段，它可能被清空。这是真实项目中非常常见的缺陷类型（"改一个字段把别的字段弄丢了"）。

    **测试点**：PUT 时故意只传部分字段，观察未传的字段是被保留、被清空还是报错。三种行为都不算错，但**必须符合接口文档的约定**。

**任务 C：参数化与边界值**

对 `POST /booking` 的 `totalprice` 字段做边界值测试：

```text
0 / -1 / 0.01 / 极大值（如 99999999999）/ 字符串 "abc" / null
```

记录每个输入的响应，判断服务端的校验是否合理（例如负价格是否被拒绝）。

## 三、petstore：Swagger 官方示例 { #lab-petstore }

```
Base URL: https://petstore.swagger.io/v2
文档:     https://petstore.swagger.io
```

这是 Swagger 官方的示例 API，**最大的价值是它有一份标准的 Swagger 文档**——可以练习"根据接口文档设计用例"这个真实工作流。

### 3.1 特点

| 项目 | 说明 |
|------|------|
| 鉴权 | 无 |
| 写入持久化 | ✅ 是（自己创建的数据能读回） |
| 接口数量 | 多（pet / store / user 三组） |
| 文档 | 标准 Swagger / OpenAPI，页面可直接试用 |

### 3.2 ⚠️ 种子数据已被污染

实测结果：

| 请求 | 结果 |
|------|------|
| `GET /pet/1` | 200，返回 `doggie` |
| `GET /pet/2` | **404 Not Found** |
| `GET /pet/3` | **404 Not Found** |
| `GET /pet/4` | 200 |
| `GET /pet/5` | 200 |

因为这是公开靶场，**全世界的练习者都在上面增删改**。`/pet/2`、`/pet/3` 这类经典种子数据已经被别人删掉了。

查询 `findByStatus` 更能看出污染程度：

```bash
curl "https://petstore.swagger.io/v2/pet/findByStatus?status=available"
```

返回的数据里混着大量其他练习者造的测试数据，名字类似 `pwp-pet-1789615551242`、`test_pet_for_api_tool`。

!!! danger "核心教训：不要写死测试数据"
    ```
    ❌ 错误做法：用例里断言 GET /pet/1 返回 name == "doggie"
       → 别人把 pet/1 改了或者删了，你的用例就"失败"了
       → 这不是发现了缺陷，是你的用例设计有问题

    ✅ 正确做法：
       1. 先 POST 创建自己的数据，拿到自己生成的 id
       2. 用这个 id 做后续的 GET / PUT / DELETE
       3. 用例结束后 DELETE 清理
    ```

    **这个原则在真实工作中同样成立**：用例不应该依赖环境里"碰巧存在"的数据，而应该自己准备数据。详见 [测试框架设计与设计模式](../自动化测试/测试框架设计与设计模式教程.md) 里的"数据三级分层"。

### 3.3 练习任务

**任务 A：文档驱动设计用例**

打开 `https://petstore.swagger.io`，只用文档（不看教程提示），完成：

1. 找出所有**不需要鉴权**的接口
2. 找出 `POST /pet` 的必填字段是哪些
3. 为 `POST /pet` 设计 8 条用例：必填缺失、id 重复、status 非法值、字段类型错误等

**任务 B：状态查询与数据校验**

```text
1. GET /store/inventory 获取库存统计
2. 记录某个 status（如 available）的数量
3. POST /pet 新增一条 available 状态的宠物
4. 再次 GET /store/inventory，确认 available 数量 +1
5. DELETE 刚才创建的宠物，确认数量恢复
```

**任务 C：体验"污染"的影响**

故意用 `GET /pet/2` 断言 `name == "doggie"`，让它失败。然后思考并写下：这条用例失败的原因是什么？应该怎么改？

## 四、dummyjson：鉴权与数据校验 { #lab-dummyjson }

```
Base URL: https://dummyjson.com
```

有完整的用户、商品、购物车数据，**带真实的 JWT 鉴权**，字段丰富，很适合做数据校验练习。

### 4.1 特点

| 项目 | 说明 |
|------|------|
| 鉴权 | ✅ **真实 JWT**（不是假的） |
| 写入持久化 | ❌ **否**（假成功） |
| 数据量 | 商品 194 条、用户 100 条 |
| 分页 | ✅ 支持 `limit` / `skip` / `select` |

**测试账号：**

```text
用户名: emilys
密码:   emilyspass
```

### 4.2 鉴权是真的，实测有效

```bash
# 登录
curl -X POST https://dummyjson.com/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"emilys","password":"emilyspass"}'
```

返回真实的 JWT（`accessToken` 是三段式 JWT，可解码）：

```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refreshToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "id": 1,
  "username": "emilys",
  ...
}
```

鉴权校验确实生效：

| 请求 | 结果 |
|------|------|
| `GET /auth/me` 带 `Authorization: Bearer <token>` | ✅ 200，返回用户信息 |
| `GET /auth/me` 不带 Token | ✅ 401 `{"message":"Access Token is required"}` |

!!! tip "可以用它练 JWT 解析"
    因为这是**真的 JWT**，你可以把 token 拿到 [jwt.io](https://jwt.io) 解码，看到 payload 里的用户信息。这在真实工作中是排查鉴权问题的常用手段。

    **练习点**：解码后检查 payload 里有没有敏感信息（如明文密码、手机号）——**这是安全测试的检查项**。

### 4.3 分页与数据校验

```bash
# 分页 + 字段筛选
curl "https://dummyjson.com/products?limit=5&skip=10&select=title,price"
```

响应：

```json
{"total": 194, "skip": 10, "limit": 5, "products": [...]}
```

**可练习的校验点：**

```text
1. total 是否等于实际总数
2. 返回条数是否等于 limit
3. skip=10 时，第一条数据的 id 是否等于 11（即真的跳过了前 10 条）
4. 返回的字段是否只有 title 和 price（select 是否生效）
5. skip + limit 超过 total 时，返回是空数组还是报错
```

### 4.4 ⚠️ 写入是假成功

实测：

```text
POST /carts/add   → 201 Created，返回新 id = 209
GET  /carts/209   → 404 {"message":"Cart with id '209' not found"}
```

```text
PUT  /products/1  → 200 OK
GET  /products/1  → title 仍是原值，**未被修改**
```

!!! warning "这个特性非常适合用来练一件事"
    它模拟了一个真实场景：**接口返回成功，但数据没有真正落库。**

    在真实系统里，这往往是**严重缺陷**（比如写入了从库、写入了缓存没落库、事务未提交、消息没投递）。

    你可以用它练习写出"**写入后必须读回校验**"的测试习惯：

    ```python
    def test_create_and_verify():
        # 1. 创建
        resp = post("/carts/add", {...})
        assert resp["status"] == 201
        new_id = resp["json"]["id"]

        # 2. 关键：读回验证，而不是只看创建接口的返回
        detail = get(f"/carts/{new_id}")
        # 在这里你会拿到 404 —— 学会区分"接口假成功"与"自己断言写错"
        assert detail["status"] == 200, "创建成功但读回失败，需确认是靶场特性还是真实缺陷"
    ```

    这段"读回校验"的习惯，正是接口自动化里最有价值的断言模式。

## 五、reqres：分页与错误场景 { #lab-reqres }

```
Base URL: https://reqres.in/api
```

专门为 API 测试设计的服务，接口简洁，适合练分页和错误码。

### 5.1 特点

| 项目 | 说明 |
|------|------|
| 鉴权 | ⚠️ 返回 token 但**不实际校验** |
| 写入持久化 | ❌ 否 |
| 特色 | 支持模拟**延迟响应** |

### 5.2 可用接口

| 请求 | 实测结果 |
|------|----------|
| `GET /users?page=2` | 200，返回分页数据（`page`/`per_page`/`total`/`total_pages`） |
| `POST /login` | 200，返回 token |
| `GET /users/23` | **404**（id 超出范围） |
| `POST /users` | 201，返回假 id，**读回 404** |

### 5.3 练习任务：分页边界

```text
1. GET /users?page=1 → 记录 total 和 total_pages
2. GET /users?page=2 → 验证是否返回不同的数据
3. GET /users?page=3 → 超出 total_pages 时返回什么？
4. GET /users?page=0 / -1 / "abc" → 非法值如何处理？
5. 验证 page=1 和 page=2 的 id 是否有重复（分页是否重叠）
```

!!! tip "第 5 步是真实工作里容易漏的点"
    分页重叠/漏数据是**经典缺陷**：不同页之间返回了同一条数据，或者某条数据在两页之间"消失"了。

    在生产系统里，这通常由"排序不稳定"引起（比如按 `created_at` 排序，但同一秒有多条数据）。**这是很好的面试话题。**

## 七、httpbin 与 postman-echo：请求回显 { #lab-httpbin }

```
httpbin:      https://httpbin.org
postman-echo: https://postman-echo.com
```

这两个服务的特点是：**把你发过去的请求原样回显给你**。用来验证"我的请求到底构造对了吗"极其方便。

| 请求 | 用途 |
|------|------|
| `GET /get` | 回显 URL 参数、请求头 |
| `POST /post` | 回显请求体 |
| `GET /status/404` | 返回指定状态码 |
| `GET /delay/3` | 延迟 3 秒响应（**练超时**） |
| `GET /redirect/2` | 重定向 2 次（**练重定向处理**） |
| `GET /headers` | 回显所有请求头 |
| `GET /basic-auth/user/pass` | 基础认证（**练 401 场景**） |

!!! tip "用它练三件事"
    ```text
    1. 超时处理：GET /delay/5，把你的客户端超时设为 2 秒，
       观察超时异常是否被正确处理

    2. 重定向：GET /redirect/3，看你的客户端是否自动跟随，
       还是需要手动处理

    3. 请求头验证：GET /headers，确认你设置的
       Content-Type、Authorization、自定义头是否真的发出去了
    ```

!!! warning "服务偶发不稳定"
    首次探测 httpbin 时遇到 502，重试 3 次后全部正常。**这是公共服务器的常态。**

    **测试启示**：如果你的自动化用例依赖外部服务，偶发失败要能区分"是被测服务问题还是网络抖动"，否则会产生大量误报。这正是**重试机制**要解决的问题，但要注意——

    重试只能用来区分"环境抖动"与"真实问题"，**不能用来掩盖真实的偶发缺陷**。

## 八、所有靶场的共同坑与应对

### 8.1 数据被其他练习者污染

**现象**：你明明没动过 `/pet/2`，它却 404 了；昨天还能查到的数据，今天变了。

**应对**：

```text
✅ 永远自己创建数据，用自己的 id 做后续操作，用完删除
✅ 断言时校验"结构性属性"（如 id 是否等于自己创建的），
   而不是"具体值"（如 name 是否等于 "doggie"）
✅ 用例之间互相独立，不依赖执行顺序
```

### 8.2 服务可能挂掉或限流

**现象**：请求超时、429、502。

**应对**：

```text
1. 判断是服务问题还是你的问题（换 curl 直接试一次）
2. 在报告里明确记录"外部服务不可用"，而不是记为用例失败
3. 重要练习前先跑一次健康检查（如 restful-booker 的 /ping）
```

### 8.3 国内访问可能较慢

这些都是境外服务，国内访问可能有延迟。如果遇到持续超时，可以用代理，或改用自己的本地服务（见下一节）。

### 8.4 关于 `/ping` 的返回值

!!! warning "restful-booker 的 /ping 返回 201，不是 200"
    实测：`GET /ping` → **201 Created**（还带一个空的响应体）。

    如果你写 `assert status == 200`，会失败。

    **测试启示**：**不要凭"常见惯例"写断言，要按接口文档和实际行为写。** 健康检查接口返回 201 确实奇怪，但它是这个靶场的实际约定——你只能适配它，或者把它作为一个"文档与实现不一致"的观察记录下来。

## 九、兜底方案：当公开靶场都不够用时 { #lab-fallback }

公开靶场能覆盖大部分基础练习，但它们有一个共同的硬伤：**没有真实的业务链路。**

你没法在它们上面测试这些：

```text
❌ 下单 → 扣库存 → 支付 → 回调 → 幂等校验
❌ 优惠券叠加计算 → 订单金额 → 对账
❌ 并发下单时库存超卖
❌ 数据在数据库中的最终一致性
```

因为这些靶场**没有业务状态机**，也没有你能访问的数据库。

!!! abstract "这时候该怎么办"
    有两条路：

    **路线一：改用带完整业务的公开项目（重量级）**
    找开源电商系统（如 mall 类项目），用 Docker 完整部署。优点是业务真实；缺点是依赖重（通常要 MySQL + Redis + MQ + 注册中心），本地经常起不来，镜像几个 G。

    **路线二：自建一个极简的业务 Mock 服务（推荐）**
    自己写一个 200 行左右的服务，只实现你需要的业务链路：登录 → 商品 → 下单 → 支付 → 库存。用 SQLite 存数据（零依赖），一个命令就能起来。

    **为什么推荐路线二**：
    - 零依赖，秒级启动，永远不会"起不来"
    - 你能访问数据库，可以做数据一致性校验
    - 你可以**故意植入缺陷**（比如让下单接口在并发下超卖），用来练习缺陷发现
    - 它本身可以作为你的**面试作品**

    !!! tip "现成的实现"
        本站已提供一个可直接使用的版本，独立仓库维护：

        **[github.com/bingu7/test-lab-api](https://github.com/bingu7/test-lab-api)**

        它是 FastAPI + SQLite 的极简电商 API，支持**可控缺陷**——通过环境变量在「干净模式」和「缺陷模式」之间切换：

        ```bash
        pip install -r requirements.txt
        python -m uvicorn app.main:app --port 8099          # 干净模式：接口全对
        LAB_FLAWS=all python -m uvicorn app.main:app --port 8099   # 缺陷模式：植入 5 个真实缺陷
        ```

        5 个缺陷覆盖：并发超卖、支付回调不幂等、水平越权、金额精度误差、参数校验缺失。
        自带 Pytest 分层示例（**同一套用例：干净模式 25 通过 / 缺陷模式 11 失败**），
        可以直接当作你练习框架设计的起点。

## 十、把靶场变成面试素材

!!! tip "一个被忽略的用法"
    用靶场练习的最大附加价值是：**它产出的是你可以公开给面试官看的东西。**

    在公司做的东西涉及保密，你没法展示代码和报告。但用公开靶场做的练习，你可以：

    ```text
    ✅ 把自动化代码推到自己的 GitHub 仓库
    ✅ 把 Allure 报告截图放进 README
    ```

    **面试官对"自学项目"是认可的，对"编造的公司项目"是零容忍的。** 明确说清这是你自己的练习，然后展示技术细节——这比含糊地说"我在公司做过"要可信得多。

## 附录：靶场可用性自检脚本

公开靶场会失效（服务下线、被墙、限流）。练习前可以先跑一段自检，确认哪些能用：

```python
# lab_check.py —— 靶场可用性自检
import urllib.request, urllib.error

TARGETS = {
    "restful-booker": "https://restful-booker.herokuapp.com/ping",
    "petstore":       "https://petstore.swagger.io/v2/store/inventory",
    "dummyjson":      "https://dummyjson.com/products/1",
    "reqres":         "https://reqres.in/api/users?page=1",
    "jsonplaceholder": "https://jsonplaceholder.typicode.com/posts/1",
    "httpbin":        "https://httpbin.org/get",
    "postman-echo":   "https://postman-echo.com/get",
}

for name, url in TARGETS.items():
    req = urllib.request.Request(
        url,
        headers={"Accept": "application/json", "User-Agent": "lab-check/1.0"},
    )
    try:
        with urllib.request.urlopen(req, timeout=15) as resp:
            print(f"OK    {name:<18} [{resp.status}]")
    except urllib.error.HTTPError as e:
        print(f"HTTP  {name:<18} [{e.code}]  （能连通，返回了错误码）")
    except Exception as e:
        print(f"FAIL  {name:<18} {type(e).__name__}: {str(e)[:50]}")
```

**注意**：`restful-booker` 的 `/ping` 正常应返回 **201**，脚本把任何 HTTP 状态码都视为"能连通"，因为靶场的状态码不总是 200。
