# 接口自动化项目实战

!!! info "概述"
    本实战用于把接口测试方法论、Postman 调试、Python Requests、Pytest、Allure 报告和 CI/CD 串成一个可落地的小型接口自动化项目。

---

## 新手导读

| 项目 | 说明 |
|------|------|
| 适合人群 | 会用 Postman 调接口，准备把核心接口改成自动化脚本的新手 |
| 前置知识 | HTTP、JSON、Postman 环境变量、Python 函数、Pytest 基础 |
| 最终产出 | 一套可运行的接口自动化目录、登录用例、订单用例、数据驱动示例、Allure 报告 |
| 跟练方式 | 先写一个最小登录用例，能跑通后再抽请求封装、测试数据和报告 |
| 常见卡点 | 一开始就搭大框架；Token 写死；只断言 200；测试数据互相污染 |

本实战建议边写边运行。每新增一个文件，都执行一次 `pytest`，确认问题发生在哪一步，避免最后堆出一堆难排查的错误。

## 一、项目目标

本项目以电商系统核心接口为对象，完成一套可维护的接口自动化框架。目标不是把所有接口都自动化，而是先覆盖稳定、关键、高频的主流程。

如果你基础薄弱，先记住一句话：

```text
接口自动化 = 用代码代替 Postman，重复执行接口请求，并自动判断结果是否正确。
```

所以学习顺序应该是：

```text
先用 Postman 手工调通接口
  ↓
再把请求改成 Python 代码
  ↓
再用 Pytest 管理用例
  ↓
再加测试数据、断言、报告和 CI
```

不要一开始就写复杂框架。框架是从重复代码中提炼出来的，不是第一天凭空设计出来的。

### 核心目标

| 目标 | 说明 |
|------|------|
| 请求封装 | 统一处理 Base URL、Header、Token、超时和日志 |
| 用例组织 | 按业务模块拆分登录、商品、购物车、订单接口 |
| 数据驱动 | 用 YAML / JSON / CSV 管理测试数据 |
| 断言策略 | 同时断言状态码、业务码、字段、数据库结果 |
| 报告输出 | 使用 Allure 展示接口用例执行结果 |
| 持续集成 | 支持在 Jenkins 或 GitHub Actions 中执行 |

## 二、新手先搞懂接口自动化在测什么

一个接口请求通常包含：

| 部分 | 说明 | 示例 |
|------|------|------|
| 请求方法 | 表示操作类型 | `GET`、`POST` |
| URL | 接口地址 | `/api/login` |
| Header | 请求头，常放 Token、Content-Type | `Authorization` |
| 参数 | 查询参数、JSON、表单数据 | `username`、`password` |
| 响应状态码 | HTTP 层结果 | `200`、`401`、`500` |
| 响应 body | 业务结果 | `code`、`message`、`data` |

接口自动化不是只看接口有没有返回。你至少要判断：

- HTTP 状态码是否正确。
- 业务 code 是否正确。
- 响应字段是否完整。
- 数据库结果是否符合业务。
- 异常场景是否被正确拒绝。

## 三、从 Postman 到 Python：跟练路线

建议按下面 6 步走：

1. 用 Postman 调通登录接口。
2. 从登录响应里拿到 Token。
3. 带 Token 调用商品详情接口。
4. 带 Token 调用创建订单接口。
5. 把这 3 个请求改写成 Python 代码。
6. 用 Pytest 把代码变成可重复执行的自动化用例。

你先能完成这 6 步，再考虑封装、数据驱动和报告。

## 四、接口范围

第一阶段建议只覆盖 P0 和 P1 接口：

| 模块 | 接口 | 优先级 | 是否自动化 |
|------|------|--------|------------|
| 登录 | `/api/login` | P0 | 是 |
| 商品 | `/api/products` | P0 | 是 |
| 商品 | `/api/products/{id}` | P0 | 是 |
| 购物车 | `/api/cart` | P0 | 是 |
| 订单 | `/api/orders` | P0 | 是 |
| 订单 | `/api/orders/{id}` | P0 | 是 |
| 订单 | `/api/orders/{id}/cancel` | P1 | 是 |
| 支付 | `/api/pay/callback` | P1 | 视环境决定 |

不建议第一版就覆盖低频后台配置接口。自动化优先做稳定流程，变化频繁的接口先保留手工验证。

## 八、请求封装

示例封装思路：

```python
import requests


class ApiClient:
    def __init__(self, base_url, timeout=10):
        self.base_url = base_url.rstrip("/")
        self.timeout = timeout
        self.session = requests.Session()

    def set_token(self, token):
        self.session.headers.update({"Authorization": f"Bearer {token}"})

    def request(self, method, path, **kwargs):
        url = f"{self.base_url}{path}"
        return self.session.request(method, url, timeout=self.timeout, **kwargs)
```

封装后，用例只关注业务行为：

```python
def test_get_product_detail(api_client):
    response = api_client.request("GET", "/api/products/10001")
    assert response.status_code == 200
    assert response.json()["code"] == 0
```

## 九、用例设计

### 9.1 登录接口

| 场景 | 数据 | 预期 |
|------|------|------|
| 正确账号密码 | 有效账号、有效密码 | 登录成功，返回 Token |
| 密码错误 | 有效账号、错误密码 | 登录失败 |
| 账号不存在 | 不存在账号 | 登录失败 |
| 参数缺失 | 不传 password | 参数校验失败 |

### 9.2 创建订单接口

| 场景 | 数据 | 预期 |
|------|------|------|
| 正常下单 | 商品上架、库存充足 | 创建成功 |
| 未登录下单 | 不带 Token | 返回 401 |
| 商品下架 | 下架商品 ID | 创建失败 |
| 库存不足 | 数量大于库存 | 创建失败 |
| 重复提交 | 相同请求重复发送 | 不重复扣库存 |

## 十、数据驱动

示例 `data/login.yaml`：

```yaml
- case_name: 正确账号密码登录
  username: test_user
  password: test_password
  expected_code: 0

- case_name: 密码错误
  username: test_user
  password: wrong_password
  expected_code: 1001
```

测试用例示例：

```python
import pytest


@pytest.mark.parametrize("case", login_cases)
def test_login(api_client, case):
    response = api_client.request(
        "POST",
        "/api/login",
        json={"username": case["username"], "password": case["password"]},
    )
    assert response.json()["code"] == case["expected_code"]
```

数据驱动适合参数组合清晰的接口；复杂业务流程不要过度数据化，否则可读性会下降。

## 十一、断言策略

接口自动化建议分层断言：

| 层级 | 示例 |
|------|------|
| 协议层 | HTTP 状态码、响应时间、Content-Type |
| 业务层 | 业务 code、message、关键字段 |
| 数据层 | 数据库记录、库存、订单状态 |
| 安全层 | 鉴权、越权、敏感字段 |

创建订单接口不能只断言 `code == 0`，还应校验：

- 返回订单号不为空。
- 订单金额正确。
- 订单状态为待支付。
- 库存被正确扣减。
- 订单归属当前用户。

---

## 十二、常见新手错误

| 错误 | 问题 | 改法 |
|------|------|------|
| 只断言状态码 200 | 业务失败也可能返回 200 | 同时断言业务 code 和关键字段 |
| 用例之间强依赖 | 一个失败导致后面全失败 | 单接口用例尽量独立，流程用例单独管理 |
| Token 写死 | Token 过期后全部失败 | 登录接口动态获取 Token |
| 测试数据混用 | 多人执行互相影响 | 使用独立测试账号和可恢复数据 |
| 把所有接口都自动化 | 维护成本过高 | 先做 P0/P1 稳定接口 |

## 十三、Allure 报告

建议在用例中补充标题、模块和步骤：

```python
import allure


@allure.feature("订单模块")
@allure.story("创建订单")
@allure.title("库存充足时创建订单成功")
def test_create_order_success(api_client):
    with allure.step("创建订单"):
        response = api_client.request("POST", "/api/orders", json={"product_id": 10001, "quantity": 1})

    with allure.step("断言订单创建成功"):
        assert response.status_code == 200
        assert response.json()["code"] == 0
```

运行命令：

```bash
pytest --alluredir=reports/allure-results
allure serve reports/allure-results
```

## 十六、维护规范

| 问题 | 建议 |
|------|------|
| 接口字段频繁变化 | 只断言关键字段，不对非核心字段做强绑定 |
| 测试数据污染 | 每次执行前准备数据，执行后清理或使用独立测试数据 |
| 用例互相依赖 | 主流程可以串联，单接口用例尽量独立 |
| 环境不稳定 | 区分脚本失败、环境失败和业务缺陷 |
| 敏感信息泄露 | 密码、Token、密钥使用环境变量或 CI Secret |

接口自动化的价值不只是“自动跑”，更重要的是稳定反馈核心业务是否被破坏。

## 动手任务：把偶发失败的流水线诊断清楚

> 这是本教程的收尾练习。请**独立完成**，不要先看参考答案。目标不是把用例改成「必定通过」，而是能区分脚本问题与被测系统问题，并给出可维护的改造方案。

### 任务背景

接口自动化流水线从上周开始「时绿时红」：同一个 commit 重跑有时全过、有时红 3~8 条，失败用例每次都不一样。研发已经习惯性说「自动化不稳定，忽略就行」，但你说不出到底是哪一边的问题，就没有底气要求修复。

你拿到了流水线最近一次失败的完整报告摘要和一个可重放的测试环境。请定位根因，并给出改造方案。

### 任务准备

流水线失败报告摘要（示例值）：

```text

环境: staging   并发: 4 workers   耗时: 4m12s
结果: 431 passed / 7 failed / 2 error   总用例: 440

失败清单：
FAIL  test_order_query_by_status[status=PAID]     期望 12 条, 实际 11 条
FAIL  test_user_profile_update                    期望 nickname=qa_new, 实际 nickname=qa_old
FAIL  test_cart_add_then_list                     购物车为空
FAIL  test_order_cancel_invalid_state            期望 400, 实际 500
FAIL  test_payment_callback_idempotent            期望幂等, 实际重复扣款
FAIL  test_product_search_keyword                 期望 5 条, 实际 4 条

```

### 任务要求

请依次完成，并**保留每条命令和输出**：

1. **逐条归因**：把上面 9 条失败/错误逐条判定为「脚本问题 / 数据问题 / 被测系统缺陷 / 环境问题」四类之一，并写出判定依据（要引用报告或代码里的具体线索，不要只给结论）。输出表格：用例 / 类别 / 依据 / 置信度。

2. **定位偶发性来源**：说明「同 commit 重跑结果不同」这一点能排除什么、不能排除什么，并指出当前配置里最可能导致随机失败的两处设计。

3. **写改造方案**：给出至少 4 项可落地的改造（含断言分层、数据隔离、依赖处理、失败重试策略），每项写明「改什么 / 怎么改 / 解决上面哪几条失败」。用代码块给出关键改造后的写法。

4. **交付复现脚本 + 改造清单**：写一段最小可运行脚本或命令，能在本地复现「失败 → 重跑通过」的现象；并输出一份改造优先级清单（表格：改造项 / 解决条数 / 工作量 / 优先级）。

### 提交物

| 产出 | 要求 |
|------|------|
| 归因表 | 9 条全覆盖，每条有代码或报告级证据 |
| 偶发性分析 | 300 字以内，说明「能排除 / 不能排除」各是什么 |
| 改造方案 | ≥ 4 项，含改造后代码片段 |
| 优先级清单 | 表格，含工作量与优先级 |
| 复现命令 | 可复制执行，含实际输出 |

### 完成标准

- [ ] 能区分「必然失败」与「偶发失败」的判定逻辑
- [ ] 能识破「同 commit 重跑通过」不等于「脚本问题」的误判
- [ ] 能指出共享数据库 + 并行执行是随机失败的放大器
- [ ] 能给出断言分层方案（传输层 / 业务字段 / 数据层）
- [ ] 改造清单中的每一项都能对应到具体失败用例

??? tip "参考答案与思路（先自己做完再看）"

    **第 1 题：归因表**

    | 用例 | 类别 | 依据 |
    |------|------|------|
    | test_order_query_by_status | 数据问题 | 期望写死 12 条，依赖外部前置数据；并行下被其他 worker 干扰 |
    | test_user_profile_update | 脚本问题 | 断言直连无等待，未处理最终一致性（读从库/缓存） |
    | test_cart_add_then_list | 脚本问题 | 跨用例依赖共享购物车状态，`-n 4` 并行下被清空 |
    | test_order_cancel_invalid_state | 被测系统缺陷 | 非法订单号返回 500 而非 400，属服务端未做参数校验 |
    | test_payment_callback_idempotent | 被测系统缺陷 | 重复扣款是真实资损缺陷，重跑也不会消失 → **最高优先级** |
    | test_product_search_keyword | 数据问题 | 期望 5 条写死，依赖搜索索引/数据量 |
    | test_order_detail_amount | 待定（需复验） | 单跑仍 199.00 则是真缺陷；单跑通过则同上一条属数据污染 |
    | test_coupon_create_duplicate | 脚本问题 | fixture 未做幂等，重复创建撞唯一索引 |
    | test_login_invalid_password | 环境问题 | 连接超时 10s，属环境/网络抖动，非业务缺陷 |

    关键判断：`test_payment_callback_idempotent` 是唯一「重跑仍必然失败」的业务缺陷（幂等性破坏），其余 8 条在重跑中消失，说明它们大多不是业务缺陷。

    **第 2 题：偶发性来源**

    - **能排除**：这些失败与本次代码改动无关；它们不是「新引入的回归」。
    - **不能排除**：被测系统确实存在并发缺陷、时序缺陷或幂等缺陷——偶发失败常常正是**竞态条件**的表现。所以「重跑通过」不是「没问题」，只是「这次没触发」。
    - 最可能的两处设计问题：
      1. **共享 staging 库 + `-n 4` 并行**：用例之间通过数据库隐式耦合，谁先跑谁改变状态，结果随机。
      2. **断言写死绝对值 + 无等待**：`== 12`、`== 5` 这类断言对数据总量敏感；用户资料更新后立即读，未处理主从延迟/缓存。

    **第 3 题：改造方案**

    1. **断言分层**（解决 test_order_detail_amount / test_product_search_keyword 等）

       ```python
       def test_order_detail_amount(api):
           resp = api.post("/api/order/create", json=payload)
           # L1 传输层：状态码 + 协议
           assert resp.status_code == 200
           body = resp.json()
           # L2 业务字段：只断言与本次请求强相关的字段
           assert body["code"] == 0
           assert body["data"]["total_amount"] == "398.00"
           # L3 数据层：用 SQL 校验落库，而不是断言列表长度
           assert query_pay_amount(body["data"]["orderId"]) == Decimal("348.00")
       ```

    2. **数据隔离**（解决 test_order_query_by_status / test_cart_add_then_list）——每个 worker 独立 schema 或用唯一标记数据：

       ```python
       @pytest.fixture(scope="session")
       def tenant(request):
           tag = f"qa_{uuid4().hex[:8]}"      # 每个 worker 一个命名空间
           yield tag
           cleanup(tag)
       ```

    3. **依赖显式化 + 幂等 fixture**（解决 test_coupon_create_duplicate / test_login_invalid_password 的偶发）

       ```python
       @pytest.fixture
       def coupon(api, tenant):
           resp = api.post("/api/coupon/create", json={"code": tenant})
           if resp.status_code == 409:        # 已存在即复用，不报错
               return api.get(f"/api/coupon/{tenant}").json()["data"]
           return resp.json()["data"]
       ```

    4. **最终一致等待 + 失败重试分级**（解决 test_user_profile_update）

       ```python
       def wait_until(fn, timeout=5, interval=0.3):
           deadline = time.time() + timeout
           while time.time() < deadline:
               if fn():
                   return True
               time.sleep(interval)
           return False

       # 仅对「传输层/环境类」失败重试；业务断言失败【不重试】
       @pytest.mark.flaky(reruns=2, reruns_delay=1, only_rerun=["ConnectionError", "Timeout"])
       def test_user_profile_update(api, user_01, tenant): ...
       ```

       注意：`--reruns` 不能开成「所有失败都重试」，否则会把 `test_payment_callback_idempotent` 这类真缺陷也吞掉，这是最常见的错误做法。

    **第 4 题：优先级清单**

    | 改造项 | 解决条数 | 工作量 | 优先级 |
    |--------|----------|--------|--------|
    | 修复支付回调幂等（转研发缺陷跟踪） | 1 条真缺陷 | 研发侧 | P0 |
    | 数据隔离（独立 schema / 命名空间） | 3 条 | 1~2 天 | P0 |
    | 断言分层 + 去掉写死绝对值 | 3 条 | 2~3 天 | P1 |
    | 幂等 fixture + 显式依赖 | 2 条 | 0.5 天 | P1 |
    | 环境类失败定向重试 | 1 条 | 0.5 天 | P2 |

    本地复现「失败 → 重跑通过」：

    ```bash
    # 并行时高概率触发数据耦合
    pytest tests/test_order.py::test_order_query_by_status -n 4 -q
    # 单线程串行时通常通过，证明是并行/数据耦合问题而非业务缺陷
    pytest tests/test_order.py::test_order_query_by_status -q
    ```

    提交前一定要做的动作：把 P0 的真缺陷（幂等破坏）单独拉出来给研发，**不要让「重跑绿了」掩盖它**。
